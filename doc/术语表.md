# dteam 术语表

dteam 是 Pi 里的**模型分级路由执行层 + 主代理证据驱动路由协议**：主模型（T1 思考档）负责确定证据问题、分轮路由、综合与验收，独立小任务 fan-out 给 T3 快速档批量并行做；主模型汇总后按 T3→T2→T1 明确逐级升级。

本文件是 dteam 的命名权威：代码、文档、路线图和对外说明优先使用这里的术语。`_Avoid_` 表示容易造成误解或当前明确不采用的同义词。

## 1. 定位与边界

**dteam（模型分级路由执行层）**：
dteam 的存在理由是「强模型做小任务是双重浪费（贵 + 慢）」。它是一个 Pi 扩展，也规定主代理如何以证据驱动方式分轮使用该执行层：主模型（T1 思考档）作为 owner 负责确定当前证据问题、决策、综合、路由与验收，把有界事实搜集和机械小任务 fan-out 给 T3 快速档；事实足够后才明确派发 T2 或 T1。worker 以进程内 `AgentSession` 运行，使用 Logical Isolation；任务从主模型路由派生，不维护独立的 task plan，不预先穷举。
_Avoid_: 召唤池、群策群力、自发生长、对抗式合议、Orchestrator 编排者、流水线、预先 Task Plan、generic workflow platform

**dteam vs dgoal（项目分工边界）**：
两个项目独立并列，本质模式不同：
- **dgoal = 单模型建检循环**：主代理单兵带 task plan 全程推进（全程一个强模型），完成时由独立审核员（fresh 子进程）验证 DoD 达标。
- **dteam = 多模型分级路由**：主模型（T1）路由 + fan-out 小模型（T3）并行 + fresh 验收 + 回退。
主 LLM 自己判断：长串行目标、冻结验收合同或独立终审由 dgoal 管；非极小任务仍需仓库证据、外部来源提取、机械实现或 fresh 验证时用 dteam，阶段内可以嵌套。
_Avoid_: 把 dteam 和 dgoal 视为同一项目的两种模式、在两者间设置自动切换

**Main LLM / Main Agent（主模型 / 主代理）**：
直接和用户对话、持续理解用户目标与上下文的主要执行者，也是 dteam 的 owner。它负责任务理解、拆解、证据筛选、冲突裁决、路由、升级、收口和最终交付；不应亲自承担可由低档 worker 完成的仓库事实搜索、机械实现或机械检查。主模型可用 T1 思考档，但它**不是**被派发的 T1 worker；后者是主模型在复杂攻坚或 fresh 验证时额外创建的独立 session。
_Avoid_: leader agent（如果暗示它要长期管理所有 worker）、把主 LLM 与 T1 worker 混同

**Model Tier（模型档位）**：
dteam 内部的"角色"= 模型能力档位，分三档（取代旧的五角色职能分工）：
- **T1 思考档（frontier）**：旗舰模型，高思考，默认只读。用途：思考/决策/综合/路由/验收/回退重做。
- **T2 标准档（standard）**：标准模型，中思考，默认只读。用途：常规实现。
- **T3 快速档（fast）**：快速/本地模型，低思考，默认只读。用途：机械小任务。所有档位写入都必须在 dispatch 的 `addTools` 中显式预授权并声明 `writeScope`。
标准锚定**供应商产品线层级**（每家供应商都已分好旗舰/标准/快速三线），价格为辅验证。档位本质是人为划档（模型能力连续，档位是离散近似），不是客观物理边界。dispatch 可覆盖默认配置（如 T3 临时给可写权限）。
_Avoid_: 五角色（explore/design/build/check/close 的职能分工）、绝对"强模型/小模型"二元

**Thinking Budget（思考强度）**：
worker 的 reasoning effort / thinking budget 配置。**默认跟随档位**（T1 高 / T2 中 / T3 低），不独立成维。理由：思考收益随档位降低而递减（小模型高思考不划算）；难任务由主模型汇总低档结果后逐级派发，不是让小模型多想。dispatch 参数可覆盖；前提是该档模型支持 thinking，不支持则静默忽略。
_Avoid_: 思考强度独立二维矩阵、小模型调高思考（难任务应逐级升级而非让小模型多想）

**T3 优先代码探测（T3-first Code Reconnaissance）**：
T3 → T2 → T1 递增成本纪律的起点：主模型在需从当前仓库取得事实的非极小代码任务开始时，先派发一轮有界、独立、只读且证据面互补的 T3 worker；汇总后只为新暴露的具体未知追加下一轮 fresh T3。T3 也可在最小显式授权内完成独立机械小改；T2 只承接已定位的常规实现，T1 只处理复杂判断、高风险收敛、复杂重构与验收。它不是 runtime 自动派发或任务编排。
_Avoid_: 每个问题强制 worker、固定视角清单、关键词自动调度、Orchestrator Loop、T1 默认亲自探索

**证据驱动多轮路由（Evidence-driven Multi-round Routing）**：
主代理先定义当前必须取得的证据，再派有界 worker；综合本轮带来源报告后，按真实缺口决定收口、补充取证、实现、fresh 重试、相邻升级或请求用户决策。外部信息由主代理选源，T3 只对已选来源做受限提取。轮次与下一步只存在于主代理判断中，不进入 Worker Manager 状态。
_Avoid_: 预生成完整任务树、固定轮数、worker 自选来源后直接裁决、Manager 自动导演

**结构化工作报告（Structured Worker Report / `WorkerReport`）**：
worker 在结束前通过内部 `dteam_report` 恰好提交一次的统一结果模型，必含 `outcome`、`summary`、`activities`、带 `claim` / `evidence` 的 `facts` 与 `verification`，可含 `uncertainties`。它是 worker 被 Manager 视为 completed 的必要条件，但 `state=completed` 只表示报告有效，不代表任务完整或验证通过。
_Avoid_: final free-text report、无来源结论、按 explore / implement / review 拆报告类型

**Worker Activity（工作动作）**：
`activities` 只报告本轮实际做过的动作：`inspected`（读取核对）、`modified`（修改文件）、`tested`（自动检查）、`executed`（实际运行目标路径）、`captured_visual`（捕获并检查视觉产物）。活动不是任务角色，也不自动证明工作正确。
_Avoid_: 把 tested 当 passed、把 activity 枚举当角色系统

**Verification Depth / Status（验证深度 / 结果）**：
`verification.depth` 记录 worker 实际达到的最深直接验证方式：`none / inspection / automated / runtime / visual`；`verification.status` 记录在该深度上的 `passed / failed / partial / not_run` 结论。它们必须由 `verification.evidence` 支撑，且不在派发前声明强制 expected depth。
_Avoid_: human verification depth、预填 expected verification、把 runtime state 当验证结果、把深度当全局质量分数

**Remaining Verification / Uncertainty（剩余验证 / 不确定性）**：
`verification.remaining` 是已经知道但本轮没有完成的检查；`uncertainties` 是尚未查明且可能改变结论的事实。人工复测发生在 worker 报告之后，不能写成 worker 的 verification depth，也不回写终态报告。
_Avoid_: 用 remaining 隐藏任务未完成、把未知事实写成验证待办、用 human 伪装 worker 证据

**有界上下文交接（Bounded Handoff）**：
主模型在 `dteam_dispatch` 中显式传给下一轮 worker 的有限事实、约束和不确定性集合。Manager 为事实附加实际 worker 来源；它不包含完整主会话、完整 transcript 或 worker P2P 消息。
_Avoid_: shared conversation、full transcript forwarding、peer-to-peer handoff

**递增成本验证（Incremental-cost Verification）**：
变更完成后由 fresh worker 按最低足够档位验证的纪律：T3 核对机械条件、测试、diff 和明确要求；T2 审查行为与跨模块实现；仅高风险、证据冲突或低档无法确定时使用 T1。验证 worker 不得是实现该变更的同一 session。
_Avoid_: 自验、默认 T1 审核、固定 Completion Gate

**写入范围（Write Scope）**：
可写 worker 在派发时声明的项目相对文件或目录集合。它用于中断后的完整性检查，不表达依赖、文件锁、所有权或调度顺序。
_Avoid_: file lock、ownership graph、implicit scope inference

**可写工作者中断完整性守卫（Write-interruption Integrity Guard）**：
可写 worker 未被确认完成时，主模型必须派 fresh T3 检查其 writeScope 的 diff、编译或定向测试；准备新的可写派发时，发现未解释 dirty diff 也必须先检查。它不自动回滚、不持久化专用中断标记，也不自动派发检查 worker。
_Avoid_: auto rollback、persistent recovery queue、automatic orchestrator

**`dteam_dispatch`（派发工具）**：
受理 1–32 个互不依赖后台 worker 的模型工具。它只表达本轮 `workers` 输入；不表达依赖图、batch、dgoal task 对应关系或后续自动派发。0.7 也曾有同名同步工具，但其语义已废弃。

**`dteam_respond`（普通回应工具）**：
主模型对 waiting worker 的非超时请求作出的定向回应工具，可提供上下文、授予本次派发预授权的工具、追加一次工具额度、作出业务决策、拒绝或取消。`cancel`（取消）作为 `deny` 的并列选项，用于主代理接管任务时直接停掉该 worker；它只在 worker waiting 时可用，不是通用 cancel 工具（ADR 0023）。它不执行 timeout recovery。

**`dteam_recover`（恢复工具）**：
主模型对 timeout recovery 请求作出的定向决策工具，可选择 fresh retry、相邻 escalate、有限 extend 或 stop。Worker Manager 仍强制 fresh session、相邻升级、次数与预算上限。

**`dteam_wait`（显式依赖等待工具）**：
主模型在后续工作依赖指定 worker 时调用的一次性 event wait（事件等待）。它等待多个指定 worker 的下一可消费事件：任一 worker 完成、失败、终态或进入 waiting 时立即返回本次实际消费的 `events`、已就绪结果与剩余 `pendingWorkerIds`；timeout 只结束等待，不取消 worker。parent event 先留在 Manager 待消费队列；即使 wait 晚于事件发生，只要事件尚未回放，wait 仍会消费并删除它。只有主代理 idle / settled 后仍未消费的事件才进入 follow-up，因此同一事件只走一个 wait 或一次异步回放；终态 Snapshot 不冒充新事件。Signal Log 与 `/dteam` 仍保留记录。
_Avoid_: polling、dteam_status、wait-all 默认阻塞、dependency graph、automatic join、wait 后重复 follow-up

**工具结果人类可读投影（Human-readable Tool Result Projection）**：
dteam 所有用户可见工具结果的 UI 规则：默认只显示紧凑摘要；按 `Ctrl+O` 展开完整但仍为人类可读的文字树、事实、列表或诊断。完整结构化结果仅供模型上下文、内部 `details` 与测试使用，不能原样显示给用户。
_Avoid_: raw JSON UI、直接渲染 details、把展开等同于暴露 schema

**Fresh 验收（Fresh Review）**：
对抗主模型倾向的验收机制。主模型既是任务分配者又是验收者，会倾向性放水（给自己分配的活说"行"）+ 上下文锚定。dispatch 创建的 worker 都是 fresh session（不继承主会话），所以验收 worker 天然看不到主会话/方案出处。这是 dgoal「不让学生判卷」原则从"完成判定"迁移到"路由+验收"。**复活自 ADR 0007 的 fresh check 零件**（不是回到对抗式合议整体）。验收按最低足够档位 fresh 派发：机械条件可用 T3，跨模块行为可用 T2，复杂判断、高风险收敛或低档证据冲突才用 T1。
_Avoid_: 主模型自验自产、close 带主会话上下文打分

**回退（Fallback）**：
同档模型候选的可用性兜底机制：当前候选报错、限流或工具异常时，Manager 可自动尝试该 tier 的下一个 `provider/model[:thinking]` 候选。跨档不是自动回退：主代理汇总已回传事实后，按 `T3 → T2 → T1` 逐级派发下一轮；不得跳档。质量不过可由主代理显式派发 fresh 验收后决定重做。
_Avoid_: 自动 T3/T2→T1 跳档、无限重试、小模型反复调高思考硬扛

**超时恢复（Timeout Recovery）**：
当前 Pi 会话内 worker 达到一次 attempt 预算后的有类型恢复请求。Manager 记录当前 attempt 预算、recovery 累计上限、经过时间、最后活动、当前工具和裁剪输出摘要，等待主代理通过 `dteam_recover` 决定同档 fresh retry、相邻升级、有限 extend 或 stop。它不恢复旧 `AgentSession`，不跨 reload/进程持久化。
_Avoid_: 完整 session resume、自动盲重试、把 timeout 直接混同为无输出失败

**Adaptive Concurrency（自适应并发）**：
主模型可以同时 dispatch 多个 worker，而不是严格串行。并发度根据实际情况（如供应商 429 限流）自适应升降。是 ant-colony `ConcurrencyConfig`（min/max/optimal/history/lastRateLimitAt）模式的延续。
_Avoid_: strict sequential、fixed single worker

**Multi-Provider Routing（多供应商路由）**：
每个档位可以配置不同主模型和 fallback 链（多供应商），避免单供应商约 3 个并发就撞墙。是 ant-colony `ModelOverrides` + `FallbackModels` + `resolveModelWithFallback` 模式的延续。0008 后是 dteam 的核心基础设施，加 `tier` + `thinking` 字段激活。
_Avoid_: single provider、hardcoded model、no fallback

**Logical Isolation（逻辑隔离）**：
dteam 放弃默认 OS 子进程隔离后，对进程内 worker 的 fresh（新鲜上下文）约束。每个 worker 使用 `SessionManager.inMemory()`、最小 `ResourceLoader`、工具白名单和独立 system prompt；只接收 dispatch 明确传入的 task，不继承主对话完整上下文。这是 fresh 验收能成立的物理基础。
_Avoid_: shared main conversation context、implicit branch inheritance、full session reuse

**Opinionated Subagent Replacement（有立场的子代理替代层）**：
dteam 对通用 subagent（子代理）系统的替代定位：吸收有价值的能力形态（分级路由、fresh 验收、多供应商），但用 507 的工作流约束过滤，不追求功能复刻。
_Avoid_: feature parity clone、generic subagent platform

**Configuration Surface（外部配置面）**：
用户或项目可以直接声明、覆盖或扩展 dteam 行为的入口，例如档位模型配置、思考强度、工具白名单。dteam 优先把能力沉淀为内部结构，只有真实痛点足够强时才扩大外部配置面。
_Avoid_: internal execution plan、runtime state

## 2. 运行模型

**Extension Runtime（扩展运行时）**：
Pi extension（扩展）承载工具、命令、UI、消息和会话条目的运行环境。dteam 的 dispatch 执行依附在这个运行环境上。

**In-process Execution（进程内执行）**：
dteam worker 的默认执行基底：用 Pi SDK 的 `createAgentSession` 创建进程内 `AgentSession`，dispatch 后执行返回结果。它牺牲默认 OS 子进程隔离，换取低启动开销和 fresh 保证；隔离由 Logical Isolation 承担。
_Avoid_: process isolation by default、child pi process by default、spawn-first architecture

**No Default Resume（默认不恢复）**：
dteam 不做默认持久化 / resume（恢复）。0.8 即使引入会话级后台 worker，也只在当前 Pi 进程内保存运行态；shutdown / reload 后中止活跃 worker，不跨进程恢复。见 [ADR 0004](./决策档案/0004-不做resume和默认持久化.md)。
_Avoid_: persistent Kanban、always-on job queue

### 2.1 0.8 会话级后台运行时术语（目标）

**会话级后台运行时（Session-scoped Background Runtime）**：
附着于当前 Pi 主会话的内存运行态。`dteam` 的 dispatch 受理后立即返回，Worker Manager 在后台执行 fresh worker；会话关闭或重载即中止活跃 worker，不恢复。
_Avoid_: daemon、persistent job queue、Extension Runtime 长驻 run

**Worker Manager（工作者管理器）**：
当前 Pi 会话内唯一拥有 worker 生命周期的组件：启动、取消、fallback、结果汇聚、Signal Log、Snapshot 与 Request State。它不判断下一步该派谁、不维护计划，主代理仍是 owner。
_Avoid_: Orchestrator、scheduler、autonomous coordinator

**Signal Log / Worker Snapshot / Request State（信号日志 / 工作者快照 / 请求状态）**：
0.8 的三份内存运行态：Signal Log 只追加已验证事实；Snapshot 投影每个 worker 的最新展示态；Request State 保存阻塞请求及其 deferred responder。它们不做 TTL、分数或驱动下一轮派发。
_Avoid_: Signal Store、TTL decay、blackboard

**Dteam Usage Ledger（dteam 用量账本）**：
位于 `~/.pi/agent/dteam-usage.jsonl` 的独立、append-only 脱敏数字账本。每条 worker assistant message 记录父会话、项目、worker、请求/实际档位、candidate、模型、时间、usage / cost 与去重键；不记录 task、prompt、输出、工具参数或 WorkerReport。它只供 `pi-session-insights` 等观察层聚合，不参与路由、恢复或完成判定。
_Avoid_: persistent worker session、复用 dgoal `audit-usage.jsonl`、保存 worker transcript、用量写入失败终止业务 worker

**星型 signal 协议（Star-topology Signal Protocol）**：
worker 只向 Worker Manager 发 B 类 signal，Manager 向主代理回传，主代理以 C 类 signal 经 Manager 回给同一 worker；worker 不 P2P。A 类 signal 仅由系统记录状态迁移。
_Avoid_: mailbox、peer forwarding、swarm bus

**接管视图（Takeover View）**：
`/dteam` Modal 中某个运行中 worker 的详情页。可 steering（插队指令），取消需二次确认；完成、失败、超时、取消或 session shutdown 后的 worker 只读封存。
_Avoid_: always-on floating panel

## 2.5 已推翻（保留追溯）

以下概念已被推翻，仅保留以追溯历史决策，**不再有效**：

**被 ADR 0008 推翻（0006/0007 对抗式合议 + 0005 执行基底部分）**：
- **对抗式合议（Adversarial Deliberation）**：0006 的定位，已被 0008 推翻（原型验证繁琐无用）。
- **合议单元 / 对抗回合 / 积分制（Score-based Convergence）/ N design 差异化 / fresh 裁判 / summary 不转原文**：0007 的机制，整体推翻。**但 fresh check 零件被 0008 复活**到 dispatch 的验收用法。
- **Orchestrator（编排者）/ Orchestrator Loop（编排循环）**：0005 的主体与主循环，已被 0008 推翻——主模型自己路由，不要独立编排循环。
- **Signal Store（信号存储）/ 旧 Signal（progress/found/blocked/help）/ worker_sendSignal**：0005 的 TTL 信号系统已被 0008 砍掉。ADR 0009 的 `Signal Log` 与 A/B/C 有类型 signal 是不做衰减、不决定下一轮派发的会话级协作协议，不能混称为旧 Signal Store。
- **LLM-Driven Orchestration（每轮 LLM 现场决策召唤谁）**：0005 第 17 条，已被推翻——主模型在对话里直接路由，不是独立 loop 每轮拍板。
- **Completion Gate（强制 check 收口）/ 固定五角色对抗视角重对齐**：0006 的收口闸门与角色重对齐，已被 0008 推翻——收口改为 fresh 验收（dispatch 用法），五角色改为 T1/T2/T3。
- **Peer Forwarding / Help Self-heal / Escalation to Human**：0005 的协作回路，随 Signal Store 一起退场。

**被 ADR 0005 推翻（0.4.x / 0.5.0 旧形态）**：
- **后台运行 / `Run` / `runId` / `RunsStore` / Background Collaboration State Machine**：被 ADR 0005 推翻 ADR 0003。
- **`Task Plan` / `DPlan Contract` / `.dplan.*`**、**`ExecutionPlan.mode`（solo/chain/team）**、**`Strategy`（direct/build_check/adaptive）**、**`SchedulingPlan` / `FileGraph` / Preflight Scheduling**、**planner 穷举**、**进程级 OS 子进程隔离作为默认**：均被 ADR 0005 推翻。

## 3. 模型档位与工具权限

**T1 / T2 / T3 档位默认配置**：

| 档位 | 模型 | 思考 | 默认工具 | 用途 |
|---|---|---|---|---|
| T1 思考档 | 旗舰 | 高 | 全工具（读写改 + 审核） | 思考 / 决策 / 验收 / 回退重做 |
| T2 标准档 | 标准 | 中 | 可写（读写改） | 常规实现 |
| T3 快速档 | 快速 / 本地 | 低 | 默认只读；显式限定写 | 机械小任务 |

dispatch 可覆盖（如 T3 临时给可写权限做独立模块小改）。

**BASIC_TOOLS（基础工具集）**：
T1/T2 的基础工具为 `read`、`bash`、`grep`、`find`、`ls`。T3 默认只保留只读的 `read`、`grep`、`find`、`ls`；`bash`、`edit`、`write` 都必须由调用方在 `tools` 显式授予。
_Avoid_: all Pi tools

**availableTools（可用工具清单）**：
主 LLM 调用 dteam 时显式传入的当前可见工具名列表。dispatch 用它校验 worker 工具；不传则回落到档位默认白名单。
_Avoid_: dteam auto-discovery of tool universe

**旧五角色（已推翻，仅追溯）**：
`explore / design / build / check / close` 是 0.5.0/0.6.0 的职能分工角色，已被 0008 的 T1/T2/T3 能力分级取代。旧的 `build` 唯一能 edit 边界，在 0008 下改为"按档位默认工具白名单 + dispatch 可覆盖"。

## 4. 执行回路（0008 后简化）

> 0008 后没有独立的信号系统（Signal Store 已砍）。执行回路极简：

```
主模型（T1，owner）
  ├─ 思考 / 路由：判断任务难度 + 独立性
  ├─ 小任务 → dteam_dispatch({ workers: [...] }) [可一次受理多个]
  │    ├─ 成功 → follow-up 汇聚结果
  │    └─ 同档候选可用性回退；异常/质量问题回传主模型决定下一轮
  └─ 大任务/思考 → 自己做（高思考）
```

**WorkerRun（工作者运行记录）**：
单个 dispatch worker 的执行快照（档位、task、结果、用时、状态）。用于结果回收和追溯，不再以信号回流为中心。

## 5. UI、报告与可观察性

**当前入口观察**：
`dteam` 立即返回逐项 `DispatchAccepted`；Worker Manager 通过主会话 follow-up 汇聚结果、失败、取消和阻塞请求，`/dteam` 提供运行态与历史查看。

**可观察性边界**：
0.6 的 Reporter、UIStore、Panel 与 Widget 已随旧 runtime 删除。0.8 的会话级后台运行态由 `/dteam` 按需展示 Worker Snapshot（含实时文本、思考、工具活动和 timeout 诊断）；主对话经 `dteam_respond` 回应普通请求、经 `dteam_recover` 处理 timeout recovery。

**Evidence（证据）**：
dteam 用来支撑"完成/回退判断"的可回溯材料，包括 dispatch 轨迹、worker 结果、fresh 验收结论。

## 6. API 与入口

**dteam 四工具入口（Four-tool Surface）**：
模型侧当前只暴露 `dteam_dispatch`、`dteam_respond`、`dteam_recover` 与 `dteam_wait`，分别负责派发、普通回应、超时恢复和显式依赖等待；`/dteam` 是独立的用户管理命令，不是模型工具。字段、错误边界和示例以 [`10-架构与运行/12-API参考.md`](./10-架构与运行/12-API参考.md) 为唯一 API 契约，术语表不重复展开 schema。
_Avoid_: 单工具 `dteam({ type })`、dteam_status、把 `/dteam` 当模型工具

## 7. 内部模块

**dispatch 实现（派发实现层）**：
`src/runtime/worker-manager.ts` + `src/session.ts` 负责创建进程内 worker `AgentSession`、按档位解析模型（Multi-Provider Routing + tier/thinking）、注入工具和资源、实现 Logical Isolation、执行并返回结果。
_Avoid_: Orchestrator Loop、Plan→Execute→Report 流水线

**session（会话层）**：
`src/session.ts` 和 `src/session/*`，负责创建进程内 worker session、加载档位配置、解析模型（含 Multi-Provider Routing + tier/thinking）、注入工具和资源、实现 Logical Isolation。

## 8. 外部参考与明确不做

**ant-colony（蚁群系统）参考**：
dteam 的多态分工（T1/T2/T3 = 不同 castes）、Multi-Provider Routing、Adaptive Concurrency 均源自 ant-colony。借多态分工 + 派发形态；不借信息素涌现/自组织（= 0005 自发生长老路，已失败）。
_Avoid_: queen/pheromone 虫化术语（dteam 已去虫化）

**zcode-swarm 蜂群插件参考**：
coordinator 模式（主模型派发 worker）印证 dteam 形态；blockedBy 依赖图与 dgoal 同构；红队独立审核与 fresh 验收同源。见 `20-能力参考/29`。借派发 + fresh 审核；不借竞争认领/邮箱 P2P/液态拓扑。

**明确不做**：
- 角色市场 / 自定义角色（T1/T2/T3 三档写死）
- 持久 Kanban / Harness 平台 / 固定流水线
- resume / 跨进程持久化（ADR 0004）
- Orchestrator Loop / Signal Store / 对抗回合 / 积分制（0008 推翻）
- Worktree / File Lock / Auto Merge（只有并发写冲突成真实痛点再评估）

## 9. 已解决

- **完成收口**：由主模型决定；fresh 验收是关键任务可选调用的独立证据，不再需要独立 Completion Gate。
- **路由判定**：主模型（T1）做，它有对话上下文知道任务难度；倾向性由 fresh 验收兜底。
- **回退与升级触发**：同档模型候选因可用性问题自动尝试；硬失败、timeout 或质量问题回传主模型，由主模型按 T3→T2→T1 决定下一轮。
