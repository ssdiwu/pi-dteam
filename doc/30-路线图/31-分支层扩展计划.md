# 分支层扩展计划

> 记录于 2026-06-04。当根→叶子两层架构遇到规模瓶颈时，按此文档加入分支层。

## 当前架构：两层

```
根（orchestrator）
  ├─ 信号：收集所有叶子的 progress/found/blocked/help
  ├─ 决策：全局 plan、help 自愈、blocked 标记、升级到人类
  └─ 直接派叶子：explore / design / build / check / close
```

## 目标架构：三层（未来）

```
根（coordinator）
  ├─ 全局 plan
  ├─ 监听分支升级的 help/blocked
  ├─ 升级到人类
  │
  ├─ 直接派叶子（简单任务，不经过分支）
  │
  └─ 派 分支（复杂子任务组）
       ├─ 信号收集：管辖范围内叶子的所有信号
       ├─ 局部决策：help → 派 explore 补充 → 注入回叶子
       ├─ 上下文桥接：提取叶子 A 的发现 → 注入叶子 B 的 prompt
       └─ 向根升级：搞不定的 help/blocked
```

## 分支的角色定义（待实现）

- **agent 文件**：`agents/coordinator.md`（不是 design.md）
- **职责**：信号收集、评估、策略派发、上下文桥接
- **工具**：`decide` + `worker_sendSignal`
- **本质**：一个嵌套的根——管理自己的 task 池、信号总线、runs 存储
- **与 design 的关系**：design 是叶子角色，分支判断"需要架构设计"时派 design 叶子

## 触发条件（什么时候需要分支）

以下任一条件满足时，考虑引入分支层：

1. **根的上下文窗口溢出**：叶子信号太多，根处理不过来
2. **叶子间需要中间协调**：A 的发现需要实时注入 B，但根顾不过来
3. **并发叶子 > 5**：根无法有效监控所有叶子的信号
4. **子任务组有强内聚性**：一组子任务之间高度关联，应该由一个中间层统一管理

## 实现路径

### 第一步：根→叶子双向信号（当前）

- `signalBus.on("progress")` listener 实时更新 UI
- `handleHelpSignals()` 根收到 help → 派 explore 补充 → 注入下一步
- blocked 信号自动标记 step failed
- RunResult 包含 signals + workers + taskSummary

### 第二步：叶子 session 暂停/恢复

- leaf.execute() 从单次 `session.prompt()` 改成循环
- 叶子发 help 后暂停，等上级注入补充信息再继续
- 需要 session 级别的暂停/恢复机制

### 第三步：人类在环

- dteam 工具从 `action: "run"` 单步变成 `action: "run" | "resume"`
- 根判断无法自动解决 → 中途返回中间结果给主对话 LLM → 用户回复 → resume

### 第四步：分支层

- 分支 = 嵌套的 orchestrator，有自己的 taskPool + signalBus + runsStore
- 根的 plan 阶段可以决定某组子任务交给分支
- 代码层面：分支复用 orchestrator.ts 的逻辑，只是作用域缩小

## 外部参考

| 框架 | 分支等价 | 通信模式 |
|------|---------|---------|
| 蚁群 | 蚁后（单层，无分支） | 信息素（stigmergy） |
| CrewAI | Manager Agent | delegate_task 工具 |
| Claude Code | Lead Agent | Task 工具 + context bridge |
| OpenCode | Lead + peer messaging | inbox JSONL + auto-wake |
| arxiv HMAS | Mid-level supervisor | top-down + bottom-up + peer |

**蚁群没有分支层**——所有蚂蚁由蚁后直接调度。Claude Code 也没有——Lead 直接派 Subagent。分支层是 dteam 在规模增长后的扩展选择，不是必选项。
