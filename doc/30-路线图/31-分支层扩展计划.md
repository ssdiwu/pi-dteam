# 分支层扩展计划

> 远期参考。当前 0.5 不做分支层；只有当根直接管理叶子 worker 出现规模瓶颈时，再评估本方案。

## 1. 当前架构：根 → 叶子

```
根（orchestrator）
  ├─ 制定 ExecutionPlan
  ├─ 直接派叶子 worker：explore / design / build / check / close
  ├─ 收集 progress / found / blocked / help 信号
  ├─ help 自愈或升级到人类
  └─ 汇总 RunResult + dteam-report
```

当前判断：这对 507 的个人编程任务足够。0.5 先打磨可观测性，不加中间层。

## 2. 目标架构：根 → 分支 → 叶子（远期）

```
根（coordinator）
  ├─ 全局目标、全局 run 状态、用户交互
  │
  ├─ 简单任务：直接派叶子
  │
  └─ 复杂任务组：派分支 coordinator
       ├─ 管辖一组叶子 worker
       ├─ 局部收集信号
       ├─ 局部 help 自愈
       ├─ 局部上下文桥接
       └─ 无法解决时向根升级
```

分支层的本质不是“更多 agents”，而是减少根的上下文压力和协调负担。

## 3. 触发条件

以下任一条件连续出现，再考虑分支层：

1. 单次 run 的 worker 数量经常 > 5
2. 根收到的信号太多，导致 UI / report 难以理解
3. 叶子之间需要高频上下文桥接，根成为瓶颈
4. 子任务天然分组，例如“前端组 / 后端组 / 测试组”各自需要局部协调
5. 真实任务证明 root → leaf 两层不够，而不是为了架构完整性

## 4. 暂定设计

| 项 | 初步想法 |
|---|---|
| 角色名 | `coordinator`（不是 `design`） |
| 职责 | 局部调度、局部信号收集、上下文桥接、向根升级 |
| 工具 | `decide` / `worker_sendSignal` / 只读状态查询 |
| 状态 | 有自己的 task pool / signal scope（作用域） |
| 边界 | 不能直接覆盖根的全局决策 |

## 5. 与 0.5 的关系

0.5 不实现分支层，但 0.5 的可观测性要避免把未来路堵死：

- UI worker state 保留 `parentId`
- report 尽量保留 worker tree 结构
- 信号仍按 `runId` + `workerId` 记录
- 不把所有并行 worker 扁平成纯列表

## 6. 外部参考

| 系统 | 可参考点 | 不照搬点 |
|---|---|---|
| SwarmFlow | 阶段 / 节点可观察 | workflow.py |
| MiMo Code | 旁路 writer / verifier | 固定大流水线 |
| pi-subagents | nested run 在状态树里可见 | 进程级递归 fanout |
| CrewAI | manager agent 思路 | 重型 crew 配置 |

## 7. 当前结论

分支层是远期扩展，不是 0.5 起点。

0.5 只做：**让当前根 → 叶子模型更可见、更好懂、更不乱。**
