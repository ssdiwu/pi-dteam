# 已取代候选：主代理后台状态查看（方案一）

> **状态：❌ 已被 [ADR 0024](../决策档案/0024-主代理运行中主动协调成为默认能力.md) 吸收并取代，未实施。** 只读 `dteam_inspect` 只能让主代理看见状态，不能形成“可行动发现 → 主 LLM → running worker”的主动协调闭环；首版继续不提供 status / inspect 轮询。以下保留原候选与权衡，仅供历史追溯。

## 背景

[ADR 0023](../决策档案/0023-cancel作为dteam-respond的受限取消响应.md) 已落地 `dteam_respond` 的 `cancel` 响应，让主代理在 worker 请求交互（waiting）时能直接停掉它，消除了"deny 后 worker 晾在后台空跑、完成时回放打断主代理"的最痛场景。

但仍剩一个缺口：**主代理对一个正在 running（未请求交互）的后台 worker，没有感知手段**。当前主代理要知道某个 worker 的状态，只有两条路——主动 `dteam_wait`（但那要求主代理依赖它的结果、会阻塞当前决策），或等 worker 终态后在 idle / settled（轮次安定）时被异步回放。当主代理既不依赖、又想"抽查某个 worker 现在跑到哪了 / 有没有产出"时，没有干净通道。

主代理要路由、要收口，却看不见后台 worker 在干嘛，是个掌控感缺口——没有掌握就没法判断，这对主代理是有害的。

## 候选设计

新增一个**只读查看**能力（暂称 `dteam_inspect`），让主代理按需查看指定 worker 的当前状态与已有产物：

- **查看内容**：worker 当前 state（queued / running / waiting / 终态）、最近活动、已提交的 `latestFinding` / `liveText` 摘要、若已提交的 `WorkerReport`。
- **定位**：**低频的决策性抽查**，不是"等结果的方式"——等结果仍用 `dteam_wait`（显式依赖等待）。
- **禁止轮询 + 限频**：服务端硬约束，每个 worker 至少间隔 **1 分钟**才能被再次 inspect；工具描述明确写"不要高频查看"。被限频时返回上次快照缓存 + 距下次可查的剩余秒数，而不是让主代理空转重试。

## 待论证（落地前必须先回答）

这个候选**直接撞上 ADR 0013 / 0018 反复刻碑否决的 `dteam_status`（状态查询）/ 轮询**（四处：术语表 `_Avoid_`、`12-API参考.md`、两个 ADR）。要落地必须先推翻或修订它们，论证以下几点：

1. **"触发不会很多"是否成立**。当初否决的核心顾虑是：模型一旦有查看工具，就会滑向高频轮询（`dispatch → status → status → ...` 的忙等）。1 分钟限频能否真正压住？需要在真实任务里观察主代理调用 inspect 的频率分布，而不是凭假设。
2. **限频能否消除忙等**。每分钟查一次仍是低频忙等，仍烧 token。inspect 必须严格定位成"决策性抽查"（接管前看一眼、判断要不要 cancel），而不是"我在等它"——后者用 `dteam_wait`。这个分工要写进工具描述和主代理协议，且要验证模型确实遵守。
3. **与已落地的 cancel 联动后，剩余需求是否仍足够**。ADR 0023 的 cancel 让主代理接管时能停掉 worker，"晾在后台不管"的 worker 会变少。方案一剩下的真实场景（"没接管、只想抽查一个 running worker"）频率有多高，值得先观察 cancel 上线后的实际使用，再定 inspect 的范围，避免过度设计。

## 与既有决策的关系

- **不违背 ADR 0023**：cancel 是"停掉"，inspect 是"看一眼"，正交。
- **需修订 ADR 0013 / 0018**：当前它们把 `dteam_status` / 状态查询列为 `_Avoid_`（禁用）。方案一若推进，需新写 ADR 论证"受限、限频、只读的 inspect"与"通用 status / 轮询"的区别，并修订术语表与 `12-API参考.md` 的 `_Avoid_` 表述。
- **限频值**：初步定 1 分钟（2026-07-21 对齐确认），待真实观察后调整。

## 不在本候选范围

- **通用 cancel（停 running worker）**：仍由 `/dteam` 独占；主代理要停一个 running worker，得等它请求交互再用 `cancel`（ADR 0023），或走 timeout recovery（超时恢复）的 `stop`。
- **改变事件投递机制**：inspect 只是补一个主动查看通道，不改 `dteam_wait` 优先、idle / settled 后回放的现有事件机制（见术语表 `dteam_wait` 条目）。
