## 2. 有意收敛的设计

### 2.1 planner 不用复杂 tool calling

原始设想：用 tool calling（工具调用）让 LLM 输出结构化 plan。

当前实现：

1. 规则优先：`quickRuleBasedPlan(goal)` 零成本命中常见场景
2. LLM 兜底：复杂情况让模型输出 JSON（结构化文本）
3. 失败回落：`solo + build + direct`

原因：MiniMax-M3 在复杂 schema（模式）下 tool calling 不够稳定；JSON 模式更可控。

### 2.2 不接入递归分解

原始设想：build step 内部再判断 execute / decompose。

当前实现：orchestrator 直接执行 planner 给出的 step，不在 build 中再递归拆任务。

原因：

- 当前个人编程场景更需要轻量、可预测
- 递归会引入 depth guard（深度保护）、cycle guard（环保护）、更多状态管理
- 超大任务可以由主 LLM 拆成多次 dteam 调用，而不是一次 dteam 无限递归

### 2.3 不做固定工业流水线

外部系统常见 `plan → execute → review → TDD → verify → merge`。dteam 不把它做成固定流程。

原因：

- 固定流程会把轻量多 worker 引擎变成重型工作流平台
- review / verify 如果未来需要，应是可选 worker 或策略，不是每次必经阶段
- 507 当前真实工作流更需要“复杂任务派 worker 协作”，不是“每个任务过一条大流水线”

### 2.4 角色写死，不做角色市场

`pi-subagents` 的 frontmatter 角色体系很完整，但 dteam 当前保留写死 5 角色。

原因：

- 保证 `build` 唯一可写边界
- 降低 planner 输出空间
- 让文档、测试、UI 都保持可验证

## 3. UI 实施现状

已落地：

- `/dteam` 面板 toggle（切换）
- 折叠态 widget 自动显示进行中 run
- worker tab（标签页）
- 信号分组展示
- 完成后 `dteam-report` 注入主对话

未落地但 0.5 优先：

- 完成项保留到下一次 agent response（回复）开始后再消失
- 更清晰的 4 状态展示
- plan mode（`solo` / `chain` / `team`）在面板标题中更稳定显示
- 聊天区安全 live summary（实时摘要）需要再评估，不能复活 v0.4.1 已修掉的 `onUpdate` 越界问题

## 4. 当前已知限制

| 限制 | 当前处理 | 是否 0.5 |
|---|---|:---:|
| planner 英文规则弱 | LLM 兜底 | 可做小修 |
| `files` 不参与调度 | 仅作为 plan 元数据 | 暂后 |
| 无持久化 / resume | 进程退出后重跑 | 远期 |
| check 判断靠正则 | 保持轻量 | 暂不做 |
| 角色不可配置 | 有意设计 | 暂不做 |
| 完成 UI 清理粗糙 | run 完成后 reset | **0.5 优先** |

## 5. 当前设计边界

dteam 的主线不是“更像某个多 agent 框架”，而是：

> 在 Pi 里提供一个后台、轻量、可观察的多 worker 协作状态；主 LLM 仍是用户的主要交互入口，dteam 只在复杂任务时被调用。
