# dteam 系统架构

> 当前定义：dteam 是 **Pi 里的轻量多 subagent（子代理）协作引擎**。它不是固定流水线，也不是独立 TUI（终端界面）产品；它是主 LLM 在遇到复杂编程任务时调用的一次后台协作状态。

## 0. 产品定位

### 0.1 什么时候用 dteam

| 任务类型 | 推荐做法 |
|---|---|
| 简单改动、单文件修复、普通问答 | 主 LLM 直接干，不调 dteam |
| 需要探索 + 实现 + 验证的复杂编程任务 | 调 `dteam(action="run", goal="...")` |
| 多个方向可并行探索 / 并行实现 | dteam planner（规划器）可能选择 `team` |
| 需要用户补充决策 | worker 发 `help`，主对话再用 `dteam(action="continue")` 注入 |

### 0.2 dteam 负责什么

1. **拆分**：把复杂 goal（目标）拆成少量 step（步骤）
2. **调度**：按 `solo` / `chain` / `team` 组织 worker
3. **隔离**：用写死角色限制工具权限，`build` 唯一能 `edit`（编辑）现有文件
4. **观察**：把 worker 状态、信号、输出映射到 `/dteam` 面板和最终报告
5. **汇总**：后台完成后发送 `dteam-report` 到主对话

### 0.3 dteam 不负责什么

- 不替代主 LLM 的普通编码能力
- 不做固定 `review → TDD → verify → merge` 工业流水线
- 不做完整项目管理工具
- 不做默认持久化 / resume（恢复）
- 不默认 spawn（启动）独立 `pi` 子进程
- 不引入可配置角色市场；当前 5 个角色写死是有意简化

## 1. 后台运行模型

`dteam(action="run")` 明确是后台任务：

1. 立即返回 `{ "status": "running", "runId": "..." }`
2. 后台继续执行，不阻塞主对话
3. 实时进度通过 `/dteam` 面板、widget（小组件）、状态栏观察
4. 结束后通过 `dteam-report`（结果报告）消息进入主对话
5. 不再依赖已结束工具调用的 `onUpdate`（流式更新回调）

这是 v0.4.1 的核心收口：启动通道和运行态展示通道分离。

## 2. 运行结构

```
dteam(action="run", goal, availableTools?)
  │
  ├─ index.ts
  │   ├─ 创建 runId / SignalBus / RunsStore
  │   ├─ 启动后台 run，不 await
  │   └─ 立即返回 runId
  │
  ├─ src/orchestrator.ts
  │   ├─ plan(goal)      → ExecutionPlan
  │   ├─ execute(steps)  → StepResult[]
  │   └─ report          → RunResult
  │
  ├─ src/planner.ts
  │   ├─ 规则判断 quick path
  │   └─ LLM JSON 兜底
  │
  ├─ src/leaf.ts + src/session.ts
  │   └─ 创建 worker session 并执行具体 step
  │
  └─ src/reporter.ts + src/ui/*
      └─ 更新 /dteam 面板、widget、最终报告
```

## 3. 二维编排模型

二维编排不是“固定流水线”，而是两个轻量选择：

### 3.1 组织形式：step 怎么排列

| mode（模式） | 含义 | 适用场景 |
|---|---|---|
| `solo` | 一个 worker 做一个 step | 简短目标、单点验证 |
| `chain` | 串行 step，前一步输出注入下一步 | 探索 → 实现、实现 → 验证 |
| `team` | 多 step 分批并行，每批 ≤ 3 | 多方向探索、多个独立模块并行 |

### 3.2 执行策略：单个 step 怎么跑

| strategy（策略） | 含义 | 边界 |
|---|---|---|
| `direct` | 执行一次并返回 | 无循环 |
| `build_check` | build → check → 修 → 再 check | 最多 3 轮 |
| `adaptive` | 执行 → 评估 → 调整 → 再执行 | 最多 5 轮 |

`strategy` 是 per-step（每步独立）的字段，不是全局 workflow（工作流）。

## 4. 数据结构

```ts
interface ExecutionPlan {
  mode: "solo" | "chain" | "team"
  reason: string
  steps: PlanStep[]
}

interface PlanStep {
  role: "explore" | "design" | "build" | "check" | "close"
  task: string
  strategy: "direct" | "build_check" | "adaptive"
  files?: string[]
  tools?: string[]
}

interface RunResult {
  status: "done" | "failed"
  goal: string
  plan: ExecutionPlan
  steps: StepResult[]
  summary: string
  signals?: Signal[]
  workers?: WorkerRun[]
  taskSummary?: { total: number; done: number; failed: number }
}
```

## 5. 信号系统

worker 可以通过 `worker_sendSignal` 上报 4 类信号：

| signal（信号） | 含义 | 根的处理 |
|---|---|---|
| `progress` | 进展更新 | 更新 UI，转发给同 run 其它 worker |
| `found` | 新发现 | 更新 UI，转发，chain 下一步注入历史上下文 |
| `blocked` | 无法继续 | step 标记 failed |
| `help` | 需要补充信息 | 先尝试 explore 自愈，再升级到人类 `continue` |

信号让 dteam 不是“盲跑多个子任务”，而是可观察、可中途补充的后台协作。

## 6. 当前实现不变量

| 不变量 | 说明 |
|---|---|
| `build` 唯一能 `edit` | 其它角色不得修改已有代码文件 |
| `team` 并发 ≤ 3 | 避免 API 限流和并发冲突 |
| `build_check` ≤ 3 轮 | 防止死循环 |
| `adaptive` ≤ 5 轮 | 防止无限迭代 |
| chain 失败即停止 | 保留已完成结果，不继续错误传播 |
| 角色写死 | 先保留 5 个角色，不引入用户自定义角色系统 |
| in-process（进程内）执行 | 当前用 `createAgentSession`，不默认 spawn 子进程 |
| `availableTools` 由主 LLM 传入 | dteam 不猜运行时工具宇宙 |

## 7. 从外部系统学到的架构边界

| 来源 | 对 dteam 的启发 | 是否采用 |
|---|---|---|
| SwarmFlow | 编排和智能分离；确定流程才固化 | 采用原则，不照搬 workflow.py |
| MiMo Code | 长程任务需要 verifier / writer 这类旁路角色 | 远期参考，不做固定流水线 |
| pi-subagents | 自然语言可用、async widget、child safety、doctor | 选择性借鉴，不改角色体系 |
| rpiv-todo | live overlay（实时浮层）和完成项清理体验 | 0.5 优先借鉴 |

## 8. 已知限制

- `/dteam` 面板完成后会清空，缺少“完成项保留到下次 response 后消失”的体验
- 正常聊天区只看到启动 runId 和最终 `dteam-report`，没有安全的 live summary（实时摘要）
- planner 英文关键词规则较弱，复杂英文 goal 更依赖 LLM 兜底
- `files` 字段已有但未参与调度预检
- 无持久化 / resume；Pi 进程退出后 active run 丢失
- `check` / `adaptive` 通过正则判断结果，暂不改 tool calling（工具调用）
