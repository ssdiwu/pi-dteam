# dteam 系统架构

> 当前定义（[ADR 0008](../决策档案/0008-dteam重定位为模型分级路由执行层.md) + [ADR 0020](../决策档案/0020-主代理证据驱动多轮路由协议.md) + [ADR 0024](../决策档案/0024-主代理运行中主动协调成为默认能力.md)）：dteam 是 **模型分级路由执行层 + 主代理证据驱动多轮路由协议**。
>
> 与 [`pi-dgoal`](../../../pi-dgoal) 独立并列：dteam = 多模型分级路由，dgoal = 单模型建检循环。
>
> **实施状态**：本文描述当前实现：`session.ts` 提供 T1/T2/T3 fresh 基础，`runtime/worker-manager.ts` 提供后台生命周期、signal、带证据 finding、主动控制、报告、回退与聚合；`index.ts` 公开五工具，`/dteam` 提供按需管理。0.6 SignalStore/五角色/loop 已删除。

## 0. 产品定位

### 0.1 什么时候用 dteam

| 任务类型 | 推荐做法 |
|---|---|
| 已有上下文足够的普通问答或极小单步改动 | 主 LLM 直接处理 |
| 非极小任务仍需仓库事实、独立证据面或已选外部来源提取 | 调 `dteam_dispatch`，先用 T3 分轮取证 |
| 单兵持续推进、串行依赖、冻结验收合同或独立终审 | 用 dgoal 管目标；阶段内可用 dteam |
| 一批独立小任务可分级并行 | 调 `dteam_dispatch` fan-out |
| 用户明确指定 dteam / dgoal / 直接处理 | 服从用户 |

详细 routing rule（路由规则）见 `14-dteam触发协议.md`。

### 0.2 dteam 负责什么

1. **证据驱动多轮路由**：主代理先定义当前证据问题，按需派多证据面 T3；技术路径不明时，以带依据、风险和最小验证动作的候选收束选择；汇总合法报告后只为真实缺口追加下一轮。
2. **模型分级执行**：机械小改交 T3、已定位常规实现交 T2、复杂判断与高风险验收交 T1；跨档由主代理决定。
3. **后台 dispatch 执行**：`dteam_dispatch({ workers: [...] })` 创建 fresh 进程内 worker，立即返回接收凭据，结果经主会话或 `dteam_wait` 回传。
4. **统一工作报告**：worker 必须区分 outcome、activities、facts 与实际 verification；Manager completed 不代表任务或验证通过。
5. **思考跟随档位**：T1 高思考 / T2 中 / T3 低；主代理汇总低档结果后按 T3→T2→T1 逐级升级，不是让小模型多想或 Manager 自动跳档。
6. **fresh 验收与回退**：关键变更由 fresh worker 按最低足够档位验证；同档候选只处理可用性，质量或 timeout 由主代理决定补验、重试或相邻升级。

### 0.3 dteam 不负责什么

- 不替代主 LLM 的普通编码能力
- 不做固定流水线 / 工业流程 / 编排引擎
- 不做项目管理工具；可消费 issue、PRD、spec 或 dgoal plan 的当前切片，但不保存外部 ID 或依赖图
- 不做默认持久化 / resume（见 [ADR 0004](../决策档案/0004-不做resume和默认持久化.md)）
- 不维护独立的 task plan（主模型在对话里临时路由，不预先穷举）
- 不默认 spawn 独立 OS 子进程（用进程内 `AgentSession` + Logical Isolation）

## 1. 运行模型：主代理多轮路由 + Worker Manager 执行

dteam **没有独立的编排循环**（Orchestrator Loop 已被 0008 推翻）。轮次与下一步只存在于主代理判断中：

```text
用户目标 / 外部耐久地图的当前切片
  ↓
主代理：定义当前证据问题与用户决策边界
  ├─ 第一轮 T3：架构 / 调用链 / 测试 / 复用等互补证据面
  │    └─ Worker Manager：fresh session → signal → WorkerReport
  ├─ 主代理综合 facts、verification、remaining 与 uncertainties
  ├─ 仍有会改变决策的未知或技术路径 → 下一轮 fresh T3 取证 / 候选探测
  ├─ 事实足够 → T3 机械小改 / T2 常规实现 / T1 复杂收敛
  └─ fresh 验证 → 收口、补验、重试、相邻升级或询问用户
```

**关键点**：
- 主代理是 owner，负责问题定义、选源、候选筛选、证据筛选、冲突裁决和最终收口；Worker Manager 只执行已派发 worker。
- dispatch 创建的 worker 是一次性 fresh session；过程 signal 与快照不形成任务图或自动后继。
- 多个独立证据面可在一次 dispatch 中 fan-out；下一轮只针对汇总后暴露的具体缺口。
- 外部事实由主代理选源并先抓取或 clone 到可读位置，T3 只做有界提取；当前不开放任意联网 worker。

## 2. 模型档位（T1/T2/T3，取代五角色）

| 档位 | 模型 | 思考 | 默认工具 | 初始工作工具额度 | 用途 |
|---|---|---|---|---:|---|
| **T1 思考档** | 旗舰 | 高 | 默认只读；显式最小授权写 | 180 | 思考 / 决策 / 验收 / 回退重做 |
| **T2 标准档** | 标准 | 中 | 默认只读；显式最小授权写 | 120 | 常规实现 |
| **T3 快速档** | 快速 / 本地 | 低 | 默认只读；显式最小授权写 | 60 | 机械小任务 |

- **标准锚定供应商产品线层级**（旗舰/标准/快速三线），价格为辅。
- **思考跟随档位**：小模型高思考收益递减 + 难任务走回退换强模型（自带高思考）。
- 所有档位写入都必须通过 `addTools` 显式最小授权并声明项目相对 `writeScope`；T3 只用于独立机械小改。
- worker 可在耗尽前经 `dteam_signal` 申请一次工作工具额度；主代理可批准 +60～+120 次（10 的倍数）。再次耗尽时回传诊断，由主代理重新 dispatch fresh worker；Manager 不自动续派。`dteam_signal` 与最终 `dteam_report` 不计入额度。

## 3. fresh 验收与回退

### 3.1 fresh 验收（对抗主模型倾向）

主模型既是分配者又验收，会倾向放水（dgoal「不让学生判卷」原则迁移到路由+验收）。dispatch 创建的 worker 都是 fresh session（不继承主会话），所以：

```
验收 = dteam_dispatch({ workers: [{ title: "fresh review", task: "验收这个产出是否达标", tier: "T1" }] })
       ↑ fresh session，不看主会话/方案出处
```

验收不是独立工具，是 dispatch 的一个用法。**复活自 ADR 0007 的 fresh check 零件**（不是回到对抗式合议整体）。默认可选；关键任务才由主模型显式调 T1 fresh worker。

### 3.2 回退（可用性兜底）

| 触发 | 机制 |
|---|---|
| 同档候选不可用（provider/限流/工具异常） | 自动尝试该档下一个候选 |
| worker 报错、timeout 或质量不过 | 回传诊断；主代理决定自己接手、重试、fresh 验收或 T3→T2→T1 相邻升级 |

这是「乐观用小模型（省）+ 兜底强模型（稳）」策略。

## 4. 并发与多供应商

### 4.1 Adaptive Concurrency（自适应并发）

主模型可同时 dispatch 多个 worker，并发度根据实际情况自适应升降（如供应商 429 限流）。参考 ant-colony `ConcurrencyConfig`。

### 4.2 Multi-Provider Routing（多供应商路由）

每个档位可配置不同主模型 + fallback 链，避免单供应商约 3 个并发就撞墙。通过 `~/.pi/agent/pi-dteam.json` 显式声明 T1/T2/T3；三档主模型缺一不可，缺失时 fail-closed，不回落 `ctx.model`。**0008 后是核心基础设施**，加 `tier` + `thinking` 字段激活。参考 ant-colony `ModelOverrides` + `FallbackModels`。

## 5. 当前运行结构

```text
dteam_dispatch(...) / dteam_respond(...) / dteam_control(...) / dteam_recover(...) / dteam_wait(...)
  │
  ├─ index.ts / tools.ts（dteam 工具入口）
  │
  ├─ src/runtime/worker-manager.ts + src/session.ts（dispatch 实现）
  │   ├─ createAgentSession（进程内，fresh）
  │   ├─ Logical Isolation（最小 ResourceLoader + 工具白名单 + SessionManager.inMemory）
  │   ├─ Multi-Provider Routing（按 tier 解析模型 + thinking + fallback 链）
  │   ├─ dteam_signal（progress / finding / 阻塞请求）+ dteam_report（统一结果模型）
  │   ├─ finding 单消费者事件队列 + dteam_control（steer / graceful_stop / cancel）
  │   └─ 执行 → Worker Snapshot / parent event / completed event / wait result
  │
  └─ 主对话结构化上下文 + 人类可读工具投影 + `/dteam` 管理视图

不维护 Reporter 或自动编排 UI；0.8 的会话级后台运行态由 `/dteam` 按需展示 Worker Snapshot，主模型经 `dteam_respond` 回应普通请求、经 `dteam_control` 协调 running worker、经 `dteam_recover` 处理 timeout、经 `dteam_wait` 等待真实依赖。
```

## 6. 当前实现不变量（0008 + 0020 + 0021 + 0024）

| 不变量 | 说明 |
|---|---|
| 五个公开工具 | dispatch、普通回应、主动控制、timeout recovery 与显式依赖等待独立 schema；不保留旧工具 |
| 可行动发现上行 | 只有带 summary/evidence/impact 且可能改变路径的 finding 进入 parent event；progress、实时文本和工具活动只更新 UI / Snapshot |
| 主代理主动控制 | `dteam_control` 只作用于 `running` worker；steer / graceful_stop / cancel 不需要 requestId，不授予工具、不扩大 writeScope |
| 优雅停止优先 | graceful_stop 要求合法 `partial` 报告；必要时 cancel 标记 `cancelInitiator=main` 并同步返回可写中断守卫 |
| control 投递事实 | Worker Manager 独占逻辑隔离 worker session；新 steer / graceful_stop 会移除同一 worker 未注入的旧 control，并记录 queued / injected / superseded / expired。injected 只表示离开 Pi queue，不代表 worker 已执行；老 runtime 缺 `clearQueue()` 时第二条 latest-wins control fail-closed |
| Snapshot 可观察性 | context usage 仅只读展示且 candidate-scoped；null、缺 API 或 getter 异常不复用旧值。pending request 只投影脱敏摘要、requestId 与精确 response type |
| 单消费者事件与 wait 投影 | finding、终态和中断事件由 `dteam_wait` 或 idle/settled follow-up 二选一消费，不能重复回放；wait 对外只给脱敏、有界事件/worker/request view，不泄露 task、完整 Snapshot 或原始 payload |
| worker 是 fresh session | Logical Isolation：`SessionManager.inMemory()` + 最小 ResourceLoader + 工具白名单 |
| candidate 隔离 | 每个 candidate 的 signal / report 工具绑定独立 `candidateId`；fallback 或 fresh recovery 后拒绝旧 session 的迟到写入 |
| 统一 WorkerReport | outcome、activities、facts、verification 必填；合法报告才允许 Manager completed |
| facts provenance | completed event 只为 facts 注入真实 workerId；verification 不进入 handoff |
| 思考跟随档位 | 默认 T1高/T2中/T3低；dispatch 可覆盖 |
| T1/T2/T3 三档 | 取代五角色；不做角色市场 |
| 多轮只在主代理 | Manager 不保存轮次、batch、依赖、外部地图或后继任务 |
| 不做 resume | 见 ADR 0004 |

## 7. 已推翻的旧形态（保留追溯）

**被 ADR 0008 推翻**（0005/0006/0007）：
- **Orchestrator Loop / Signal Store / LLM-Driven 每轮现场决策** → 主模型路由 + dispatch 取代
- **对抗式合议 / 对抗回合 / 积分制 / N design 差异化** → 繁琐无用放弃（fresh check 零件复活到验收）
- **五角色（explore/design/build/check/close 职能分工）** → T1/T2/T3 能力分级
- **强制 check 收口（Completion Gate）** → fresh 验收（dispatch 用法）

**被 ADR 0005 推翻**（0.4.x/0.5.0）：
- 后台运行 / `runId` / `RunsStore`；`solo/chain/team` + `direct/build_check/adaptive` 二维编排；`SchedulingPlan`/`FileGraph`；planner 穷举；进程级 OS 子进程隔离作为默认。

详见 [`../30-路线图/30-项目路线图.md`](../30-路线图/30-项目路线图.md) "已推翻"段。

## 8. 从外部系统学到的架构边界

| 来源 | 对 dteam 的启发 | 0008 采纳 |
|---|---|---|
| ant-colony（蚁群系统） | 多态分工（T1/T2/T3 = castes）+ Multi-Provider Routing + Adaptive Concurrency | ✅ 核心血源 |
| zcode-swarm 蜂群插件 | coordinator 派发形态 + fresh 红队审核 | ✅ 印证形态 |
| dgoal | 建检循环、独立终审、不让学生判卷 | fresh 验收同源 |
| Curio（507 真实项目） | 大量小任务积压，强模型做小任务是双重浪费 | ✅ 真实痛点锚定 |
| Wayfinder / Ponytail / Critical-Fetch-Deep-Review | 动态证据前沿、最小承载探测、选源后有界提取、结果后再路由 | ✅ 移到主代理协议；不复活 Manager loop |

## 9. 已知限制（0008 当前）

- **真实派发验证**：自动化测试覆盖 dispatch 行为与入口契约；已在本 checkout 的有 API key Pi 环境完成一次有界真实双 worker 主动协调冒烟，仍未覆盖所有 provider、fallback、限流和长时运行组合。
- **路由倾向性**：主模型可能偷懒跳过 T3 探测、重复派发或误判档位；协议是规范性默认而非 Manager 硬门，后续以 routing benchmark 证伪和收窄。
- **外部读取**：第三方 extension 候选仍 fail-closed；当前由主代理选源并抓取 / clone 后让 T3 本地提取，尚无安全的 worker 任意联网能力。
- **文件写冲突**：并发 dispatch 改同一组文件会冲突；靠主模型判断文件独立性与 writeScope，不引入 worktree/file lock（除非成真实痛点）。
