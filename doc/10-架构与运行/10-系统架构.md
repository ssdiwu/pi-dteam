# dteam 系统架构

> 当前定义（0.6.0 重定义后）：dteam 是 **基于 goal（目标）自发生长的多 worker 群策群力扩展**。
>
> 决策骨架见 [`../adr/0005-dteam-0.6.0-重定义为自发生长召唤池.md`](../adr/0005-dteam-0.6.0-重定义为自发生长召唤池.md)（18 条根本决策）。
> 与 [`pi-dgoal`](../../../pi-dgoal) 独立并列：dteam = 群策群力，dgoal = 建检循环。

## 0. 产品定位

### 0.1 什么时候用 dteam

| 任务类型 | 推荐做法 |
|---|---|
| 简单改动、单文件修复、普通问答 | 主 LLM 直接干，不调 dteam |
| 单兵能持续推进 + 需要独立审核 | 用 dgoal（不是 dteam） |
| 需要群策群力——召唤多个专业角色协作 | 调 `dteam`（`/dteam <goal>` 或主 LLM 自动拉起） |
| 用户明确说"用 dteam / 走 dteam" | 必须触发 dteam |

详细 routing rule（路由规则）见 `14-dteam触发协议.md`。

### 0.2 dteam 负责什么

1. **自发生长**：接到 goal 后进入 Orchestrator Loop，任务从执行中涌现，不预先穷举 plan。
2. **召唤**：Orchestrator 每轮一次 LLM 调用，决定召唤哪个固定角色（explore / design / build / check / close）。
3. **隔离执行**：每个 worker 是进程内 `AgentSession`（代理会话）+ Logical Isolation（逻辑隔离）；`build` 唯一能 `edit`（编辑）现有文件。
4. **信号收集**：worker 通过 `session.subscribe` 把 progress / found / blocked / help 写入 Signal Store（信号存储）。
5. **收口**：goal 完成前必须召唤 `check` 通过（Completion Gate，收口闸门）。

### 0.3 dteam 不负责什么

- 不替代主 LLM 的普通编码能力
- 不做固定流水线 / 工业流程
- 不做项目管理工具
- 不做默认持久化 / resume（恢复）（见 [ADR 0004](../adr/0004-不做resume和默认持久化.md)）
- 不默认 spawn（启动）独立 OS 子进程（改为进程内 `AgentSession` + 逻辑隔离）
- 不引入可配置角色市场（见 [ADR 0002](../adr/0002-角色写死不做用户自定义角色.md)）
- 不预先穷举 Task Plan（计划）

## 1. 运行模型：同步前台 Orchestrator Loop

dteam 是**同步前台**执行：启动后进入 Orchestrator Loop（编排循环），阻塞主对话直到 `check` 收口完成。

```text
/dteam <goal> 或 主 LLM 自动拉起
  │
  └─ 进入 Orchestrator Loop（同步前台）
       │
       ├─ 读 Signal Store 当前快照
       ├─ 一次 LLM 调用：决定召唤哪个/哪些角色、给什么任务、并发多少
       ├─ 召唤 worker（进程内 AgentSession + Logical Isolation）
       │    └─ session.subscribe 实时把 progress/found/blocked/help 写入 Signal Store
       ├─ 收 worker 结果与信号
       ├─ 写入 Signal Store（TTL 衰减）
       └─ 继续循环 / 进入 check 收口 / 完成
```

**关键点**：
- **不再后台运行、不再返回 `runId`**（推翻 [ADR 0003](../adr/0003-后台运行依附Extension-Runtime而非单次tool-call.md)）。
- Orchestrator = dteam 对 ant-colony（蚁群系统）`queen`（蚁后）的去虫化命名。
- 启动方式 = C 混合：用户显式 `/dteam <goal>` 或主 LLM 自动拉起。

## 2. 运行结构

```text
dteam(goal)
  │
  ├─ index.ts
  │   ├─ /dteam <goal> 或主 LLM 自动拉起入口
  │   └─ 进入同步前台 Orchestrator Loop
  │
  ├─ src/orchestrator.ts（Orchestrator Loop 主循环）
  │   ├─ 读 Signal Store 快照
  │   ├─ LLM 驱动决策：召唤谁
  │   ├─ 召唤 worker（adaptive concurrency）
  │   └─ 强制 check 收口
  │
  ├─ src/leaf.ts + src/session.ts（worker 执行层）
  │   ├─ createAgentSession（进程内）
  │   ├─ Logical Isolation（最小 ResourceLoader + 工具白名单 + SessionManager.inMemory）
  │   ├─ Multi-Provider Routing（主模型 + fallback 链）
  │   └─ session.subscribe → 写 Signal Store
  │
  ├─ src/signals/*（Signal Store）
  │   └─ TTL 衰减、单 goal 生命周期、不落项目目录
  │
  └─ src/reporter.ts + src/ui/*
      └─ Orchestrator Loop 推进 + Signal Store 快照展示
```

## 3. 18 条核心决策（骨架摘要）

| 维度 | 决策 |
|---|---|
| 本质 | 召唤池，非流水线；删除 `solo/chain/team` |
| 运行 | 同步前台 Orchestrator Loop；放弃后台运行 |
| 主体 | Orchestrator（去 ant `queen` 隐喻） |
| 驱动 | LLM-Driven Orchestration（每轮一次 LLM 调用） |
| worker 基底 | 进程内 `AgentSession` + Logical Isolation |
| 计划 | 无预先 Task Plan；召唤轨迹即计划 |
| 信号 | Signal Store（TTL 衰减，临时，不落项目目录） |
| 并发 | Adaptive Concurrency + Multi-Provider Routing |
| 角色 | 固定 `explore/design/build/check/close` |
| 收口 | 强制 `check`（Completion Gate），Orchestrator 不能自停 |
| 边界 | 与 dgoal 独立并列（群策群力 ≠ 建检循环） |

完整表格见 ADR 0005。

## 4. 信号系统（Signal Store）

worker 通过 `session.subscribe` 把 4 类信号实时写入 Signal Store：

| signal（信号） | 含义 | Orchestrator 的处理 |
|---|---|---|
| `progress` | 进展更新 | 更新 Signal Store；影响下一步召唤决策 |
| `found` | 新发现 | 写入 Signal Store；可能触发同伴转发 |
| `blocked` | 无法继续 | Orchestrator 决定召唤 `explore` 自愈或换角色 |
| `help` | 需补充信息 | 先 `explore` 自愈，再升级到人类 |

**Signal Store 生命周期**：
- 单个 goal 的 Orchestrator Loop 内维护
- TTL（time to live，存活时间）衰减：新信号优先，旧信号过期
- 默认随编排循环结束清理，**不落项目目录**（去 ant-colony `pheromone` 信息素的持久目录）

## 5. 并发与多供应商

### 5.1 Adaptive Concurrency（自适应并发）

Orchestrator 可同时召唤多个 worker，并发度根据实际情况自适应升降（如供应商 429 限流）。参考 ant-colony `ConcurrencyConfig`（min/max/optimal/lastRateLimitAt）。

### 5.2 Multi-Provider Routing（多供应商路由）

每个角色可配置不同主模型 + fallback 链，避免单供应商约 3 个并发就撞墙。参考 ant-colony `ModelOverrides` + `FallbackModels` + `resolveModelWithFallback`。

> 注：`AGENTS.md` 旧"不做自适应并发"条款已被 0.6.0 更新——Adaptive Concurrency 现已采纳，配套 Multi-Provider Routing 应对并发墙。

## 6. 当前实现不变量

| 不变量 | 说明 |
|---|---|
| `build` 唯一能 `edit` | 其它角色不得修改已有代码文件 |
| 固定五角色 | `explore/design/build/check/close`；不引入用户自定义角色（ADR 0002） |
| 逻辑隔离 | 进程内 `AgentSession` 用 `SessionManager.inMemory()` + 最小 ResourceLoader + 工具白名单 |
| 强制 `check` 收口 | Orchestrator 不能自停；goal 完成前必须 `check` 通过 |
| Signal Store TTL | 旧信号自动衰减，不无限堆积 |
| 不做 resume | 见 ADR 0004 |
| `availableTools` 由主 LLM 传入 | dteam 不猜运行时工具宇宙 |

## 7. 已推翻的旧形态（保留追溯）

以下 v0.4.x / v0.5.0 的形态已被 [ADR 0005](../adr/0005-dteam-0.6.0-重定义为自发生长召唤池.md) 推翻，仅作历史追溯：

- **后台运行 / `runId` / `RunsStore` / 立即返回式 run** → 改为同步前台 Orchestrator Loop
- **`solo / chain / team` 组织模式 + `direct / build_check / adaptive` 执行策略**（二维编排）→ 删除
- **planner 穷举 / quick rule-based plan / LLM JSON fallback** → 改为 LLM-Driven Orchestration
- **`SchedulingPlan` / `FileGraph` / preflight batches 主轴** → 不再是编排核心
- **Task Plan / DPlan Contract** → 无预先计划，召唤轨迹即计划
- **进程级 OS 子进程隔离作为默认** → 改为进程内 `AgentSession` + Logical Isolation

详见 [`../30-路线图/30-项目路线图.md`](../30-路线图/30-项目路线图.md) "已推翻"段。

## 8. 从外部系统学到的架构边界

| 来源 | 对 dteam 的启发 | 0.6.0 采纳 |
|---|---|---|
| ant-colony（蚁群系统） | 进程内 `AgentSession` + 实时信号 + 自适应并发 + 多供应商 + 召唤池本质 | ✅ 核心血源 |
| 官方 subagent 示例 | tool calling、结构化输出 | 候选（信号通道改用进程内订阅） |
| dloop | 主代理执行 + 独立审核 | dgoal 项目已吸收；dteam 借鉴 `check` 收口思想 |
| dgoal | 建检循环、独立终审 | 独立并列项目，明确分工 |
| rpiv-todo | live overlay、低噪声 | Live Loop View 事中展示 |
| SwarmFlow / MiMo / Routa / pi-subagents | 编排与智能分离、证据、门禁 | 借轻动作，不照搬重型系统 |

## 9. 已知限制（0.6.0 当前）

- Orchestrator Loop 可能无限循环：靠强制 `check` 收口 + 最大轮次上限兜底。
- Signal Store 并发写冲突：TTL 衰减 + 最新覆盖；必要时引入 quorum 合并（参考 ant-colony）。
- Logical Isolation 不够"fresh"：最小 ResourceLoader 严格化；关键角色必要时回退子进程。
- 放弃后台运行导致长任务阻塞主对话：长任务由主 LLM 拆成多次 dteam 调用。
- 0.6.0 代码已落地（见 [`../40-版本实施方案/42-v0.6.0-召唤池重定义实施方案.md`](../40-版本实施方案/42-v0.6.0-召唤池重定义实施方案.md)）；端到端真实 LLM 实测需在有 API key 的 Pi 环境手验。
