# dteam 系统架构

> 当前定义（[ADR 0008](../决策档案/0008-dteam重定位为模型分级路由执行层.md)）：dteam 是 **模型分级路由执行层**。
>
> 与 [`pi-dgoal`](../../../pi-dgoal) 独立并列：dteam = 多模型分级路由，dgoal = 单模型建检循环。
>
> **实施状态**：本文描述并对应当前 0.7 实现：`leaf.ts` / `session.ts` 提供 T1/T2/T3 fresh dispatch、档位路由、超时、取消与并发；`index.ts` 只公开 `dteam_dispatch`。0.6 SignalStore/五角色/loop/UI 已删除。

## 0. 产品定位

### 0.1 什么时候用 dteam

| 任务类型 | 推荐做法 |
|---|---|
| 简单改动、单文件修复、普通问答 | 主 LLM 直接干，不调 dteam |
| 单兵能持续推进 + 需要独立审核 | 用 dgoal（不是 dteam） |
| 有大量小任务可分级并行加速（refactor 批、UI 优化批、独立模块小改） | 调 `dteam_dispatch` fan-out 给 T3 小模型批量做 |
| 用户明确说"用 dteam / 走 dteam" | 必须触发 dteam |

详细 routing rule（路由规则）见 `14-dteam触发协议.md`。

### 0.2 dteam 负责什么

1. **模型分级路由**：主模型（T1）判断任务难度 + 独立性，小任务 fan-out 给 T3 小模型批量并行做，大任务/思考自己做。
2. **dispatch 执行**：单工具 `dteam_dispatch(task, tier, thinking?, tools?)` 创建 fresh 进程内 worker session 执行，返回结果。
3. **思考跟随档位**：T1 高思考 / T2 中 / T3 低；难任务走回退换强模型，不是让小模型多想。
4. **fresh 验收**：主模型既是分配者又验收会倾向放水；dispatch 创建的 worker 都 fresh，验收 worker 不看主会话/方案出处。
5. **回退兜底**：硬失败自动回退 + 质量不过 fresh 验收触发回退到 T1。

### 0.3 dteam 不负责什么

- 不替代主 LLM 的普通编码能力
- 不做固定流水线 / 工业流程 / 编排引擎
- 不做项目管理工具
- 不做默认持久化 / resume（见 [ADR 0004](../决策档案/0004-不做resume和默认持久化.md)）
- 不维护独立的 task plan（主模型在对话里临时路由，不预先穷举）
- 不默认 spawn 独立 OS 子进程（用进程内 `AgentSession` + Logical Isolation）

## 1. 运行模型：主模型路由 + dispatch fan-out

dteam **没有独立的编排循环**（Orchestrator Loop 已被 0008 推翻）。主模型在对话里直接路由 + 调 dispatch：

```text
主模型（T1，owner，在对话里）
  │
  ├─ 思考 / 路由：判断任务难度 + 独立性
  │
  ├─ 小任务 → dteam_dispatch(T3, task, 低思考)  [可并发多个 = 并行 fan-out]
  │    ├─ 创建 fresh 进程内 worker session
  │    ├─ 执行 → 返回结果
  │    └─ 硬失败自动回退 / 质量不过 fresh 验收 → 回退 T1
  │
  └─ 大任务 / 思考 → 主模型自己做（高思考）
```

**关键点**：
- 主模型是 owner，带对话上下文判断路由（哪些任务独立可并行、哪些是小任务该给 T3）。
- dispatch 创建的 worker 是一次性 fresh session（做完返回），无信号回流、无独立循环。
- 主模型并发调用多个 dispatch = 并行 fan-out（依赖 Pi 的并行工具调用）。

## 2. 模型档位（T1/T2/T3，取代五角色）

| 档位 | 模型 | 思考 | 默认工具 | 用途 |
|---|---|---|---|---|
| **T1 思考档** | 旗舰 | 高 | 全工具（读写改 + 审核） | 思考 / 决策 / 验收 / 回退重做 |
| **T2 标准档** | 标准 | 中 | 可写（读写改） | 常规实现 |
| **T3 快速档** | 快速 / 本地 | 低 | 默认只读；显式限定写 | 机械小任务 |

- **标准锚定供应商产品线层级**（旗舰/标准/快速三线），价格为辅。
- **思考跟随档位**：小模型高思考收益递减 + 难任务走回退换强模型（自带高思考）。
- dispatch 可覆盖默认配置（如 T3 临时给可写权限做独立模块小改）。

## 3. fresh 验收与回退

### 3.1 fresh 验收（对抗主模型倾向）

主模型既是分配者又验收，会倾向放水（dgoal「不让学生判卷」原则迁移到路由+验收）。dispatch 创建的 worker 都是 fresh session（不继承主会话），所以：

```
验收 = dteam_dispatch(T1, "验收这个产出是否达标", 只读工具)
       ↑ fresh session，不看主会话/方案出处
```

验收不是独立工具，是 dispatch 的一个用法。**复活自 ADR 0007 的 fresh check 零件**（不是回到对抗式合议整体）。默认可选；关键任务才由主模型显式调 T1 fresh worker。

### 3.2 回退（可用性兜底）

| 触发 | 机制 |
|---|---|
| 硬失败（worker 报错/超时/工具异常） | 自动回退 |
| 质量不过（fresh 验收未通过） | 回退 T1 重做 / 主模型自己接手 |

这是「乐观用小模型（省）+ 兜底强模型（稳）」策略。

## 4. 并发与多供应商

### 4.1 Adaptive Concurrency（自适应并发）

主模型可同时 dispatch 多个 worker，并发度根据实际情况自适应升降（如供应商 429 限流）。参考 ant-colony `ConcurrencyConfig`。

### 4.2 Multi-Provider Routing（多供应商路由）

每个档位可配置不同主模型 + fallback 链，避免单供应商约 3 个并发就撞墙。通过 `DTEAM_T1_MODEL` / `T2` / `T3` 与对应 `_FALLBACK_MODELS` 显式声明；未配置 primary 时才回落 `ctx.model`。**0008 后是核心基础设施**，加 `tier` + `thinking` 字段激活。参考 ant-colony `ModelOverrides` + `FallbackModels`。

## 5. 运行结构（0008 目标形态）

```text
dteam_dispatch(task, tier, thinking?, tools?)
  │
  ├─ index.ts / tools.ts（dteam_dispatch 工具入口）
  │
  ├─ src/leaf.ts + src/session.ts（dispatch 实现）
  │   ├─ createAgentSession（进程内，fresh）
  │   ├─ Logical Isolation（最小 ResourceLoader + 工具白名单 + SessionManager.inMemory）
  │   ├─ Multi-Provider Routing（按 tier 解析模型 + thinking + fallback 链）
  │   └─ 执行 → 返回结果
  │
  └─ 主对话结果 + ctx.ui status/notify（当前入口观察）

不维护 Reporter、Signal UI 或独立面板；主模型直接消费 `DispatchResult`。
```

## 6. 当前实现不变量（0008）

| 不变量 | 说明 |
|---|---|
| 单工具 dteam_dispatch | 执行/验收/回退都是它的用法；不拆多工具 |
| worker 是 fresh session | Logical Isolation：`SessionManager.inMemory()` + 最小 ResourceLoader + 工具白名单 |
| 思考跟随档位 | 默认 T1高/T2中/T3低；dispatch 可覆盖 |
| T1/T2/T3 三档 | 取代五角色；不做角色市场 |
| 不做 resume | 见 ADR 0004 |

## 7. 已推翻的旧形态（保留追溯）

**被 ADR 0008 推翻**（0005/0006/0007）：
- **Orchestrator Loop / Signal Store / LLM-Driven 每轮现场决策** → 主模型路由 + dispatch 取代
- **对抗式合议 / 对抗回合 / 积分制 / N design 差异化** → 繁琐无用放弃（fresh check 零件复活到验收）
- **五角色（explore/design/build/check/close 职能分工）** → T1/T2/T3 能力分级
- **强制 check 收口（Completion Gate）** → fresh 验收（dispatch 用法）

**被 ADR 0005 推翻**（0.4.x/0.5.0）：
- 后台运行 / `runId` / `RunsStore`；`solo/chain/team` + `direct/build_check/adaptive` 二维编排；`SchedulingPlan`/`FileGraph`；planner 穷举；进程级 OS 子进程隔离作为默认。

详见 [`../30-路线图/30-项目路线图.md`](../30-路线图/30-项目路线图.md) "已推翻"段。

## 8. 从外部系统学到的架构边界

| 来源 | 对 dteam 的启发 | 0008 采纳 |
|---|---|---|
| ant-colony（蚁群系统） | 多态分工（T1/T2/T3 = castes）+ Multi-Provider Routing + Adaptive Concurrency | ✅ 核心血源 |
| zcode-swarm 蜂群插件 | coordinator 派发形态 + fresh 红队审核 | ✅ 印证形态 |
| dgoal | 建检循环、独立终审、不让学生判卷 | fresh 验收同源 |
| Curio（507 真实项目） | 大量小任务积压，强模型做小任务是双重浪费 | ✅ 真实痛点锚定 |

## 9. 已知限制（0008 当前）

- **真实派发验证**：自动化测试覆盖 dispatch 行为与入口契约；真实 provider 调用仍需在有 API key 的 Pi 环境手验。
- **路由倾向性**：主模型可能偷懒跳过验收或误判任务难度；靠 fresh 验收兜底，但不强制（A 形态要轻）。
- **文件写冲突**：并发 dispatch 改同一组文件会冲突；靠主模型判断文件独立性（它有上下文），不引入 worktree/file lock（除非成真实痛点）。
