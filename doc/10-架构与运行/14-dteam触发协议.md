# dteam 触发协议

> 目的：让主 LLM 在面对任务时有明确 routing rule（路由规则），避免版本级、多模块、有验收门禁的任务被主 LLM 直接吞掉。dteam 仍保持轻量：它不是默认工具，而是复杂编程任务的后台协作执行层。

## 1. 一句话规则

> **简单任务主 LLM 直接做；版本级、多模块、多阶段、有验收门禁的任务默认走 dteam；用户明确说“用 dteam”时必须走 dteam。**

## 2. 必须触发 dteam

命中任一强触发条件时，主 LLM 应调用：

```ts
dteam(action="run", goal="...")
```

| 强触发条件 | 说明 |
|---|---|
| 用户明确说“用 dteam / 走 dteam / 让 dteam 做” | 用户显式指定优先级最高 |
| “按这个版本实施方案完整实现” | 版本级方案通常包含多阶段、约束和验收 |
| 任务要求后台执行，不阻塞主对话 | dteam 的 `run` 就是后台模型 |
| 任务天然需要多个角色接力 | 例如先探索、再设计、再实现、再验证、最后收口 |
| 任务涉及多个独立方向可并行推进 | dteam runtime 可做 preflight scheduling 和 batch 拆分 |

## 3. 默认触发 dteam

没有强触发，但命中以下条件中任意 2 条，默认应走 dteam，除非用户明确要求“你直接做”。

| 判断项 | 例子 |
|---|---|
| 版本级 / milestone 级任务 | `V1.0.3 实施方案`、`0.5.x 可选增强` |
| 涉及 3 个以上模块 / 目录 | `src/vault` + `src/ui` + `tests` + `doc` |
| 同时包含代码、测试、文档、UI 中的 3 类以上 | 实现 + 测试 + README + 面板 |
| 有 checklist / phase / 验收标准 | `P0~P6`、`验收标准 20 条` |
| 涉及数据契约、缓存、pipeline、状态流转 | cache invalidation、CLI pipeline、UI 状态 |
| 需要先读大量上下文再实施 | 需要读 doc、README、现有实现、测试 |
| 有明确风险约束 | “不能破坏旧入口”、“必须统一 policy”、“必须可追溯” |
| 需要真实验证或分阶段验收 | build/test/dry-run/真实样本验收 |

## 4. 不应该触发 dteam

| 场景 | 推荐做法 |
|---|---|
| 普通问答 / 解释代码 | 主 LLM 直接回答 |
| 单文件小改 | 主 LLM 直接改 |
| 修 typo / 格式 / 文案 | 主 LLM 直接改 |
| 跑一个命令或查一个状态 | 主 LLM 直接跑 |
| 只做方案评审，不实施 | 主 LLM 先分析，不调 dteam |
| 用户要求“你先别改代码” | 不调 dteam，不改代码 |

## 5. 触发前的主 LLM 自检

主 LLM 在决定是否调用 dteam 前，应快速问自己：

```text
1. 这是不是实施任务，而不只是讨论 / 评审？
2. 是否需要探索 + 实现 + 验证？
3. 是否跨多个模块或文件边界？
4. 是否有阶段、验收、风险或回退要求？
5. 如果我直接做，是否容易漏掉证据或验收？
```

如果第 1 条为“是”，且 2~5 命中两条以上，默认走 dteam。

## 6. 用户显式触发语句

以下说法都视为强制触发：

```text
用 dteam 做这个
这个任务走 dteam
让 dteam 按这个方案实施
用 dteam 跑一轮后台实现
交给 dteam，完成后给我 report
```

如果用户同时要求范围，例如“只做 P0~P2”，goal 必须保留这个范围，不得自动扩大。

## 7. 示例

### 7.1 应触发：版本实施方案

用户：

```text
按 doc/40-版本实施方案/40-V1.0.3-群聊近期动态与关键人物群内角色实施方案.md 实现。
```

判断：

- 版本级方案
- 多阶段 checklist
- 多模块代码 / 测试 / UI / 文档
- 有数据契约、缓存、pipeline、状态流转
- 有验收标准

结果：应调用 dteam。

### 7.2 不触发：只问是否适合

用户：

```text
这份 V1.0.3 方案你会用 dteam 做吗？
```

判断：这是评估问题，不是实施请求。

结果：主 LLM 直接分析，不调 dteam。

### 7.3 不触发：局部小改

用户：

```text
把 README 里 dteam 的一句介绍改得更短。
```

判断：单文件文案小改。

结果：主 LLM 直接做。

### 7.4 默认触发：多模块增强

用户：

```text
给 dteam 加 status action，同时更新 README、API 文档和测试。
```

判断：代码 + 文档 + 测试，跨 API / index / tests，且有用户可见行为。

结果：默认走 dteam；若用户说“你直接改”，则主 LLM 可直接做。

## 8. 边界

dteam 触发协议不是为了把所有任务都变重。它只解决一个问题：

> 当任务的复杂度来自“拆解、交接、证据、验收”时，主 LLM 应把它交给 dteam，而不是靠单轮上下文硬扛。

因此 dteam 仍不做：

- 持久 Kanban
- 企业级 Harness
- 固定 6 阶段流水线
- 自动审批流
- 角色市场
