# dteam 触发协议

> 目的：规定主代理何时以及如何使用 dteam 取得证据、分级实施与验证，并在 dteam、dgoal 和直接处理之间正确选择。
>
> 当前权威：[ADR 0020](../决策档案/0020-主代理证据驱动多轮路由协议.md)。本协议是规范性默认，不是 Worker Manager 的自动状态机；用户明确要求直接处理、指定档位、使用 dgoal 或不调用 dteam 时优先服从。

## 1. 一句话规则

> **不需要新事实的极小任务直接做；需要从仓库或已选外部来源取得事实的非极小任务，先用有界 T3 分轮取证；事实足够后，机械小改交 T3、已定位常规实现交 T2、复杂判断与高风险验收交 T1；长串行目标和独立终审由 dgoal 管目标，阶段内仍可用 dteam 取证。**

## 2. dteam vs dgoal vs 直接处理

| 判断 | 入口 |
|---|---|
| 普通概念问答、已有上下文足够、单步机械改且无需仓库探索 | 主代理直接处理 |
| 非极小任务仍需仓库事实、独立证据面、外部来源提取、机械实现或 fresh 复验 | **dteam** |
| 目标有串行依赖、需持续推进、需冻结验收合同或独立终审 | **dgoal**；阶段内可用 dteam fan-out |
| 一批独立小任务可并行 | **dteam** |
| 用户明确指定 dteam / dgoal / 直接处理 | 服从用户 |

两者独立并列：dgoal 保存目标、计划和验收；dteam 只执行主代理当前派出的有界 worker，不保存 dgoal task 映射或后继依赖。

## 3. 派发前由主代理保留的判断

主代理先完成三件事，再写 worker task：

1. **锁定当前目标**：用户究竟要理解、修改、验证还是交付什么；
2. **保留用户决策**：产品意图、风险承受、不可逆取舍和只能由用户回答的问题不派给 worker；
3. **定义证据问题**：本轮拿到什么事实，主代理就能作出下一步判断。

不要求预生成完整任务树，也不把“前沿”“轮次”或 expected verification depth 写进 Manager schema。worker task 应自包含、范围有界，并说明期望回传的事实格式或验证证据。
`writeScope` 与 worker task 中的局部限制只约束对应 worker；主代理不得把它们提升为父任务的非目标、交付边界或完成依据。

## 4. 代码任务：多轮、多证据面 T3

### 4.1 第一轮

凡非极小代码任务且仍需仓库事实，默认先派 1–3 个相互独立的只读 T3。证据面按任务动态选择，不固定全上：

- 目录职责、架构边界和权威文档；
- 入口、调用链、数据流或错误路径；
- 现有测试、配置、构建与可复验信号；
- 仓内已有、标准库、原生平台或已安装依赖能否承载；
- 变更范围、兼容性、安全或用户可见风险。

多个 worker 不应重复搜索同一问题；主代理负责筛选相互补充的视角。

### 4.2 汇总与下一轮

主代理只消费合法 `WorkerReport`，核对 facts 的 claim / evidence 与 workerId 来源，裁决冲突并写出当前已知、约束和具体未知。只有新暴露的未知仍会改变实现决策时，才派下一轮 fresh T3；不得为了“更完整”固定追加轮次。

事实足够后：

- 独立机械小改：T3 + 显式最小 `addTools` + `writeScope`；
- 已定位的常规实现：T2；
- 复杂架构判断、高风险收敛或低档证据冲突：T1；
- 不需要实现：主代理直接收口并说明证据。

### 4.3 完成后的验证

验证也按最低足够档位 fresh 派发。主代理根据任务风险选择检查范围，不要求 worker 假装达到环境不支持的深度。worker 只报告实际 `verification.depth / status / evidence / remaining`；若缺模拟器、浏览器、账号或服务，remaining 进入下一步路由或用户人工复测。

## 5. 外部信息：主代理选源，T3 提取

外部事实遵循固定责任边界：

1. 主代理定义问题、搜索并选择可信的一手来源；
2. 当前版本由主代理抓取、clone 或保存到 worker 可读位置；
3. T3 只对已选来源做有界提取、对照或复验；
4. 主代理综合多源结论、反证与时间边界。

当前第三方 extension 工具仍 fail-closed，不能声称 worker 可任意联网。未来受限只读联网工具验证完成后，也只允许读取主代理指定 URL，不把来源选择和最终裁决下放给 T3。

## 6. 根据 WorkerReport 路由下一步

Manager `state=completed` 仅表示 worker 正常结束并提交合法报告。主代理必须分别读取：

- `outcome`：任务完成还是 partial；
- `activities`：实际 inspected / modified / tested / executed / captured_visual；
- `facts`：可复验且可进入 bounded handoff 的事实；
- `verification`：实际深度、结果、证据和 remaining；
- `uncertainties`：仍可能改变结论的未知。
- `writeScope` / `workerBoundary`：当前 worker 的局部预期写入范围，不是父任务的覆盖证明；

然后只选择当前必要动作：

| 报告信号 | 下一步 |
|---|---|
| outcome completed，证据足够，风险可接受 | 收口 |
| outcome partial 或 remaining 会影响交付 | 缩小问题后 fresh 重派或补验 |
| 事实缺失 / 来源冲突 | 新一轮有界 T3 取证 |
| 低档无法判断且目标已清楚 | 相邻升级 T3→T2→T1 |
| 验证 failed | 建立失败反馈环，修根因后再验 |
| 只能由用户决定或人工环境才能验证 | 回到用户；不改写 worker 历史报告 |

若 worker 已知有范围外未覆盖的工件或检查，应在 `remaining` 中明确；尚未查明但可能改变结论的风险进入 `uncertainties`。主代理据此决定是否派 fresh T3 复核声明交付物、实际 diff 与相关工件；Manager 不自动派发或阻断收口。

## 7. 外部耐久地图与长任务

issue、PRD、spec、dgoal plan 或项目既有地图可以保存跨会话目标、决策与依赖。主代理只把当前 slice、必要事实与 evidence pointer 交给 dteam。dteam 不保存外部 ID、不更新地图、不恢复旧 worker session，也不把完整地图或主会话全文注入 worker。
主会话发生 compaction（压缩）时，dteam 不恢复 worker session 或保存 transcript；仅在当前 Pi 进程内从 Manager Snapshot 一次性重注入未收口 worker 的有界摘要。摘要只包含局部范围、验证、事实摘要和未收口风险，注入后即消费。

## 8. 示例

### 8.1 非极小单模块修复

即使最终只改一个文件，只要根因、调用链或测试入口尚未确认，也先派 T3 分别定位代码路径和现有反馈环；主代理综合后交 T2 作最小修复，再派 fresh T3 跑定向检查。它不因“单文件”自动退化为主代理盲改。

### 8.2 一批独立小改

多个模块或文档可独立验证时，一次 `dteam_dispatch` fan-out；写入范围不重叠，主代理汇总完成报告后统一验证。不得为并行而拆出相互依赖的水平层。

### 8.3 长串行目标

需要“探索 → 决策 → 实施 → 独立终审”的长期目标用 dgoal 保持计划和验收。每个阶段出现可并行证据面或机械小改时再用 dteam；dteam 不接管 dgoal goal。

### 8.4 极小直接改

用户明确指出 README 某句要替换，位置和目标文本都已知，且无需额外事实：主代理直接改，不为遵守协议制造 worker 往返。

## 9. 明确不做

- Orchestrator Loop、固定流水线、预生成完整任务树；
- Manager 自动派发、自动选择下一档或保存依赖图；
- 每个问题强制 worker、固定视角清单、固定轮数；
- worker 独自选择外部来源并作最终裁决；
- 把人工复测、用户决策或 expected verification depth 伪装成 worker 证据；
- 跨进程 worker resume、完整 transcript 或 worker P2P 消息。
