# dteam 触发协议

> 目的：让主 LLM 在面对任务时有明确 routing rule（路由规则），并在 dteam 与 dgoal 之间正确选择。
>
> 0.6.0 重定义后：dteam = 群策群力（召唤池，同步前台 Orchestrator Loop）；dgoal = 建检循环（单兵 + 独立审核）。两者独立并列。

## 1. 一句话规则

> **简单任务主 LLM 直接做；单兵能持续推进 + 需独立审核走 dgoal；需要群策群力（召唤多个专业角色）走 dteam；用户明确说"用 dteam / 用 dgoal"时必须尊重。**

## 2. dteam vs dgoal 判断（核心）

| 判断 | 走哪个 |
|---|---|
| 单代理能干，自己持续推进即可 | 主 LLM 直接做 |
| 单兵推进 + 需要独立零上下文终审 | **dgoal**（建检循环） |
| 需要召唤多个专业角色（explore/design/build/check/close）协作 | **dteam**（群策群力） |
| 用户明确说"用 dteam" | **dteam** |
| 用户明确说"用 dgoal / /dgoal" | **dgoal** |

两者独立并列，不合并，不自动切换。主 LLM 自己判断。

## 3. 必须触发 dteam

命中任一强触发条件时，主 LLM 应调用 `dteam(goal="...")`：

| 强触发条件 | 说明 |
|---|---|
| 用户明确说"用 dteam / 走 dteam / 让 dteam 做" | 用户显式指定优先级最高 |
| 任务天然需要多个角色接力协作 | 例如先探索、再设计、再实现、再验证、最后收口——这种"群策群力"是 dteam 的本质 |
| 任务有多个独立方向可并行推进 | Orchestrator 可自适应并发召唤多 worker |

## 4. 默认触发 dteam

没有强触发，但命中以下条件中任意 2 条，默认应走 dteam，除非用户明确要求"你直接做"或"用 dgoal"。

| 判断项 | 例子 |
|---|---|
| 版本级 / milestone 级任务 | `0.6.0 实施方案`、`V1.0.3 实施` |
| 涉及 3 个以上模块 / 目录 | `src/vault` + `src/ui` + `tests` + `doc` |
| 同时包含代码、测试、文档、UI 中的 3 类以上 | 实现 + 测试 + README + 面板 |
| 有 checklist / phase / 验收标准 | `P0~P6`、`验收标准 20 条` |
| 涉及数据契约、缓存、pipeline、状态流转 | cache invalidation、CLI pipeline、UI 状态 |
| 需要先读大量上下文再实施 | 需要读 doc、README、现有实现、测试 |
| 有明确风险约束 | "不能破坏旧入口"、"必须统一 policy"、"必须可追溯" |
| 需要真实验证或分阶段验收 | build/test/dry-run/真实样本验收 |

## 5. 不应该触发 dteam

| 场景 | 推荐做法 |
|---|---|
| 普通问答 / 解释代码 | 主 LLM 直接回答 |
| 单文件小改 | 主 LLM 直接改 |
| 修 typo / 格式 / 文案 | 主 LLM 直接改 |
| 跑一个命令或查一个状态 | 主 LLM 直接跑 |
| 只做方案评审，不实施 | 主 LLM 先分析，不调 dteam |
| 用户要求"你先别改代码" | 不调 dteam，不改代码 |
| 单兵能干 + 只需独立审核 | 走 dgoal，不是 dteam |

## 6. 触发前的主 LLM 自检

主 LLM 在决定是否调用 dteam 前，应快速问自己：

```text
1. 这是不是实施任务，而不只是讨论 / 评审？
2. 是否需要探索 + 实现 + 验证的多角色协作？
3. 是否跨多个模块或文件边界？
4. 是否有阶段、验收、风险或回退要求？
5. 单兵能干吗？能干 + 要独立审核 → dgoal；不能 / 需群策群力 → dteam。
```

## 7. 用户显式触发语句

以下说法都视为强制触发 dteam：

```text
用 dteam 做这个
这个任务走 dteam
让 dteam 按这个方案实施
用 dteam 召唤几个角色协作
交给 dteam，完成后给我报告
```

以下说法视为走 dgoal：

```text
用 dgoal 做这个
/dgoal <目标>
```

如果用户同时要求范围，例如"只做 P0~P2"，goal 必须保留这个范围，不得自动扩大。

## 8. 示例

### 8.1 应触发 dteam：版本实施方案

用户：

```text
按 doc/40-版本实施方案/42-v0.6.0-召唤池重定义实施方案.md 实现。
```

判断：版本级方案、多角色协作（探索/实现/验证/收口）、多模块。

结果：应调用 dteam。

### 8.2 走 dgoal：单兵 + 独立审核

用户：

```text
/dgoal 把这个 README 的错别字全改了，改完独立审核一遍。
```

判断：单兵能干 + 需要独立终审。

结果：走 dgoal，不是 dteam。

### 8.3 不触发：只问是否适合

用户：

```text
这份 0.6.0 方案你会用 dteam 做吗？
```

判断：这是评估问题，不是实施请求。

结果：主 LLM 直接分析，不调 dteam。

### 8.4 不触发：局部小改

用户：

```text
把 README 里 dteam 的一句介绍改得更短。
```

判断：单文件文案小改。

结果：主 LLM 直接做。

### 8.5 默认触发：多模块增强

用户：

```text
给 dteam 加一个新能力，同时更新 README、API 文档和测试。
```

判断：代码 + 文档 + 测试，跨 API / index / tests，且需要 explore+build+check 协作。

结果：默认走 dteam；若用户说"你直接改"或"用 dgoal"，则按用户指定。

## 9. 边界

dteam 触发协议不是为了把所有任务都变重。它只解决一个问题：

> 当任务的复杂度来自"拆解、交接、多角色协作、证据、验收"时，主 LLM 应把它交给 dteam 群策群力，而不是靠单轮上下文硬扛。

因此 dteam 仍不做：

- 持久 Kanban
- 企业级 Harness
- 固定 6 阶段流水线
- 自动审批流
- 角色市场
- 后台运行（0.6.0 改同步前台）
