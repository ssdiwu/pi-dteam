# dteam 角色系统

> 角色系统保持写死：`explore` / `design` / `build` / `check` / `close`。这是有意设计（见 [ADR 0002](../决策档案/0002-角色写死不做用户自定义角色.md)），不是临时限制。
>
> 0.6.0 重定义后，角色是**被 Orchestrator 按需召唤的专业角色池**（召唤池本质），不是流水线阶段。`check` 是强制收口闸门（Completion Gate）。

## 1. 角色清单

| 角色 | 中文定位 | 主要职责 | 是否能改现有文件 |
|---|---|---|:---:|
| `explore` | 探索者 | 读代码、查资料、发现入口和风险 | ❌ |
| `design` | 方案者 | 输出实施方案、权衡、ADR（架构决策记录） | ❌ |
| `build` | 实现者 | 写代码、改文档、补测试 | ✅ |
| `check` | 验收者 | 跑测试、审查结果、指出问题；**强制收口闸门** | ❌ |
| `close` | 收口者 | 总结、归档、沉淀经验 | ❌ |

核心边界：**只有 `build` 能 `edit`（编辑）已有文件**。

## 2. check 是 Completion Gate（收口闸门）

0.6.0 的关键决定（ADR 0005 第 14 条）：**Orchestrator Loop 不自行判定完成；每个 goal 必须召唤 `check` 角色做收口确认才算完成。**

这防止 `check` 被忽略，保证群策群力有明确的收尾验证。它和 dgoal 的独立审核（零上下文子进程终审）在概念上呼应，但机制不同：

| | dteam `check` | dgoal 独立审核 |
|---|---|---|
| 形态 | 进程内固定角色 worker | 独立零上下文子进程 |
| 隔离 | Logical Isolation（逻辑隔离） | OS 进程级隔离 |
| 触发 | Orchestrator 强制召唤 | goal 完成时自动终审 |

## 3. worker 是进程内 AgentSession + 逻辑隔离

每个 worker 是进程内 `AgentSession`（代理会话），不是 OS 子进程（ADR 0005 第 5 条）。隔离靠 Logical Isolation（逻辑隔离）：

- `SessionManager.inMemory()` — 不继承主对话会话
- 最小 `ResourceLoader` — 不加载 extensions/skills/prompts/themes
- 工具白名单 — 由角色 `ROLE_DEFAULTS` + 主 LLM 传入的 `availableTools` 取交集
- 独立 system prompt — 角色提示词 + Orchestrator 传入的 goal/task/Signal Store 摘要

worker 通过 `session.subscribe` 实时把 progress / found / blocked / help 写入 Signal Store。

## 4. 为什么不借鉴 pi-subagents 的可配置角色

`pi-subagents`（Pi 子代理扩展）支持 markdown frontmatter（前置元数据）定义 agent、override（覆盖）模型 / 工具 / prompt（提示词）。dteam 不借这部分：

| 选择 | 原因 |
|---|---|
| 角色写死 | 5 个角色已覆盖当前个人编程工作流（ADR 0002） |
| 工具权限写在代码里 | 更容易验证 `build` 唯一可写这一安全边界 |
| 不做用户自定义角色 | 避免角色数量膨胀、Orchestrator 决策不稳定 |
| 模型可配（Multi-Provider Routing） | 0.6.0 新增：每角色可配主模型 + fallback 链，应对并发墙 |

## 5. 工具权限矩阵

实际 fallback（降级）工具表来自 `src/session/role-config.ts` 的 `ROLE_DEFAULTS`。当主 LLM 传入 `availableTools` 且 Orchestrator 决定该 worker 的工具时，会按可用工具交集透传；否则回落到角色默认工具。

| 工具 | explore | design | build | check | close |
|---|:---:|:---:|:---:|:---:|:---:|
| `read` | ✅ | ✅ | ✅ | ✅ | ✅ |
| `bash` | ✅ | ✅ | ✅ | ✅ | ✅ |
| `grep` | ✅ | ✅ | ✅ | ✅ | ✅ |
| `find` | ✅ | ✅ | ✅ | ✅ | ✅ |
| `ls` | ✅ | ✅ | ✅ | ✅ | ✅ |
| `edit` | ❌ | ❌ | **✅** | ❌ | ❌ |
| `write` | ✅ | ✅ | **✅** | ✅ | ✅ |
| `tinyfish_search` | ✅ | ❌ | ❌ | ❌ | ❌ |
| `tinyfish_fetch` | ✅ | ❌ | ❌ | ❌ | ❌ |

说明：
- `write` 可以写新文件；`edit` 才是修改现有文件的关键权限。
- 联网检索默认只给 `explore`，避免实现 / 验收角色在没有必要时扩大外部依赖。
- `availableTools` 只解决"用户环境里有哪些工具可用"，不改变角色职责边界。

## 6. Orchestrator 如何召唤角色

Orchestrator 每轮一次 LLM 调用，依据 `goal + Signal Store 当前快照 + 已完成 worker 结果`，决定召唤哪个角色。这是开放式决策，不预设固定组合（删除了旧 `solo/chain/team` 常见位置表）。

典型召唤轨迹（涌现，非预设）：
- 探索阶段：召唤 `explore` 了解代码
- 发现需要方案：召唤 `design`
- 实施：召唤 `build`
- 收口：**强制召唤 `check`**
- 总结归档：按需召唤 `close`

这些不是固定流水线，Orchestrator 按当前 Signal Store 自行判断召唤谁。

## 7. 角色文件

角色 prompt 存在 `agents/*.md`：

| 文件 | 角色 |
|---|---|
| `agents/explore.md` | `explore` |
| `agents/design.md` | `design` |
| `agents/build.md` | `build` |
| `agents/check.md` | `check` |
| `agents/close.md` | `close` |

当前 frontmatter 主要作为说明和未来兼容；运行时权威配置仍在代码的 `ROLE_DEFAULTS`。

## 8. 修改角色的原则

1. 先确认是否真的需要改角色，而不是改 prompt 或 Orchestrator 决策。
2. 如果涉及工具权限，优先保护 `build` 唯一可写边界。
3. 不新增角色，除非已有 3 次真实任务证明 5 角色不够（ADR 0002）。
4. 改角色后必须同步更新：`agents/*.md`、`src/session/role-config.ts`、`src/types/role.ts`、本文档。
