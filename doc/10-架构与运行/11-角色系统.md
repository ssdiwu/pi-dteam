# dteam 角色系统

> 当前角色系统保持写死：`explore` / `design` / `build` / `check` / `close`。这是有意设计，不是临时限制。dteam 现在要解决 507 的个人编程复杂任务，不追求开放角色市场。

## 1. 角色清单

| 角色 | 中文定位 | 主要职责 | 是否能改现有文件 |
|---|---|---|:---:|
| `explore` | 探索者 | 读代码、查资料、发现入口和风险 | ❌ |
| `design` | 方案者 | 输出实施方案、权衡、ADR（架构决策记录） | ❌ |
| `build` | 实现者 | 写代码、改文档、补测试 | ✅ |
| `check` | 验收者 | 跑测试、审查结果、指出问题 | ❌ |
| `close` | 收口者 | 总结、归档、沉淀经验 | ❌ |

核心边界：**只有 `build` 能 `edit`（编辑）已有文件**。

## 2. 为什么不借鉴 pi-subagents 的可配置角色

`pi-subagents`（Pi 子代理扩展）支持 markdown frontmatter（前置元数据）定义 agent、override（覆盖）模型 / 工具 / prompt（提示词）。这对通用插件很有价值，但 dteam 目前不借这部分：

| 选择 | 原因 |
|---|---|
| 角色写死 | 5 个角色已覆盖当前个人编程工作流 |
| 工具权限写在代码里 | 更容易验证 `build` 唯一可写这一安全边界 |
| 不做用户自定义角色发现 | 避免角色数量膨胀、planner 输出不稳定 |
| 允许未来局部 override | 等真实痛点出现后再评估，不提前抽象 |

可借鉴的是 pi-subagents 的**边界意识**：child agent 默认不应拥有父级编排权；dteam 当前通过单一 `dteam` 工具 + worker session（会话）边界实现类似约束。

## 3. 工具权限矩阵

实际 fallback（降级）工具表来自 `src/session/role-config.ts` 的 `ROLE_DEFAULTS`。当主 LLM 传入 `availableTools` 且 planner LLM 路径产出 `step.tools` 时，会按可用工具交集透传；否则回落到角色默认工具。

| 工具 | explore | design | build | check | close |
|---|:---:|:---:|:---:|:---:|:---:|
| `read` | ✅ | ✅ | ✅ | ✅ | ✅ |
| `bash` | ✅ | ✅ | ✅ | ✅ | ✅ |
| `grep` | ✅ | ✅ | ✅ | ✅ | ✅ |
| `find` | ✅ | ✅ | ✅ | ✅ | ✅ |
| `ls` | ✅ | ✅ | ✅ | ✅ | ✅ |
| `edit` | ❌ | ❌ | **✅** | ❌ | ❌ |
| `write` | ✅ | ✅ | **✅** | ✅ | ✅ |
| `tinyfish_search` | ✅ | ❌ | ❌ | ❌ | ❌ |
| `tinyfish_fetch` | ✅ | ❌ | ❌ | ❌ | ❌ |

说明：

- `write` 可以写新文件；`edit` 才是修改现有文件的关键权限。
- 联网检索默认只给 `explore`，避免实现 / 验收角色在没有必要时扩大外部依赖。
- `availableTools` 只解决“用户环境里有哪些工具可用”，不改变角色职责边界。

## 4. 角色在编排中的常见位置

| 任务形态 | 常见组织 |
|---|---|
| 只需要动手 | `solo(build)` |
| 先看代码再改 | `chain(explore → build)` |
| 改后需要验收 | `chain(explore → build → check)` 或 `build_check` |
| 多模块并行 | `team(build, build, build)`，必要时后接 `check` |
| 方案风险高 | `explore → design → build → check` |

这些不是固定流水线，planner 可以按目标选择最小够用组合。

## 5. 角色文件

角色 prompt 存在 `agents/*.md`：

| 文件 | 角色 |
|---|---|
| `agents/explore.md` | `explore` |
| `agents/design.md` | `design` |
| `agents/build.md` | `build` |
| `agents/check.md` | `check` |
| `agents/close.md` | `close` |

当前 frontmatter 主要作为说明和未来兼容；运行时权威配置仍在代码的 `ROLE_DEFAULTS`。

## 6. 修改角色的原则

1. 先确认是否真的需要改角色，而不是改 prompt 或 planner 规则。
2. 如果涉及工具权限，优先保护 `build` 唯一可写边界。
3. 不新增角色，除非已有 3 次真实任务证明 5 角色不够。
4. 改角色后必须同步更新：`agents/*.md`、`src/session/role-config.ts`、`src/types/role.ts`、planner 归一化和本文档。
