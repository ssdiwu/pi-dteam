# v0.5.0 轻量依赖图调度与运行态 UI 实施方案

> **版本归属**：0.5.0  
> **状态**：准备实施  
> **合并来源**：原 `40-Agent-Teams借鉴实施方案.md` + 原 `43-v0.5-可观测性与轻量协作实施方案.md`  
> **一句话目标**：让 dteam 具备最小 SwarmFlow / MiMo 式编排确定性：基于文件边界和轻量依赖图生成可解释 worker 批次，并一次性重做运行态 UI。

## 1. 目标排序

507 对 0.5.0 的目标排序是：

1. **C**：最小 SwarmFlow / MiMo 式编排确定性
2. **A**：多 worker 协作可见、可解释、可控
3. **B**：知道什么时候该并行，什么时候该避让

因此 0.5.0 不是单纯 UI 小修，也不是重型流水线，而是：

> **轻量依赖图调度 + 运行态 UI 重做。**

## 2. 设计来源

| 来源 | 借鉴 | 不照搬 |
|---|---|---|
| SwarmFlow | 编排和智能分离：能确定的协作关系交给系统执行 | 不引入 `workflow.py`，不做通用 workflow 平台 |
| MiMo Code | 编排结构化、旁路 verifier / writer 思想 | 不做固定 6 阶段流水线，不做 Max Mode |
| rpiv-todo | 简洁任务树 UI、完成项保留、删除线弱化完成项 | 不集成 todo 工具，不引入 blockedBy 模型 |
| pi-subagents | async widget、grouped result、child safety、自然语言可用性 | 不开放自定义 agent / chain 文件体系 |
| Agent Teams | 文件边界、冲突预检、并行解释 | 不做 tmux、worktree、文件锁、自动 merge |

## 3. 非目标

0.5.0 不做：

- 固定 `review → TDD → verify → merge` 流水线
- workflow 脚本 API
- 自定义角色系统
- 文件锁
- Git worktree
- 自动 merge / rebase
- TypeScript compiler API / Babel AST 级别依赖分析
- 跨语言依赖图
- 持久化 `.dteam/sessions/`
- 恢复后台 `onUpdate`

## 4. 系统分层定义

Q8 中的“系统”必须明确：

> **系统 = dteam runtime（运行时）的确定性代码层，不是主 LLM，也不是 worker LLM。**

| 层 | 职责 | 是否 LLM |
|---|---|:---:|
| 主 LLM | 判断是否调用 dteam，提供 goal | ✅ |
| planner | 生成 `ExecutionPlan`，给出初始 `step.files` | ✅ + 规则 |
| dteam runtime | 补全文件边界、建依赖图、做 preflight、生成 batch | ❌ |
| worker | 执行具体 step | ✅ |
| UI / report | 展示状态、批次、冲突、延后原因 | ❌ |

0.5.0 的核心是把“编排确定性”下沉到 dteam runtime，而不是要求 leader agent 每轮临场记住。

## 5. 状态存储策略

0.5.0 采用三层状态：

| 状态 | 存放位置 | 说明 |
|---|---|---|
| 运行中热状态 | 内存：`activeRuns` / `uiStore` / `SignalBus` / `RunsStore` | 高频变化，不写 session |
| plan / fileGraph / scheduling checkpoint | `pi.appendEntry()` | 写入 Pi session，不进入 LLM context |
| 最终报告 | `dteam-report.details` | 用户展开回溯 dteam 做了什么、怎么调度 |

示例：

```ts
pi.appendEntry("dteam-scheduling", {
  runId,
  goal,
  plan,
  fileGraph,
  batches,
  conflicts,
  createdAt,
})
```

原则：

- 不自己写 `.dteam/sessions/`
- 不把高频 progress 写入 `appendEntry`
- 完成态 UI 快照保留在内存，直到下一次 dteam run 才清理

## 6. `PlanStep.files` 契约

`PlanStep.files` 表示该 step 预计会读 / 改的关键文件集合。

```ts
interface PlanStep {
  role: RoleName
  task: string
  strategy: Strategy
  files?: string[]
}
```

约定：

1. planner 尽量产出 `files`
2. `files` 可以不完整，但不能故意乱填
3. 缺失 `files` 不阻塞执行，标记为 unknown boundary
4. dteam runtime 会基于文件系统补全 import 依赖
5. `files` 不是文件锁，也不是精确写集

## 7. 轻量依赖图

0.5.0 的依赖图是轻量文本扫描，不做编译器级分析。

### 支持

| 能力 | 做法 |
|---|---|
| JS / TS import 图 | 正则扫描 `import` / `export from` / `require` |
| 相对路径解析 | `./x` / `../x` 解析到候选文件 |
| index 文件 | 支持 `dir/index.ts` / `dir/index.tsx` |
| shared files | `package.json` / lockfile / config / central index 标记高风险 |
| unknown | 无法解析则标记 unknown，不阻塞 |

### 不支持

| 不做 | 原因 |
|---|---|
| TypeScript compiler API | 太重 |
| Babel AST | 太重 |
| 跨语言依赖图 | 超出 0.5.0 |
| 动态 import 精准解析 | 首版不做 |
| monorepo package graph | 远期 |

## 8. 冲突分类

| 等级 | 条件 | 行为 |
|---|---|---|
| hard conflict | 两个 step 显式声明同一文件 | 自动拆批 |
| shared conflict | 涉及 `package.json` / lockfile / config / central index | 自动拆批 |
| dependency edge | A 文件被 B import | 按依赖方向拆批：被依赖方先，依赖方后 |
| unknown boundary | step 无 `files` 或无法解析 | 不阻塞，UI / report 标 unknown |
| no conflict | 无交集、无依赖 | 同批并行 |

依赖方向规则：

```text
auth.ts imports user.ts

user.ts = 被依赖方
 auth.ts = 依赖方

调度：改 user.ts 的 step 先跑；改 auth.ts 的 step 后跑。
```

## 9. batch 生成规则

输入：`ExecutionPlan.steps` + file graph。  
输出：`SchedulingPlan`。

```ts
interface SchedulingPlan {
  batches: Array<{
    index: number
    stepIndexes: number[]
    reason: string
  }>
  conflicts: Array<{
    type: "hard" | "shared" | "dependency" | "unknown"
    stepIndexes: number[]
    files?: string[]
    reason: string
  }>
}
```

规则：

1. `solo` / `chain` 不改组织语义，只补充 UI 信息
2. `team` 才做 preflight scheduling
3. 同批出现 hard/shared/dependency 冲突时，后者延后到后续 batch
4. unknown 不阻塞，但在 UI / report 中展示
5. batch 内仍并行，batch 间串行
6. 不把 plan 强制改写成 `chain`，只改变 team 的执行批次

## 10. UI 重做

当前 UI 的问题：

- 折叠态层级不清，running / done / failed 不明显
- 展开态 tab 过工程化，像 debug panel
- 输出太吵，信息密度不稳定
- 完成后直接清空，不利于回溯
- 缺少 batch / conflict / dependency 解释

0.5.0 一次性重做运行态 UI。

### 10.1 UI 总原则

要做：

- 单一清晰标题
- 稳定状态符号
- running 高亮
- done 删除线 + dim
- failed error
- delayed warning
- batch 和 dependency 原因可见
- 输出克制：widget 只显示 running 最新一行，expanded 每个 worker 最多 2 行
- 完成态保留，直到下一次 dteam run 才清理

不要做：

- 不要大块边框
- 不要每个 worker 一个 noisy tab
- 不要每个 worker 都显示长输出
- 不要过多 emoji
- 不要 debug panel 风格

### 10.2 运行态 widget

用途：run 进行中自动显示，尽量像 rpiv-todo 的任务树。

示例：

```text
● dteam [team] 2/5 · 01:24
├ ✓ explore  scan src/ui
├ ◐ build    panel shell        batch 1/3
│   ⎿ editing src/ui/panel.ts
├ ↳ build    status model       delayed: panel.ts conflict
├ ○ check    verify UI states
└ ○ close    summarize
────────────────────────────────────────
```

状态符号：

| 符号 | 状态 | 颜色 |
|---|---|---|
| `○` | pending | muted |
| `◐` | running | accent |
| `✓` | done | muted + 删除线 |
| `✕` | failed | error |
| `↳` | delayed | warning |
| `?` | unknown | muted / warning 视情况 |

### 10.3 `/dteam` 展开态

Q10 决策：**保留 tab**，避免不同内容全部堆在一起。  
但 tab 改成内容型 tab，不再是当前“每个 worker 一个 tab”。

建议 tabs：

| Tab | 内容 |
|---|---|
| `0 概览` | goal、mode、总进度、当前 batch、关键 warning |
| `1 批次` | batches、延后原因、dependency / conflict |
| `2 Workers` | worker 树、状态、files、最新输出 |
| `3 信号` | found / progress / help / blocked 聚合 |
| `4 报告` | 完成后 final summary；运行中显示待完成 |

展开态示例：

```text
● dteam [team] 2/5 · running · 01:24
[0 概览] [1 批次] [2 Workers] [3 信号] [4 报告]

Batch 1 · running
├ ✓ explore  src/ui, src/orchestrator
├ ◐ build    panel shell
│   files: src/ui/panel.ts, src/ui/store.ts
│   now: rendering compact worker tree
└ ↳ build    status model
    delayed: depends on src/ui/store.ts

/dteam N 切换 · /dteam close
```

### 10.4 完成态保留

完成后不立即清空 UI：

1. `uiStore.finishRun()` 后保留最后快照
2. widget 显示完成态摘要
3. `/dteam` 仍可展开查看上一轮 dteam 做了什么、怎么做的
4. 只有下一次 `dteam(action="run")` 开始时清理上一轮完成态

完成态示例：

```text
✓ dteam [team] 5/5 · done · 03:12
├ ✓ explore  scan src/ui
├ ✓ build    panel shell
├ ✓ build    scheduler preflight
├ ✓ check    tests passed
└ ✓ close    summary
────────────────────────────────────────
```

### 10.5 report

`dteam-report.details` 增加：

```ts
{
  runId,
  status,
  summary,
  mode,
  reason,
  plan,
  fileGraph,
  scheduling,
  steps: [{ role, status, strategy, task, files, output }]
}
```

折叠态：

```text
✓ dteam [team] · 5/5 完成 · 1 个冲突已避让
```

展开态：显示 batch、conflicts、steps。

## 11. 实施拆分

Q6 决策：可以多 commit，但每个 commit 只做一件事。

建议顺序：

1. **类型与状态**：扩展 `UIState` / `RunResult` / `StepResult` / `SchedulingPlan`
2. **file graph**：新增轻量 import scanner 和 shared file 配置
3. **preflight scheduling**：team 执行前生成 batches，支持自动拆批
4. **appendEntry checkpoint**：写入 plan / fileGraph / scheduling
5. **UI widget 重做**：运行态任务树
6. **/dteam tabs 重做**：概览 / 批次 / Workers / 信号 / 报告
7. **dteam-report 增强**：最终可回溯
8. **文档与示例**：README / API / changelog

## 12. 验收标准

### 自动验证

```bash
npm run build
npm test
```

至少覆盖：

- planner 能产出或保留 `files`
- file graph 能解析相对 import
- hard conflict 自动拆批
- shared conflict 自动拆批
- dependency edge 按方向拆批
- unknown boundary 不阻塞
- `SchedulingPlan` 写入 report details
- 完成后 UI 快照保留
- 下一次 run 开始清理上一轮完成态
- widget 状态符号和颜色策略稳定
- `/dteam` tabs 可切换

### 手动验证

1. 启动 `solo` 任务，确认 widget 清晰、完成后保留
2. 启动 `chain` 任务，确认步骤顺序和输出克制
3. 启动 `team` 任务，确认 batch 展示清楚
4. 两个 step 同改 `package.json`，确认后者延后且解释原因
5. `auth.ts imports user.ts`，两个 step 分别改 auth/user，确认 user 先、auth 后
6. run 完成后调用 `/dteam`，能回溯上一轮结果
7. 再启动下一次 run，上一轮完成态被清理

## 13. 风险与降级

| 风险 | 降级策略 |
|---|---|
| `files` 不准 | unknown 不阻塞；只对明确冲突拆批 |
| import scanner 漏判 | 保留 warning，不做强保证 |
| 自动拆批导致变慢 | UI / report 必须说明延后原因 |
| UI 信息过多 | widget 克制，详情放 `/dteam` tabs |
| appendEntry 过多 | 只写 plan / scheduling checkpoint，不写高频 progress |
| 依赖图复杂度膨胀 | 坚持文本扫描，不引入 AST / compiler API |

## 14. 版本结论

0.5.0 的成功标准：

> dteam 能在后台跑多个 worker；runtime 能基于轻量依赖图生成可解释 batch；UI 清楚展示谁在跑、谁被延后、为什么延后、做完后如何回溯；同时保持 dteam 轻量，不变成重型工作流平台。
