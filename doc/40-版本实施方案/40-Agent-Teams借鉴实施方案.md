# Agent Teams 借鉴实施方案

> **版本归属**：0.4.1 ~ 0.4.7 候选  
> **状态**：提案  
> **来源**：微信公众号文章《Agent Teams 全景: tmux + worktrees 跑 4 个 Claude 并行交付》  
> **结论**：**借任务拆分、冲突隔离、进度可视化；不照搬 `tmux`（终端复用器）和 `Git worktree`（Git 多工作副本）。**

## 一句话总结

`dteam`（多角色编排工具）已经有 `team`（并行模式），缺的不是“再多开几个 worker”，而是：

1. **开工前声明改哪些文件**
2. **并行前识别文件冲突并降级调度**
3. **把并行过程清楚展示出来**

本文把上面 3 件事拆成可实施的小步改动。

---

## 1. 当前现状

结合现有文档，当前状态是：

- 已有 `solo` / `chain` / `team` 三种组织形式，`team` 支持分批并行（每批 ≤ 3）
- `PlanStep.files`（步骤文件列表）字段**已存在**，但还没有真正参与调度
- 文档已明确：当前**不做依赖分析 + 文件锁**，并发冲突主要靠任务拆分避免
- UI 面板已存在，但正常聊天区还缺 `live summary`（实时摘要）

所以，`dteam` 当前已经具备“并行执行”能力，但还缺“并行前隔离”和“并行时可观测”。

---

## 2. 借鉴目标

### 2.1 要解决的问题

1. 两个 `build`（构建角色）步骤同时改同一文件，容易互相覆盖
2. 共享文件（如依赖清单、全局配置、中心路由、统一导出文件）没有唯一 owner（负责人）
3. 用户看不到每个 worker 正在改什么、是否撞文件、为什么被串行化

### 2.2 非目标

下面这些**不在本方案内**：

- 不引入 `tmux`（终端复用器）控制台
- 不给每个 worker 默认创建 `Git worktree`（Git 多工作副本）
- 不做 `Git merge`（Git 合并）自动化
- 不改成 `spawn`（子进程启动）型 `sub-agent`（子代理）架构
- 不做全量静态依赖分析、文件锁、原子提交

一句话：**只补轻量并行治理，不把 dteam 做成重型多进程系统。**

---

## 3. 设计原则

### 3.1 先声明，再并行

并行前，优先让每个 step 声明自己预计会读/改哪些文件；没有声明时，保留当前行为，但不给“无冲突保证”。

### 3.2 先预警，再自动降级

检测到重叠文件时，优先：

1. 发信号提示冲突
2. 自动把冲突步骤拆到不同批次
3. 只有在无法安全并行时，才从 `team` 降级成顺序执行

### 3.3 共享文件单 owner

像 `package.json`、锁文件、全局配置、中心路由、统一导出文件这类共享入口，默认只允许一个 step 负责。

### 3.4 不追求“绝对正确”

这是轻量预检，不是编译器级分析。允许漏判，但要尽量减少明显冲突。

---

## 4. 实施范围

| 范围 | 改动方向 | 目标 |
|------|----------|------|
| `src/planner.ts` | 产出更稳定的 `files` 元数据 | 让 step 有文件边界 |
| `src/orchestrator.ts` | 增加冲突预检和分批重排 | 避免同批撞文件 |
| `src/config.ts` | 增加共享文件模式配置 | 让单 owner 规则可维护 |
| `src/ui/store.ts` / `src/ui/panel.ts` | 展示文件边界、冲突、降级原因 | 提升可观测性 |
| dteam 工具结果摘要 | 输出并行计划和实时状态 | 聊天区可见 |
| `tests/` | planner / orchestrator / UI 相关测试 | 保证行为可验证 |

---

## 5. 分阶段实施

### Phase A（0.4.1 ~ 0.4.2）：文件声明落地

### 目标

让 `PlanStep.files` 从“占位字段”变成“真实输入”。

### 改动

1. 在 `src/planner.ts`（规划器）里补强 `files` 产出
   - `LLM`（大语言模型）路径：system prompt 明确要求每个 step 尽量给出 `files`
   - 规则路径：能推断时填最小文件集；推不出来就留空
2. 给 `build` 角色提示增加约束
   - 如果多个 step 会改共享文件，必须只让一个 step 持有该文件
3. 新增共享文件模式常量
   - 放在 `src/config.ts`
   - 初始只放少量高风险文件模式，不做复杂抽象

### 建议的共享文件模式（首版）

- `package.json`
- 锁文件（如 `package-lock.json`、`pnpm-lock.yaml`、`yarn.lock`）
- 仓库级配置（如 `tsconfig.json`、`.eslintrc*`、`vitest.config.*`）
- 中心注册文件（如 `index.ts`、路由总表、统一导出文件）

### 验收标准

- planner 单测覆盖：
  - 能产出 `files`
  - 缺失 `files` 时不报错
  - 共享文件不会被多个 step 同时声明
- 真实运行时，`RunResult.plan.steps[].files` 能出现在结果中

---

### Phase B（0.4.2 ~ 0.4.4）：冲突预检 + 分批重排

### 目标

在 `team`（并行模式）执行前，先做一次轻量冲突预检。

### 改动

1. 在 `src/orchestrator.ts` 增加 `preflight`（预检）步骤
   - 输入：`plan.steps`
   - 输出：可执行批次 + 冲突说明
2. 冲突判断规则（首版）
   - 两个 step 的 `files` 有交集 → 冲突
   - 任一步含共享文件模式 → 与其他声明同文件的 step 冲突
   - 任一步无 `files` → 不阻塞执行，但标记“未声明文件边界”
3. 调度策略（首版）
   - 无冲突：保留原批次并行
   - 有冲突：把冲突 step 自动拆到后续批次顺序执行
   - 如果所有 step 都互相冲突：整体等价于 `chain`（串行模式），但 plan 不强制改写
4. 发 `found`（发现信号）
   - 内容包括：冲突文件、受影响 step、调度调整结果

### 为什么不直接失败

因为当前目标是“尽量安全地继续跑”，不是“发现一点风险就停机等人”。

### 验收标准

- orchestrator 单测覆盖：
  - 无冲突时仍并行
  - 单个冲突时自动拆批
  - 全冲突时退化为顺序执行
  - `files` 缺失时给出提示但不阻塞
- `RunResult.signals` 里能看到冲突预警

---

### Phase C（0.4.4 ~ 0.4.5）：可观测性补齐

### 目标

让用户不仅知道“正在跑”，还知道“为什么这样跑”。

### 改动

1. `/dteam` 面板展示新增字段
   - 每个 step 的 `files`
   - 当前批次号
   - 是否因冲突被顺延
   - 最近一次冲突说明
2. 正常聊天区的 dteam 结果升级为 `live summary`（实时摘要）
   - 显示当前 mode（模式）
   - 显示批次进度
   - 显示最近冲突 / 阻塞 / help（求助）信号
3. 冲突调整后，在摘要中输出一句可读解释
   - 例如：
     - “检测到 `package.json` 冲突，已把依赖修改步骤延后到下一批次”

### 验收标准

- `/dteam` 面板能看到 step 文件边界和批次信息
- 正常聊天区能看到最新并行摘要，而不是只看最终结果
- 发生重排时，用户能读懂原因

---

### Phase D（0.4.5 ~ 0.4.7）：并行模板化

### 目标

把“先并行 build，再独立 check”的常见方法固化成 planner 倾向。

### 改动

1. 在 `src/planner.ts` 增加偏好规则
   - 改多个独立模块时：优先 `team + build_check`
   - 改共享入口时：优先单 owner + 其余步骤并行
   - 用户明确要求 review / verify / audit 时：优先追加 `check`（检查角色）步骤
2. 补一个面向用户的输出模板
   - “将按前端 / 后端 / 测试 / 文档分工并行执行”
   - “共享文件由 X step 独占负责”

### 验收标准

- planner 更稳定地产出带 `files` 的 `team` 计划
- 对“并行 + review”类目标，计划可读性明显提升

---

## 6. 数据与行为约束

### 6.1 `files` 字段语义

- `files` 表示“预计会读/改的关键文件集合”
- 不是完整文件清单
- 可以只列高风险文件
- 允许为空；为空表示“未知”，不是“不会改文件”

### 6.2 冲突处理优先级

```text
共享文件冲突 > 普通文件冲突 > 未声明文件边界
```

### 6.3 调度优先级

```text
保留并行 > 自动拆批 > 顺序退化
```

---

## 7. 测试计划

### 单元测试

- `tests/planner.test.ts`
  - `files` 产出
  - 共享文件单 owner
  - 无法推断时留空
- `tests/orchestrator.test.ts`
  - 冲突检测
  - 自动拆批
  - 顺序退化
  - 冲突信号输出
- `tests/ui/*`
  - 批次、文件边界、冲突提示展示

### 手动验证

至少验证 4 类任务：

1. 两个 step 改完全不同目录 → 应并行
2. 两个 step 都改 `package.json` → 应自动拆批
3. 一个 step 无 `files`，另一个有 → 可继续跑，但有提示
4. 前端 / 后端 / 测试三路并行 → UI 能看出每路分工和批次

### 完成判定

改完后必须运行：

```bash
npm run build
npm test
```

如涉及 Pi 侧展示，再补一次真实加载验证。

---

## 8. 风险与规避

| 风险 | 说明 | 规避 |
|------|------|------|
| `files` 不准确 | LLM 可能少报或误报 | 先只把 `files` 当“轻量提示”，不当硬锁 |
| 共享文件模式过多 | 误把很多任务串行化 | 首版只保留少量高风险模式 |
| UI 信息过载 | 面板太吵 | 默认只显示关键文件和最近一次冲突 |
| 规则过重 | 把轻量 dteam 做复杂 | 每 phase 独立上线，随时可停 |

---

## 9. 不做清单

为了防止范围膨胀，本方案明确不做：

- 不做文件锁
- 不做跨 worker 的 Git 分支管理
- 不做 `worktree` 级隔离
- 不做自动 merge / rebase
- 不做全量依赖图分析
- 不做“每个 worker 一个终端”的控制台方案

---

## 10. 推荐落地顺序

如果只做最小闭环，建议顺序是：

1. **Phase A：让 `files` 真的产出**
2. **Phase B：用 `files` 做冲突预检和拆批**
3. **Phase C：把冲突和批次展示出来**

做到这里，`dteam` 就已经吸收了 `Agent Teams`（多代理团队并行交付模式）最有价值的部分。

Phase D 可以视真实使用频率再做，不必抢在前面。

---

## 11. 预期收益

实施后，`dteam` 会从“能并行”升级到“**知道何时能并行、何时该避让、并且把原因讲清楚**”。

这比直接引入 `tmux` 或 `Git worktree` 更符合当前项目的轻量化定位。
