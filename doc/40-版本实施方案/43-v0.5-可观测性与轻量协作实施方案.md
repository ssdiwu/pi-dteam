# v0.5 可观测性与轻量并行治理实施方案

> **版本归属**：0.5.0 起步  
> **状态**：准备实施  
> **目标**：不引入固定流水线，不开放角色系统；先把多 worker 后台协作“看清楚、看得懂、能避开显式冲突”。

## 1. 背景

v0.4.1 已完成后台任务稳定性：`run` 立即返回 `runId`，后台执行，完成后 `dteam-report` 回到主对话。

SwarmFlow / MiMo Code 给 dteam 的核心启发不是“固定流水线”，而是：

> 把可确定的协作关系交给系统执行，把智能推理留给 worker。

因此 0.5.0 不应只做 UI，也不应直接做重型 workflow（工作流）。它应该补多 worker 系统最基础的协作确定性和用户体验：

1. 用户能看懂当前是 `solo` / `chain` / `team`
2. 用户能看懂每个 worker 是 pending / running / done / failed
3. 完成项不会瞬间消失，也不会永久堆积
4. 最终报告保留 worker 结构
5. `team` 模式能基于显式 `files` 做轻量冲突预检和自动拆批

参考来源：

- rpiv-todo：完成项保留到下一次 agent response 后消失
- pi-subagents：async widget / grouped result / natural language examples
- SwarmFlow：把“编排”和“智能”分开，确定的协作关系交给系统执行
- MiMo Code：把编排逻辑结构化；但不要把所有验证做成固定流水线

## 2. 范围

### 2.1 要做

| 项 | 文件 | 说明 |
|---|---|---|
| UI 4 状态规范 | `src/ui/store.ts` / `src/ui/panel.ts` | pending / running / done / failed |
| 完成项保留策略 | `src/ui/store.ts` / `index.ts` | run 完成后保留快照；下一次 response / 下一次 run 清理 |
| mode 标签 | `src/reporter.ts` 或 `src/ui/store.ts` / `panel.ts` | 展示 `[solo]` / `[chain]` / `[team]` |
| 轻量并行治理 | `src/planner.ts` / `src/orchestrator.ts` / `src/config.ts` | 展示 `files`，显式同文件冲突自动拆批；缺失 `files` 只标未知不阻塞 |
| report 分组增强 | `index.ts` message renderer | 最终 report 保留 plan mode、step 摘要、files / 冲突说明 |
| 文档使用示例 | `README.md` / `doc/12-API参考.md` | 写清“什么时候该调 dteam” |
| 测试 | `tests/ui-store.test.ts` / `tests/index-background-run.test.ts` / `tests/orchestrator.test.ts` | 覆盖保留 / 清理 / report / 冲突拆批 |

### 2.2 不做

- 不做固定 6 阶段流水线
- 不做 workflow 脚本
- 不加新角色
- 不加自定义 agent 配置
- 不加持久化 / resume
- 不复活后台 `onUpdate`
- 不做文件锁 / worktree / 自动 merge

## 3. 设计

### 3.1 UI 状态

当前内部状态有 `idle` / `running` / `done` / `failed` / `error` 等。面向用户统一显示：

| UI 状态 | 内部来源 |
|---|---|
| `pending` | `idle` 或未开始 |
| `running` | `running` |
| `done` | `done` |
| `failed` | `failed` / `error` |

### 3.2 完成项保留策略

当前完成后：

```ts
uiStore.reset()
ctx.ui.setWidget(WIDGET_KEY, undefined)
```

0.5 改为：

1. run 完成时 `finishRun()`，保留最后快照
2. widget 显示 “已完成 · 可展开查看”
3. 下一次 dteam run 开始时清理旧快照
4. 如果 Pi 能提供 agent response lifecycle（回复生命周期）事件，再加“下一次 agent response 开始时清理”
5. 没有 lifecycle 事件时，先用“下一次 run 开始清理 + 手动 `/dteam close`”作为最小实现

### 3.3 mode 标签

把 `ExecutionPlan.mode` 保存到 UI state：

```ts
interface UIState {
  goal: string
  mode?: "solo" | "chain" | "team"
  planReason?: string
  ...
}
```

展示：

```text
⚙ dteam [team] · 修复 UI · 00:12 · 2/3 完成
```

### 3.4 轻量并行治理

0.5.0 的并行治理只处理**显式文件边界**：

1. planner 尽量产出 `PlanStep.files`
2. `team` 执行前检查同批 step 的 `files` 交集
3. 如果两个 step 显式声明同一文件，把后者拆到后续批次
4. 如果某 step 没有 `files`，标记“文件边界未知”，但不阻塞执行
5. 只做少量共享文件模式配置（如 `package.json` / lockfile），不做全量依赖分析

这不是文件锁，也不是工作区隔离；它只是把明显冲突从“盲目并行”变成“可解释地延后”。

### 3.5 report 分组

`dteam-report` details 增加：

```ts
{
  runId,
  status,
  summary,
  mode,
  reason,
  steps: [{ role, status, strategy, task, files, output }],
  scheduling?: [{ stepIndex, batchIndex, delayedBecause? }]
}
```

折叠态：

```text
✓ dteam [chain] · 3/3 完成
```

展开态：显示 step task、strategy、files 和首行输出。

## 4. 实施顺序

1. 改 `UIState`：增加 `mode` / `planReason` / `finishedAt` 展示逻辑
2. 改 reporter：plan 生成后写入 mode / reason
3. 改 panel：折叠态 / 展开态展示 mode；完成状态不立即隐藏
4. 改 `orchestrator.ts`：team 执行前基于 `files` 做轻量预检和拆批
5. 改 `index.ts`：完成后不直接 reset；下一次 run 开始前清理旧 run
6. 改 `dteam-report` details 和 renderer
7. 补测试
8. 更新 README / API 文档

## 5. 验收标准

### 5.1 自动验证

```bash
npm run build
npm test
```

至少覆盖：

- run 完成后 UI 快照仍存在
- 下一次 run 开始前旧快照被清理
- mode 写入并渲染
- failed / error 都显示 failed
- `dteam-report` 展示 mode + step task
- team 显式同文件冲突时自动拆到后续批次
- step 缺失 `files` 时不阻塞，只在 UI / report 标记未知

### 5.2 手动验证

1. 启动一个 `solo` 任务，确认面板标题显示 `[solo]`
2. 启动一个 `chain` 任务，确认 step 顺序清楚
3. 启动一个 `team` 任务，确认并行 worker 不伪装成 chain
4. 任务完成后打开 `/dteam`，仍能看到最后结果
5. 再启动下一次 run，旧结果不堆积
6. 两个 team step 都声明 `package.json` 时，后者被延后并有说明

## 6. 风险

| 风险 | 处理 |
|---|---|
| 没有 agent response lifecycle 事件 | 先用下一次 run 清理，不强求 |
| UI 信息变多 | 默认折叠态只显示 mode + 总进度，详情放展开态 |
| 保留快照导致旧状态误导 | 完成态标题明确写“已完成”，下一次 run 自动清理 |
| `files` 不可靠 | 只相信显式声明；缺失不阻塞，只标未知 |
| 自动拆批改变执行速度 | 只对显式同文件冲突拆批，并在 UI/report 说明原因 |
| 改动波及 reporter / tests | 每步小提交，先 UI store，再 panel，再 preflight |

## 7. 非目标确认

0.5 的成功标准不是“变成 SwarmFlow / MiMo / pi-subagents”，而是：

> dteam 在 Pi 里后台跑多个 worker 时，用户能看清楚它在做什么，系统能避开显式冲突，做完后还能看见结果，并且不会把 UI 弄乱。
