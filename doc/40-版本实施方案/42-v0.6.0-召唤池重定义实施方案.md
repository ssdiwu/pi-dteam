# v0.6.0 召唤池重定义实施方案

> **版本归属**：0.6.0  
> **状态**：方向已定（文档重构已落地），代码实施待启动  
> **一句话目标**：把 dteam 从「`solo/chain/team` × `direct/build_check/adaptive` 的二维编排引擎」改回它本来的「基于 goal（目标）自发生长的多 worker 群策群力扩展」。

## 1. 背景

dteam 此前的实现是两条不相容血脉的合并：

- **原始召唤池构想**（`ant-colony` 启发）：5 个角色是可被按需召唤的专业角色池，任务从执行中长出来。
- **叠加的 `pi-subagents` 风格 chain**（预先穷举 step、按表执行）：把召唤池做成了固定流水线。

这产生了别扭的 `solo/chain/team` + planner 穷举 + 后台 `runId` 一整套。根因诊断：**dteam 漂离了它的召唤池本质**。

同时存在对照项目 [`pi-dgoal`](../../pi-dgoal)：它把「主代理单兵推进 + 独立审核」做得很顺。这迫使 dteam 重新回答「凭什么存在」——答案是**群策群力**：主 LLM 协调，按需召唤多个专业角色。

完整决策骨架见 [`../adr/0005-dteam-0.6.0-重定义为自发生长召唤池.md`](../adr/0005-dteam-0.6.0-重定义为自发生长召唤池.md)。

## 2. 核心定义（取代旧 0.6.0 Task Plan / Live Plan）

| 概念 | 0.6.0 定义 |
|---|---|
| dteam | 基于 goal 自发生长的多 worker 群策群力扩展 |
| Orchestrator（编排者） | 围绕单个 goal 持续读 Signal Store、LLM 驱动决定下一步召唤谁的主体（取代 ant-colony `queen`） |
| Orchestrator Loop（编排循环） | Orchestrator 反复执行的同步前台循环：读信息 → 判断 → 召唤 worker → 收结果/信号 → 继续/收口 |
| Worker（工作者） | 进程内 `AgentSession` 专业角色；通过 `session.subscribe` 实时写入 Signal Store |
| Logical Isolation（逻辑隔离） | `SessionManager.inMemory()` + 最小 ResourceLoader + 工具白名单 + 独立 system prompt；取代 OS 子进程隔离 |
| Signal Store（信号存储） | 单个 goal 的临时信号空间，TTL 衰减；取代 ant-colony `pheromone` |
| Completion Gate（收口闸门） | 每个 goal 必须召唤 `check` 才算完成；Orchestrator 不能自停 |

## 3. 旧概念对照（已被推翻）

| 旧概念（失效） | 新形态 |
|---|---|
| `dteam(action="run")` 立即返回 `runId`，后台运行 | 同步前台 Orchestrator Loop，阻塞直到收口 |
| `ExecutionPlan.mode: solo\|chain\|team` | 删除；无预先 plan，召唤轨迹即计划 |
| `PlanStep.strategy: direct\|build_check\|adaptive` | 删除；由 Orchestrator LLM 驱动每轮决策 |
| planner 穷举 / quick rule-based plan / LLM JSON fallback | LLM-Driven Orchestration（每轮一次 LLM 调用） |
| `SchedulingPlan` / `FileGraph` / preflight batches | 不再是编排主轴；文件依赖可作未来辅助 |
| Task Plan / DPlan Contract | 删除；无预先 Task Plan |
| `RunsStore` / 后台 `SignalBus` | 进程内 Signal Store（单 goal 生命周期，TTL 衰减） |
| 进程级 OS 子进程隔离 | 进程内 `AgentSession` + Logical Isolation |

## 4. 目标

0.6.0 要建立的新形态：

1. **Orchestrator Loop 主循环**：读 Signal Store 快照 → 一次 LLM 调用决定（召唤哪个/哪些角色、给什么任务、并发多少）→ 召唤 worker → `session.subscribe` 收结果与信号 → 写入 Signal Store → 继续或进入收口。
2. **进程内 worker**：每个 worker 是 `createAgentSession`，Logical Isolation 保证 fresh。
3. **Signal Store**：复用现有 `progress/found/blocked/help` 语义，TTL 衰减，单 goal 生命周期，不落项目目录。
4. **强制 check 收口**：Orchestrator 不能自停；goal 完成前必须召唤 `check` 通过。
5. **Adaptive Concurrency + Multi-Provider Routing**：可同时召唤多 worker，每角色可配主模型 + fallback 链，应对 429。
6. **启动方式 C 混合**：`/dteam <goal>` 显式启动 + 主 LLM 自动拉起。

## 5. 非目标

0.6.0 不做：

- 不开放用户手写 plan 文件（无预先 Task Plan）。
- 不做 workflow engine / 固定流水线 / Kanban。
- 不做 resume / 跨进程持久化（见 ADR 0004）。
- 不改变角色写死边界（见 ADR 0002）。
- 不做角色市场。
- **本轮（文档重构阶段）不动 `src/` 代码**——本文件只描述代码改造方向。

## 10. 风险与降级

| 风险 | 降级策略 |
|---|---|
| Orchestrator Loop 无限循环 | 强制 `check` 收口 + 最大轮次上限 |
| Signal Store 并发写冲突 | TTL 衰减 + 最新覆盖；必要时引入 quorum 合并（参考 ant-colony） |
| 多供应商 fallback 链解析失败 | 回落单供应商 + 降并发 |
| 放弃后台运行导致长任务阻塞主对话 | 长任务由主 LLM 拆成多次 dteam 调用，而非单次后台 run |
| Logical Isolation 不够「fresh」 | 最小 ResourceLoader 严格化；必要时关键角色回退子进程 |

## 11. 版本结论

0.6.0 的成功标准：

> dteam 接到 goal 后，进入同步前台 Orchestrator Loop；Orchestrator 持续读 Signal Store，LLM 驱动按需召唤五角色之一，worker 以进程内 `AgentSession` 隔离执行，最终经 `check` 收口。dteam 不再像「后台跑的二维编排引擎」，而像「主 LLM 群策群力的召唤池」。
