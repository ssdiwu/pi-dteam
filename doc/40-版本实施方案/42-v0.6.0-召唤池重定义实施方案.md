## 1. 背景：为什么要重基线

0.6.0 的骨架方向没有变，权威仍是 [ADR 0005](../adr/0005-dteam-0.6.0-重定义为自发生长召唤池.md)：

- dteam = 基于 goal（目标）自发生长的多 worker 群策群力扩展
- 同步前台 `Orchestrator Loop`（编排循环）
- 进程内 `AgentSession` worker + Logical Isolation（逻辑隔离）
- `Signal Store`（信号存储，TTL 衰减）
- 强制 `check` 收口（Completion Gate）

这次重基线的原因不是方向错了，而是**实现状态和文档状态脱节**：

- 新骨架代码已经落地到一半以上
- 旧层桥接残留还没清干净
- 多份 README / 实施文档仍在说旧话
- 本文件旧版把许多阶段直接标成 ✅，甚至把 `build + test` 写成已通过，但实际此前并未核验

**2026-06-19 已重新核验**：

- `npm run build` ✅ 通过
- `npm test` ✅ 通过（8 个测试文件，140 个测试）

因此，本文件不再假装“0.6.0 全部完成”，而是基于**今天的真实代码状态**重新划分：

- A. 已落地
- B. 桥接残留
- C. 文档漂移
- D. 待端到端验证

## 2. 0.6.0 当前权威口径

在收尾前，先把 0.6.0 的不变量钉死：

1. **无预先 Task Plan**：召唤轨迹即计划
2. **同步前台执行**：不返回 `runId`，不后台运行
3. **固定五角色**：`explore / design / build / check / close`
4. **强制 `check` 收口**：Orchestrator 不能自停
5. **Signal Store 是单 goal 临时协调面**：TTL 衰减，不做跨 goal 持久 inbox
6. **用户感知粒度**：开启 dteam → 完成工作 → 验收工作；worker 内部工具轮次属于黑箱（见 `doc/术语表.md` 的 `Live Loop View`）

> 外部参考（如 `swarm-ide`）只提供启发，不构成 0.6.0 实施项。相关调研见 [`../20-能力参考/25-swarm-ide蜂群IM编排参考.md`](../20-能力参考/25-swarm-ide蜂群IM编排参考.md)。

`build + test` 绿了，不等于 0.6.0 真跑通。当前仍缺**真实 Pi 环境、真实模型、真实 `/dteam <goal>`** 的端到端验证。

| 待验证项 | 验证方式 | 通过标准 |
|---|---|---|
| `/dteam <goal>` 能启动同步前台 loop | 在有 API key 的 Pi 环境执行 | 进入 loop，而非返回旧 runId 形态 |
| Orchestrator 能按信号继续下一轮 | 用一个会触发多轮召唤的小 goal | 看到 summonTrail 增长、check 收口发生 |

| UI 最小展示可用 | `/dteam` 面板 / widget | 至少能看 worker、signals、收口完成 |
