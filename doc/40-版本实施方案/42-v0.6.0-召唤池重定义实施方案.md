## 1. 背景：为什么要重基线

0.6.0 的骨架方向没有变，权威仍是 [ADR 0005](../决策档案/0005-dteam-0.6.0-重定义为自发生长召唤池.md)：

- dteam = 基于 goal（目标）自发生长的多 worker 群策群力扩展
- 同步前台 `Orchestrator Loop`（编排循环）
- 进程内 `AgentSession` worker + Logical Isolation（逻辑隔离）
- `Signal Store`（信号存储，TTL 衰减）
- 强制 `check` 收口（Completion Gate）

这次重基线的原因不是方向错了，而是**实现状态和文档状态脱节**：

- 新骨架代码已经落地到一半以上
- 旧层桥接残留还没清干净
- 多份 README / 实施文档仍在说旧话
- 本文件旧版把许多阶段直接标成 ✅，甚至把 `build + test` 写成已通过，但实际此前并未核验

**2026-06-19 已重新核验**：

- `npm run build` ✅ 通过
- `npm test` ✅ 通过（8 个测试文件，140 个测试）

因此，本文件不再假装“0.6.0 全部完成”，而是基于**今天的真实代码状态**重新划分：

- A. 已落地
- B. 桥接残留
- C. 文档漂移
- D. 待端到端验证

## 2. 0.6.0 当前权威口径

在收尾前，先把 0.6.0 的不变量钉死：

1. **无预先 Task Plan**：召唤轨迹即计划
2. **同步前台执行**：不返回 `runId`，不后台运行
3. **固定五角色**：`explore / design / build / check / close`
4. **强制 `check` 收口**：Orchestrator 不能自停
5. **Signal Store 是单 goal 临时协调面**：TTL 衰减，不做跨 goal 持久 inbox
6. **用户感知粒度**：开启 dteam → 完成工作 → 验收工作；worker 内部工具轮次属于黑箱（见 `doc/术语表.md` 的 `Live Loop View`）

> 外部参考（如 `swarm-ide`）只提供启发，不构成 0.6.0 实施项。相关调研见 [`../20-能力参考/25-swarm-ide蜂群IM编排参考.md`](../20-能力参考/25-swarm-ide蜂群IM编排参考.md)。

## 4. B. 桥接残留

这是当前 0.6.0 最真实、也最该说清楚的部分：**新骨架已经写出来，但旧层桥接还挂着。**

| 残留 | 现状 | 含义 | 收尾完成的标准 |
|---|---|---|---|
| `src/leaf.ts` 内仍使用 `dteam.runsStore / dteam.runId / dteam.currentStepId` | 新 worker 执行层仍桥接旧 run 语义 | 说明 0.6.0 主循环已落地，但 leaf 还没完全脱离 0.5.0 运行态 | 要么删桥接，要么明确把它们降级为兼容层，并把命名 / README 说清楚 |
| `src/signals/runs-store.ts` | 文件仍在 | 旧 run-based 运行态仍存活 | 明确是否保留为桥接层；若保留，README 不再把它写成 0.6.0 主轴 |
| `src/signals/signal-bus.ts` | 文件仍在 | worker_sendSignal → 根处理的旧通路仍参与桥接 | 明确其在 0.6.0 中的角色（桥接 / 兼容），而不是继续暗示“后台协作主通路” |
| `src/ui/store.ts` / `src/ui/panel.ts` | 代码是 0.6.0 最小 worker 展示 | UI 已切骨架，但还不是完整“Loop 推进 + Signal Store 快照”展示 | 是否进一步增强，留待真实痛点决定；当前只要求文档如实描述“最小版” |

### B 档收尾原则

B 档不是“全部删除旧代码”，而是**先把语义说真**：

- 哪些是 0.6.0 主轴
- 哪些只是桥接层
- 哪些名字还沿用旧 run 语义但已非主轴

只有在说真之后，才决定删还是留。
