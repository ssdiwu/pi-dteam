# v0.4.1 后台任务稳定性实施方案

> **版本归属**：0.4.1  
> **状态**：已实施  
> **触发原因**：后台运行 dteam 时出现 `Agent listener invoked outside active run`，Pi 因 `uncaughtException`（未捕获异常）闪退。  
> **结论**：**v0.4.1 先把 dteam 收敛成稳定的后台任务系统：启动只返回 `runId`，运行态只走面板 / widget / 状态栏，完成后再发结果消息。**

## 一句话总结

`dteam(action="run")` 一旦选择“立即返回 `runId`（任务编号）”，就不应继续使用 `onUpdate`（流式更新回调）推送后台进度。v0.4.1 的核心是把“启动通道”和“运行态展示通道”彻底拆开。

---

## 1. 问题定义

### 1.1 当前症状

后台运行时，Pi 退出并打印：

```text
Error: Agent listener invoked outside active run
```

### 1.2 根因

当前实现同时做了两件互相冲突的事：

1. dteam 工具在前台**立即返回** `runId`
2. 返回后，后台执行过程还在继续调用这次工具执行的 `onUpdate`

而 `onUpdate` 只在**当前工具调用仍处于活跃执行期**时才合法。工具已经返回后，再继续用它发局部更新，就会越界。

### 1.3 产品层面的解释

这不是“后台任务不能更新进度”，而是“后台任务不能再借用已经结束的前台工具调用通道更新进度”。

---

## 2. v0.4.1 的目标

### 2.1 版本目标

把 dteam 明确收敛成一个**后台任务系统**，而不是一个“长时间占住当前工具调用的流式工具”。

### 2.2 具体目标

1. `run` 启动后立即返回 `runId`
2. 后台继续执行，不阻塞主对话
3. 用户仍可通过 `/dteam` 面板观察进度
4. 任务完成后，主对话收到新的完成消息
5. 需要人工补充信息时，进入 `continue`（继续执行）流程
6. 不再因为后台进度更新导致 Pi 闪退

---

## 3. 本版本的设计决策

### 3.1 选择后台任务模式，不选择流式工具模式

v0.4.1 明确选择：

- **要**：后台运行 + 立即返回 + 面板观察 + 最终通知
- **不要**：立即返回后仍沿用 `onUpdate` 推送实时进度

### 3.2 保留工具动态加载方案 D

`41-工具动态加载方案.md` 已确定：由主 LLM 在调用 dteam 时显式传 `availableTools`（可用工具列表）。

v0.4.1 **不推翻**这个方向，继续沿用：

- `availableTools` 参数保留
- planner / orchestrator / leaf 的透传链路保留
- 不回退到文件系统扫描已加载扩展

### 3.3 Agent Teams 式并行治理延期

`40-Agent-Teams借鉴实施方案.md` 里的这些内容不在 v0.4.1 范围内：

- `PlanStep.files`（步骤文件列表）落地
- 并行前冲突预检
- 自动拆批 / 顺序退化
- 聊天区并行 `live summary`（实时摘要）

这些延期到 **0.4.2+**。

### 3.4 Pi 新版兼容增强延期

`20-Pi版本兼容性与影响分析.md` 中的 `project_trust`（项目信任）等体验增强项，不是本次 blocker（阻塞点），延期到 **0.5+** 评估。

## 4. v0.4.1 的产品行为模型

### 4.1 启动阶段

用户调用：

```text
dteam(action="run", goal="...")
```

系统行为：

1. 创建 run context（运行上下文）
2. 分配 `runId`
3. 把任务放入后台执行
4. 立即返回：

```json
{ "status": "running", "runId": "run-xxx" }
```

### 4.2 运行阶段

后台执行时：

- 不再向这次工具调用发送 `onUpdate`
- 进度只更新到：
  - `/dteam` 面板
  - widget（小组件）
  - `status`（状态栏）
  - `notify`（通知）

### 4.3 人工介入阶段

当 worker 缺信息或发出 `help`（求助）时：

1. run 进入等待状态
2. UI 明确提示用户需要补充什么
3. 用户调用：

```text
dteam(action="continue", runId="...", message="...")
```

4. 后台任务恢复执行

### 4.4 完成阶段

后台任务结束后：

- 发送一条新的完成消息到主对话
- 消息包含：
  - `runId`
  - 总体状态
  - 摘要
  - step 结果摘要

这里的结果通知是**新的消息**，不是旧工具调用的续写。

## 5. 模块职责调整

## 5.1 `index.ts`

作为 dteam 生命周期外壳，只负责：

1. `run`：接任务、创建 run、立即返回 `runId`
2. `continue`：给等待中的 worker 注入用户补充信息
3. 后台执行完成后发送最终结果消息
4. 管理 `activeRuns`

### 本版本对 `index.ts` 的要求

- 后台执行链路**停止依赖 `onUpdate`**
- `createLiveBroadcaster` / 类似逻辑如果仍保留，也不能在工具返回后继续调用 `onUpdate`
- `/dteam` 面板刷新、状态栏刷新、widget 刷新仍可保留

## 5.2 `src/orchestrator.ts`

继续负责：

- `plan → execute → report`
- `solo / chain / team` 调度
- `direct / build_check / adaptive` 策略执行

### 本版本原则

- **不改**核心编排语义
- **不在本轮接入**文件冲突预检
- 只保持和 reporter（汇报器）的边界清晰

## 5.3 `src/reporter.ts`

继续作为业务事件到展示事件的桥：

- startRun
- addWorker
- updateWorker
- addSignal
- addStrategy
- finishRun

### 本版本原则

reporter 可以继续驱动 UI，但**不能再依赖已结束工具调用的流式回调**。

## 5.4 `src/ui/store.ts` + `src/ui/panel.ts`

继续承担“观察层”：

- 存当前 run 快照
- 展示 worker 树、信号、最近输出
- 展示执行进度

### 本版本原则

实时过程主要看 `/dteam` 面板，不强求主对话同步显示完整反馈流。

## 6. 实施范围

### 6.1 本版本要做

1. **去掉后台 run 对 `onUpdate` 的依赖**
2. 保留 `/dteam` 面板、widget、状态栏、通知的实时更新
3. 保留最终 `dteam-report`（结果报告）消息
4. 保留 `availableTools` 方案 D
5. 让人工介入继续走 `continue`
6. 补文档，明确 dteam 的后台任务模型

### 6.2 本版本不做

1. 不做聊天区实时 `live summary`
2. 不做文件边界 / 冲突预检 / 自动拆批
3. 不做 `project_trust` 自动化
4. 不做持久化 / resume
5. 不做进程级隔离

---

## 7. 验收标准

### 7.1 功能验收

1. 调用 `dteam(action="run", goal="...")` 后，立即返回 `runId`
2. 后台执行过程中，Pi 不再因 `Agent listener invoked outside active run` 闪退
3. `/dteam` 面板可继续看到 worker 进度
4. 任务完成后，主对话收到 `dteam-report`
5. 人工补充信息后，`continue` 可恢复执行

### 7.2 回归验收

至少手动验证 3 类场景：

1. **普通后台任务**：启动 → 面板可见 → 完成消息正常
2. **需要人工补充**：启动 → 等待输入 → `continue` 恢复
3. **team 模式任务**：并行执行仍可观察，不崩溃

### 7.3 工程验证

改完后必须运行：

```bash
npm run build
```

如涉及测试快照或行为变更，再运行：

```bash
npm test
```

## 8. 风险与取舍

| 取舍 | 说明 |
|---|---|
| 聊天区暂时失去实时流 | 这是为换取后台模型稳定性；实时过程改由 `/dteam` 面板承载 |
| `onUpdate` 能力被收缩 | 属于有意识收敛，不是能力倒退 |
| UI 与主对话展示不完全一致 | v0.4.1 接受这种不一致；后续再评估安全的异步摘要方案 |

## 11. 版本结论

v0.4.1 不追求“更炫的实时反馈”，只追求一件事：

> **让 dteam 的后台运行模型先稳定下来，做到“能启动、能观察、能暂停、能恢复、能完成、不会闪退”。**
