# 调试循环

> 核心心智：**有没有一个快速、确定性、agent 能跑的 pass/fail 信号，决定能不能找到 bug。** 这个信号就是反馈环——它就是调试本身，其余都是机械操作。有环，bug 已修了 90%。

## 六阶段

1. **建反馈环**（投入不成比例的精力——这步就是技能本身）
2. **复现**（跑环，确认是用户描述的那个 bug）
3. **假设**（一次性生成 3-5 个排序、可证伪假设）
4. **插桩**（每个探针对应一个假设，一次改一个变量）
5. **修 + 回归**（先写回归测试，仅当有正确接缝）
6. **清理 + 复盘**（删插桩、写明胜出假设、问"什么能预防"）

跳过任何阶段必须显式说明理由。

## Phase 1 · 建反馈环的 10 种手段（按顺序试）

1. **失败测试**——任何能触及 bug 的接缝：单元 / 集成 / e2e。
2. **curl / HTTP 脚本**——打运行中的 dev server。
3. **CLI + fixture**——带固定输入，stdout diff 已知正确的快照。
4. **Headless 浏览器脚本**（Playwright / Puppeteer）——驱动 UI，断言 DOM/console/network。
5. **重放捕获的 trace**——把真实网络请求 / payload / 事件日志存盘，在隔离中重放。
6. **Throwaway harness**——起系统最小子集（一个服务，依赖 mock），单函数调用走通 bug 路径。
7. **Property / fuzz loop**——bug 是"有时输出错"，跑 1000 个随机输入找失败模式。
8. **Bisection harness**——bug 出现在两个已知状态间（commit/数据集/版本），自动化"起状态 X、检查、重复"让 `git bisect run` 跑。
9. **差分环**——同样输入过旧版本 vs 新版本（或两配置），diff 输出。
10. **HITL bash 脚本**——最后手段，必须人工点击时，用 `hitl-loop.template.sh` 结构化驱动，捕获输出回传。

### 把环当产品迭代

有了一个环后继续问：

- 能更快吗？（缓存 setup、跳无关初始化、缩窄测试范围）
- 信号能更准吗？（断言具体症状，而非"没崩"）
- 能更确定性吗？（固定时间、seed RNG、隔离文件系统、冻结网络）

**30 秒的 flaky 环≈没环；2 秒的确定性环是调试超能力。**

### 非确定性 bug

目标不是干净复现，而是**更高复现率**。loop 触发 100 次、并行、加压、缩窄时间窗、注入 sleep。50% flaky 可调试，1% 不行——持续拉高直到可调试。

### 真的建不出环时

明确停下，列出试过的方法，向用户要：(a) 复现环境访问权 (b) 捕获产物（HAR、日志 dump、core dump、带时间戳录屏）(c) 允许加临时生产插桩。**没有环就不要进入 Phase 2 空猜。**

## Phase 3 · 可证伪假设格式

一次性生成 3-5 个排序假设（单假设会锚定第一个貌似合理的想法）。每个必须可证伪：

> 若 `<X>` 是原因，则 `<改 Y>` 会让 bug 消失 / `<改 Z>` 会让它更严重。

说不出预测的假设是 vibe（凭感觉），扔掉或锐化。把排序假设给用户看一眼——领域知识常瞬间重排（"我们刚部署了 #3 的改动"），或用户知道已排除的假设。用户 AFK 就用自己的排序继续。

## Phase 4 · 插桩纪律

- 每个探针对应 Phase 3 的一个具体预测，**一次只改一个变量**。
- 工具优先级：debugger/REPL 断点（一个断点胜过十条日志）> 边界定向日志 > 永远别"全打日志再 grep"。
- **每条 debug 日志打唯一 tag**，如 `[DEBUG-a4f2]`。清理变成一个 grep。未打 tag 的日志会残留，打 tag 的必死。
- **性能回归分支**：日志通常没用。先建基线测量（计时 harness、`performance.now()`、profiler、query plan），再 bisect。先量，后修。

## Phase 5 · 接缝信号

回归测试**先写**（红），但**仅当存在正确接缝**：测试在真实 bug 模式发生的调用点。若唯一可用的接缝太浅（单调用者测试而 bug 需多调用者、单元测试复现不了触发链），那里的回归测试给的是假信心。

**若没有正确接缝，这本身就是发现**——架构阻止了 bug 被锁定。记下来，交 `architecture-designer`。

## 好的证据

- 精确的失败命令 / 复现脚本
- 最小复现步骤
- 缩小到文件或子系统
- 与假设关联的 tag 日志或追踪
- 胜出假设的明确陈述

## 避免

- 没有反馈环就盯着代码看
- 定位前就修改多个区域
- 未确认根因就"修复"
- 在活跃调试期间做大规模重构
- 未打 tag 的 debug 日志（会残留）
