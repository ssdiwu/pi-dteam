# 主代理决策式逐级升级与超时恢复

> **状态：✅ 有效，已实施**
>
> **更新**：ADR 0008 的跨档路由规则收敛为同档候选可用性回退与主代理相邻升级；更新 ADR 0009 的 worker 生命周期，使 timeout 在当前 Pi 会话内可由主代理决策恢复。
>
> **不改变**：主代理仍是唯一路由 owner；不恢复 Orchestrator Loop、batch、依赖图、P2P、跨进程 resume 或默认持久化。

## 决定

1. **先并行 T3，再由主代理汇总决定下一轮。** T3 用于独立事实搜集和机械验证；主代理综合多个结果后，才决定自己处理、继续派 T3，或派发 T2。
2. **跨档只能逐级且必须由主代理显式决定。** 路径为 `T3 → T2 → T1`；Worker Manager 不得因报错、无输出或 timeout 自动从 T3/T2 跳到 T1。
3. **同档模型候选可以自动回退。** 同一 tier 的 `provider/model[:thinking]` 候选链仍由 Manager 为可用性问题顺序尝试。
4. **默认每次 worker attempt 预算为 5 分钟。** 内部计时使用毫秒；对用户和主代理的文案使用 `s` 或 `mXs`。同一 worker 的 timeout recovery 在当前会话内另有累计上限（默认 10 分钟），用于允许一次 fresh retry 或相邻升级；该上限不是首次 attempt 的用户预算。
5. **timeout 先形成结构化恢复请求，而不是直接终态。** 该请求包含当前 attempt 预算、recovery 累计上限、经过时间、最后活动、当前工具、裁剪输出摘要和 attempt 元数据；当前工具面由主代理通过 `dteam_recover` 选择同档 fresh retry、相邻升级、有限延长或停止（原单工具形态已被 ADR 0013 更新）。
6. **恢复重建 fresh session，不恢复旧 session。** 只向新 worker 传入有长度上限且经过常见密钥模式脱敏的结构化恢复摘要；禁止注入完整 `session.messages`、无界工具输出或未脱敏的敏感内容。

## 原因与取舍

旧的 `T3/T2 → T1` 自动回退跳过了 T2，也让 Worker Manager 替主代理做了下一轮路由决定；这与 dteam 的“主代理思考、路由、综合和验收，T3 批量执行”的定位冲突。timeout 直接失败则丢失已经产生的过程信息，无法让主代理决定是否继续投入成本。

新规则保留同档候选自动切换，避免把 provider 故障暴露给主代理；但跨档提升和 timeout 恢复必须由拥有任务上下文的主代理决定。代价是多一次 parent response 和恢复状态管理，换来可解释的成本控制、逐级使用模型和避免副作用任务的盲目重试。

## 边界

- 不自动续派；主代理收到完成、阻塞或 timeout 恢复请求后自行决定是否发起下一轮 `dispatch`。
- 不把 timeout 变成跨 reload/进程的 resume；reload 和 shutdown 仍中止活跃 worker。
- 不解析自由文本来识别恢复动作；所有恢复 action 使用 `respond` 的有类型 schema 并 fail-closed。
- retry 与 extend 必须有每 worker 的次数和预算上限；未经主代理回应不得自动重试。
- `/dteam` 只展示有界实时文本、thinking 与工具活动；过程流不以 `display:true` 原样重复进入主对话。
