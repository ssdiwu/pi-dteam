# 显式依赖等待原语

> **状态：✅ 已实施**
>
> **更新**：更新 ADR 0013 的“三工具”公开面。保留其派发、普通回应、超时恢复的职责拆分；新增显式等待原语，不恢复轮询、状态查询、依赖图或自动编排。
>
> **2026-07-17 实施校准**：parent event 先进入 Manager 待消费队列。`dteam_wait` 即使晚于事件发生也会消费对应待回放项，并在 `events` 返回实际事件；只有主代理 idle / settled 后仍未消费的事件才进入 follow-up，保证一个 wait 与一次异步回放二选一。终态 Snapshot 不作为新的可消费事件。
>
> **2026-07-19 补充**：无 `writeScope` 且没有 assistant 文本和 `WorkerReport` 的失败保留为仅 wait 可消费事件，并继续投影到 Signal Log 与 `/dteam`；它不进入 follow-up。可写中断、timeout recovery 请求及其他失败仍按原规则回放。
>
> **2026-08-08 语义校准**：迟到 wait 一次消费全部匹配的已排队事件；`pendingWorkerIds` 只表示本轮未进入 `ready`，不代表仍在运行或必须继续等待。dteam 借鉴 Pi `EventStream` 的 queue / waiter 模式但不直接引入，选择器、delivery、合并与取消清理的差异及重评条件见 ADR 0024。

在本 ADR 的 2026-07-17 决策时点，`dteam_wait` 是在三项公开能力上新增的第四项；当前公开面已由 ADR 0024 扩展为五工具：

```ts
dteam_wait({ workerIds, timeoutMs })
```

它只在主模型已判断后续工作依赖指定 worker 时调用；普通独立并行仍使用 `dteam_dispatch` 的异步 follow-up（后续回传），不默认等待。`workerIds` 可指定多个 worker，但 dteam 不保存依赖关系、batch、Plan 或 dgoal task 映射。

一次 wait 注册为指定 worker 的事件消费者。调用时若已有匹配 parent event 排队，会一次返回并删除全部匹配事件；否则任一目标 worker 产生 finding、request 或终态事件时立即返回。`reason="worker_event"` 时，`ready` 只包含本次事件涉及的 worker 快照；`reason="timeout"` 时，`ready` 包含当时 waiting 或终态的目标 worker。`pendingWorkerIds` 只是本轮未进入 `ready` 的目标 ID，不是运行态判断，也不能被机械复制为下一次 wait 的目标。

匹配 wait 的事件只作为 `dteam_wait` 结果交给主模型，不重复投递同一 follow-up；Signal Log 和 `/dteam` 仍保留完整可观察记录。工具结果默认只渲染紧凑等待摘要（目标、本轮返回、本轮无事件与返回原因）；完整 event、worker snapshot、report、request 和本轮无事件列表只在 `Ctrl+O` 展开时显示，模型上下文始终保留完整结构。`timeoutMs` 只结束本次等待并返回部分 snapshot，不取消 worker、不触发 timeout recovery、不自动派发后续 worker。等待到 `waiting` 时，主模型必须先调用 `dteam_respond` 或 `dteam_recover`，再按真实依赖决定是否继续 wait，避免死锁。

可写 worker 的关联 dgoal / Task Plan 不得在其未终态时收口。若 `dteam_wait` 返回 `write_interrupted`，仍按 ADR 0017 派 fresh T3 检查 writeScope；wait 是显式同步点，不替代写入中断完整性守卫。

实际会话中，主模型因缺少此原语只能用 Bash sleep（命令行等待）、猜测状态或过早 fresh dispatch：导致迟到 worker 与重派 worker 重叠；可写 worker 则可能在父目标收口后的 session shutdown 中留下半写入。显式、一次性的 event wait 保留主模型路由所有权，同时不给 Worker Manager 引入自动依赖调度。
