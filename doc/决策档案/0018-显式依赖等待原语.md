# 显式依赖等待原语

> **状态：已实施
>
> **更新**：更新 ADR 0013 的“三工具”公开面。保留其派发、普通回应、超时恢复的职责拆分；新增显式等待原语，不恢复轮询、状态查询、依赖图或自动编排。

下一主版本新增第四个模型工具：

```ts
dteam_wait({ workerIds, timeoutMs })
```

它只在主模型已判断后续工作依赖指定 worker 时调用；普通独立并行仍使用 `dteam_dispatch` 的异步 follow-up（后续回传），不默认等待。`workerIds` 可指定多个 worker，但 dteam 不保存依赖关系、batch、Plan 或 dgoal task 映射。

一次 wait 注册为指定 worker 的事件消费者。任一目标 worker 进入 `completed`、`failed`、`timed_out`、`cancelled`、`shutdown`，或进入需要主模型处理的 `waiting` 时，wait 立即返回已就绪 worker 的结构化结果 / report / request，以及仍可等待的 `pendingWorkerIds`。它不等全部 worker 结束，避免主模型在部分结果已可驱动下一步时卡住；若仍需其余结果，主模型以剩余 ID 显式再次 wait。

匹配 wait 的事件只作为 `dteam_wait` 结果交给主模型，不重复投递同一 follow-up；Signal Log 和 `/dteam` 仍保留完整可观察记录。工具结果默认只渲染紧凑等待摘要（目标数、已就绪数、仍等待数与返回原因）；完整 worker snapshot、report、request 和 pending 列表只在 `Ctrl+O` 展开时显示，模型上下文始终保留完整结构。`timeoutMs` 只结束本次等待并返回部分 snapshot，不取消 worker、不触发 timeout recovery、不自动派发后续 worker。等待到 `waiting` 时，主模型必须先调用 `dteam_respond` 或 `dteam_recover`，再按需要继续 wait，避免 worker 等主模型而主模型又等待 worker 的死锁。

可写 worker 的关联 dgoal / Task Plan 不得在其未终态时收口。若 `dteam_wait` 返回 `write_interrupted`，仍按 ADR 0017 派 fresh T3 检查 writeScope；wait 是显式同步点，不替代写入中断完整性守卫。

实际会话中，主模型因缺少此原语只能用 Bash sleep（命令行等待）、猜测状态或过早 fresh dispatch：导致迟到 worker 与重派 worker 重叠；可写 worker 则可能在父目标收口后的 session shutdown 中留下半写入。显式、一次性的 event wait 保留主模型路由所有权，同时不给 Worker Manager 引入自动依赖调度。
