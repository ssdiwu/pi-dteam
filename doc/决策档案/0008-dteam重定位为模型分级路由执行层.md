# dteam 重定位为模型分级路由执行层

> **状态：✅ 有效（当前定位权威）**
> **推翻**：[ADR 0006](./0006-dteam重定位为对抗式合议.md)（对抗式合议）+ [ADR 0007](./0007-对抗回合结构与积分制.md)（对抗回合结构与积分制）——经原型验证"繁琐且无用"（积分制成本与收益不成正比，git `78e03a7`）。
> **保留有效**：0001（有立场替代层）、0002 精神（角色收敛）、0004（不做 resume）。0005 的执行基底（进程内 `AgentSession` + Logical Isolation、Multi-Provider Routing、Adaptive Concurrency）保留并承载新定位；0005 的 Signal Store 与 Orchestrator Loop 在本 ADR 砍掉。
> **实施状态**：定位与文档已生效；`src/` 仍是 0.6.0 Orchestrator Loop + SignalStore，待 0.7.0 按本 ADR 改造。

## 1. 一句话决定

dteam 从「对抗式合议」重定位为：**模型分级路由执行层——主模型（T1）思考/路由/验收，小任务 fan-out 给小模型（T3）批量并行做，思考跟随档位，搞不定走 fresh 验收 → 回退强模型。**

## 2. 背景：为什么放弃对抗式合议，为什么是这个新定位

对抗式合议（0006/0007）经原型验证后被判定"繁琐且无用"——积分制成本与收益不成正比。更深的根因：对抗式合议和 0005 自发生长**同属一个失败模式**——"先发明一个重型编排机制，再让任务往机制里套"。dteam 三次定位（自发生长 → 群策群力 → 对抗式合议）都败在这。

新定位的来源不是机制设计，是**真实痛点**：强模型做小任务是**双重浪费**（贵 + 慢）。507 的 iOS 项目 Curio 的真实开发轨迹印证：大量 refactor / UI 小任务积压，本该用小模型批量做，却全压在强模型上串行。一线实践（zcode-swarm 插件一手源 `doc/20-能力参考/29` + 用户群聊）独立演化出"主模型调度 + 小模型执行 + 独立审核"的分立结构，印证方向。

**关键差异化**：dgoal 是单模型建检（全程一个强模型），结构上没有"模型分级"。dteam 的存在理由 = 给 dgoal 没有的"分级路由"能力——这是前几次定位都没找到的、dgoal 真正做不到的东西。

## 3. 定位钉死：模型分级路由

**dteam = 模型分级路由执行层。**

主模型（T1 思考档）是 owner，负责思考/决策/综合/路由/验收；小任务 fan-out 给 T3 快速档小模型批量并行；思考强度跟随档位；小模型搞不定走 fresh 验收 → 回退强模型。

**vs dgoal（零重叠）**：

| | dgoal | dteam |
|---|---|---|
| 模型 | 单模型全程 | 多模型分级路由 |
| 形态 | 主代理单兵带 plan + 独立审核审 DoD | 主模型路由 + fan-out 小模型 + fresh 验收 + 回退 |
| 适合 | 单兵够用、需独立验证完成 | 有大量小任务可分级并行、需降本加速 |

两者独立并列，不合并，不自动切换。主 LLM 自己判断用哪个。

## 4. 核心机制

### 4.1 Model Tier 三档（取代五角色）

旧五角色（explore/design/build/check/close）是**职能分工**（流水线/对抗视角产物，已放弃）。新定位下 dteam 内部的"角色"= **能力分级**：

| 档位 | 模型 | 思考 | 默认工具 | 用途 |
|---|---|---|---|---|
| **T1 思考档** | 旗舰 | 高 | 全工具（读写改 + 审核） | 思考 / 决策 / 验收 / 回退重做 |
| **T2 标准档** | 标准 | 中 | 可写（读写改） | 常规实现 |
| **T3 快速档** | 快速 / 本地 | 低 | 默认只读；显式限定写 | 机械小任务 |

- **标准锚定供应商产品线层级**（每家供应商都已分好旗舰/标准/快速三线），价格为辅验证。
- **思考强度跟随档位**（T1 高 / T2 中 / T3 低），不独立成维——理由：思考收益随档位降低而递减（小模型高思考不划算），且难任务走回退换强模型（自带高思考），不需要让小模型多想。
- **标准本质是人为划档**（模型能力连续，档位是离散近似），不是客观物理边界。

### 4.2 单工具 dteam_dispatch

dteam 暴露**唯一工具** `dteam_dispatch(task, tier, thinking?, tools?)`：
- 创建 fresh 进程内 worker session（Logical Isolation，不继承主会话），执行，返回结果。
- **执行 / 验收 / 回退都是 dispatch 的不同用法**（验收 = T1 fresh + 只读 + 验收 prompt；回退 = T1 重做或主模型自己做）。
- 主模型并发调用多个 dispatch = 并行 fan-out。

单工具够用的关键：dispatch 创建的 worker 都是 fresh session，验收 worker 天然不看主会话/方案出处——所以验收不需要第二个工具。

### 4.3 回退（可用性兜底）

- **硬失败**（小模型报错/超时/工具异常）→ 自动回退。
- **质量不过** → fresh 验收触发回退。
- 回退目标是 T1 强模型（重做）或主模型自己接手。

### 4.4 fresh 验收（对抗主模型倾向）

主模型既是分配者又是验收者，有倾向性（给自己分配的活放水）+ 上下文锚定——这是 dgoal「不让学生判卷」原则**从"完成判定"迁移到"路由+验收"**。

dispatch 的 fresh 特性保证：主模型想验收时，验收 worker 是独立 fresh session，不看主会话/方案出处。**这是复活 ADR 0007 的"fresh 独立 check 对抗主模型倾向"零件**——不是回到对抗式合议（那个积分制/多轮对抗繁琐），是把这一个有效零件用在 dispatch 的验收用法上。

## 5. 推翻了什么

| 旧 | 推翻理由 |
|---|---|
| 0006 对抗式合议 | 原型验证繁琐无用；仍是"造重型机制"的失败模式 |
| 0007 对抗回合 + 积分制 + N design 差异化 + summary 不转原文 | 同上；但 **fresh check 零件复活**到验收用法 |
| 五角色（explore/design/build/check/close 职能分工） | 被 T1/T2/T3 能力分级取代 |
| Orchestrator Loop（独立编排循环） | 主模型自己路由，不要独立 loop |
| Signal Store（信号驱动，0005 保留项） | dispatch 是 fan-out + 收结果，不需要信号回流 |

## 6. 保留有效

| 基底 | 说明 |
|---|---|
| 进程内 `AgentSession` + Logical Isolation（0005） | dispatch 的实现基底 |
| **Multi-Provider Routing + FallbackModels**（0005） | 新定位核心，加 `tier` + `thinking` 字段激活 |
| Adaptive Concurrency（0005） | 并行 fan-out 需要 |
| 0001 有立场替代层 | dteam 仍是贴合 507 工作流的替代层 |
| 0002 精神（角色收敛） | 从五角色收敛成三档 |
| 0004 不做 resume | 新定位不跨任务持久化 |

## 7. 代价与权衡

| 取舍 | 代价 | 换来 |
|---|---|---|
| 放弃对抗式合议 | 牺牲了"方案经多视角对抗检验" | 换来轻量（单工具 + 三档，不造重型机制） |
| 五角色 → 三档 | 旧 prompt / 工具配置要改 | 换来和模型分级路由自洽的内部结构 |
| 砍 Orchestrator Loop / Signal Store | 失去信号驱动编排 | dispatch fan-out + 收结果更简单直接 |
| 主模型路由有倾向性 | 可能偷懒 / 上下文干扰 | fresh 验收兜底对抗倾向 |
| 独立不合并 dgoal | 两个扩展要维护 | 换来真差异化（分级路由 vs 单模型），避免合并后边界含糊 |

## 8. 实施默认与待定分支

已在 0.7.0 dteam 实施 Phase 1 收敛的默认：

- **fresh 验收默认可选**：关键任务由主模型显式以 T1 + 只读 `tools` 调 dispatch；不为每次产出强制增加质量闸门。
- **T3 默认只读**：独立小改需调用方在 `tools` 显式授予限定 `edit` / `write`；回退不得越过该显式上限。

仍留实施验证的分支：

- dispatch 的 worker 结果回收机制（同步等返回？依赖 Pi 并行工具调用？）
- dteam 与 dgoal 在同一会话里的配合细节（dgoal goal 里调 dispatch fan-out）
