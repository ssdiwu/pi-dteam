# dteam 重定位为对抗式合议

> **状态：❌ 已被 [ADR 0008](./0008-dteam重定位为模型分级路由执行层.md) 推翻**（原型验证繁琐无用，git `78e03a7`）。仅保留追溯。
> **推翻**：[ADR 0005](./0005-dteam-0.6.0-重定义为自发生长召唤池.md) 的「自发生长」定位——第 7（vs dgoal 边界含糊）、第 8（无预先计划，召唤轨迹即计划）、第 14（进程内 check 收口）、第 17（每轮 LLM 现场决策）四条。
> **当时保留**：0001（有立场的子代理替代层）、0002（角色写死）、0004（不做 resume）。0005 的进程内 worker + Logical Isolation、Signal Store 当时作为对抗式合议的执行基底。**0.7 实现注记**：当前只保留进程内 fresh worker、Logical Isolation、Multi-Provider Routing 与 Adaptive Concurrency；Signal Store、五角色和对抗运行时均已删除。

## 1. 一句话决定

dteam 从「基于 goal 自发生长的召唤池」重定位为：**对抗式合议——贯穿全程、带上下文、逼出方案并盯死执行不背叛方案的多角色协作。**

## 2. 背景：为什么重定位

0.6.0 把「自发生长」当作 dteam 的本质，结果产生了三个相互锁死的不可用性：

1. **没有确定性锚点**：dgoal 一句话能说清（"让一个目标的完成被独立验证"），dteam 写了 9 节触发协议仍判断不清"何时该用"。根因是「自发生长」本身不提供确定收口。
2. **既不像 dgoal 又做不好自己**：0.6.0 的 `check` 角色是进程内 worker + Logical Isolation——学 dgoal 的零上下文审核学到半吊子（fresh 不如独立子进程彻底），又丢掉了 dteam 本该有的"带上下文审一致性"优势。两头不靠。
3. **承接断了**：群策群力如果只产出方案不承接执行，那它就被"先讨论再用 dgoal"完全替代——没有独立存在理由。

更深的根因：**dteam 把「确定性」当成了敌人**（自发生长 = 反确定性），但 507 的真实痛点、dgoal 的可用性、以及所有能力参考（22 多worker编排「可确定的协作关系由 runtime 执行」、23 Routa「带证据门禁和显式交接」、24 harness 确定结构、27 OpenTeams 可见计划）都在说：**确定性才是可用性**。

## 3. 定位钉死：对抗式合议

**dteam = 对抗式合议**：贯穿一个目标的全过程、带着共享上下文，逼出一个经多视角对抗检验的方案，并盯死执行不背叛方案。

**先校准 dgoal 的真实机制**（修正早期“法官断上下文”的不准确描述——经核对 dgoal 一手文档）：

- dgoal 的**主体**是主 agent **单兵、带着 task plan 全程推进**——goal/phase/task 三层每轮注入（dgoal 称“参考注意力”，goal 与 context 每轮注入、不随进度退化）。**dgoal 主体本来就是“带方案全程”，不是断上下文。**
- dgoal 只有**审核环节**（`dgoal_check` 阶段建检 / 终审）是 fresh 独立子进程——刻意看不到主会话历史、物理上拿不到方案承诺，只审“DoD 达标”。
- dgoal 的信任假设：**信任单兵定的方案**，唯一的不信任是“会不会虚报完成”，故用独立铁判审达标。

因此 dteam 与 dgoal 的差异**不在“带不带上下文”**（两者主体都带方案全程），而在两条更精确的轴：

| | dgoal | dteam |
|---|---|---|
| 方案怎么来 | 主 agent **单兵**定 | **多角色对抗**逼出（证据方/主张方/反方/裁决） |
| 信不信任方案 | **信任**单兵方案 | **不信任**单一视角，靠对抗纠偏 |
| 审什么 | 独立子进程审 **DoD 达标** | 带上下文审**执行是否背叛对抗方案 + 分歧是否解决** |
| 审核盲区 | fresh 审核员**结构性看不到方案承诺**，审不出漂移 | 能审漂移，但不替代 dgoal 的事后铁判 |
| 收口确定性 | “过了 DoD” | “决策经受对抗 + 执行未背叛 + 分歧已解决” |

**缝的来源（精确版）**：dgoal 主体带方案全程推进，但它的独立审核刻意 fresh、**物理上看不到方案承诺了哪些取舍**——所以审不出“执行背叛了设计承诺”。这恰好是 dteam 带上下文能审的。两个项目主体都“带方案全程”，差异在**方案是否经过对抗**、以及**审核能否看到方案承诺**——这是真零重叠的两个确定收口：**dgoal 审不出 dteam 审得出的漂移，dteam 不替代 dgoal 的事后铁判。**

## 4. 五角色重对齐（从流水线工序 → 对抗视角）

自发生长时代五角色是"谁先做谁后做"的流水线。对抗式合议下，五角色是**对抗中的视角分工**：

| 角色 | 自发生长时代 | 对抗式合议下 |
|---|---|---|
| `explore` | 探索者：读码查资料 | **证据方**：提供事实和约束（不预设立场） |
| `design` | 方案者：出方案 | **主张方**：提出方案并亮明权衡 |
| `build` | 实现者：唯一能改代码 | **可行性反方**：质疑方案能否落地，承接执行 |
| `check` | 验收者：跑测试 | **风险/漂移反方**：盯执行是否背叛方案、风险是否暴露 |
| `close` | 收口者：总结 | **裁决方**：显式化分歧、敲定取舍、确认收口 |

**关键变化**：`build` 不再只是"实现者"，它是**对抗的一环**——可行性反方；承接执行，但它的"改代码"特权服务于"把对抗逼出的方案落地"，而非"自由发挥"。`check` 不再学 dgoal 的零上下文审核（那留给 dgoal），而是**带上下文审一致性**——这是 dteam 唯一立足点。

> 五角色的具体工具权限、prompt（提示词）、收口协议，由后续实施方案定义，不在本 ADR 展开。

## 5. 推翻了什么（0005 的四条）

| 0005 条目 | 旧定义 | 推翻理由 |
|---|---|---|
| 第 7：vs dgoal | 群策群力 ≠ 建检循环，但边界含糊 | 校准：dgoal 主体单兵带方案全程 + 独立审核审达标；dteam 多角色对抗 + 带上下文审一致性。缝在“方案是否经对抗”与“审核能否看到方案承诺”，零重叠 |
| 第 8：无预先计划 | 召唤轨迹即计划 | 这是不确定性的总根源。合议需要**显式的决策记录与分歧记录**贯穿全程，不是"召唤轨迹即计划"的现场涌现 |
| 第 14：进程内 check 收口 | 进程内 check worker | 它学 dgoal 的零上下文学到半吊子。dteam 的收口改为**带上下文的一致性收口**，机制由实施方案定义（非进程内 fresh check） |
| 第 17：每轮 LLM 现场决策 | 每轮一次 LLM 决定召唤谁 | 开放式现场决策 = 反确定性。合议的推进由**对抗回合的结构**驱动，而非每轮重新拍板 |

## 7. 确定性来源（这是本次重定位的核心交付物）

自发生长时代的"确定性"是矛盾的（自发生长 = 反确定性）。对抗式合议的确定性来自**四个锚点**，每一个都可被验证：

1. **入口确定**：一句话能说清"何时该用 dteam"——当一个目标的价值不在"代码改完"而在"决策经得起多方推敲"时。触发协议据此重写。
2. **方案确定**：合议产出**显式的决策记录**（主张方亮明权衡、反方质疑、裁决方取舍），不是"召唤轨迹即计划"的模糊涌现。
3. **执行确定**：`build` 承接落地，但盯死在**不背叛方案**上——`check` 带上下文审一致性，漂移即暴露。
4. **收口确定**：done 的标准是「决策经受对抗 + 执行未背叛 + 分歧已解决」，可被复验。

## 8. 代价与权衡

| 取舍 | 代价 | 换来 |
|---|---|---|
| 放弃"自发生长"叙事 | 牺牲了"完全涌现、零预设"的浪漫 | 换来确定性锚点——这是可用性的前提 |
| `check` 放弃零上下文 | 不再像 dgoal 那样铁判结果达标 | 换回 dteam 唯一立足点（带上下文审漂移），且和 dgoal 零重叠 |
| 引入"决策记录/分歧记录" | 比"召唤轨迹即计划"重 | 换来全程一致性的可验证性 |
| 五角色职责重对齐 | 旧 prompt / 工具配置要改 | 换来"对抗视角"对齐定位，而非流水线工序 |

## 9. 实施指向

本 ADR 是定位级决策，不展开实现细节。**当时**的源码与文档改造方向包括 `orchestrator-loop.ts` 的每轮现场决策、`check-gate.ts` 的进程内 check、五角色 `agents/*.md` prompt、触发协议与术语表；这些实现已被 ADR 0008 推翻并在 0.7 删除。

**对现有能力参考的重新定性**（回应"越努力越没用"）：
- 22 多worker「可确定的协作关系由 runtime 执行」→ **本 ADR 采纳其核心**，对抗回合结构由 runtime 确定，智能推理留给 worker。
- 23 Routa「带证据门禁和显式交接的任务协议」→ **本 ADR 采纳**，决策记录即显式交接。
- 24 harness 确定结构 → 重新评估，6 种 pattern 中 Producer-Reviewer（生成+审核）与 Supervisor（中央调度）天然贴合对抗式合议。
- 25 swarm-ide / 26 gemma / 27 openteams → 这些参考被 0005 判为"设计冲突不借"的候选，在本 ADR 下**需要重新分级**：可见计划（27）、模式库（25 spells 的 critic-loop）、证据包（27）都从"不借"转为"贴合对抗式合议的候选"。
