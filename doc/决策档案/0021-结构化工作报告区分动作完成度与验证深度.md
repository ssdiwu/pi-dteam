# 结构化工作报告区分动作、完成度与验证深度

> **状态：✅ 有效，本轮实施。**
>
> **更新**：细化 ADR 0015 的 `dteam_report` 合同与 ADR 0016 的 fresh 验证证据；保持 ADR 0015 的 handoff facts provenance、不接受自由文本回退，并补充 ADR 0019 的人类可读报告投影。

## 决定

每个 worker 仍恰好提交一次统一的 `dteam_report`，不按 explore / implement / review 拆报告类型，也不新增验证工具。报告必须区分四个互不替代的维度：

1. **Worker runtime state**：`queued / running / waiting / completed / failed / timed_out / cancelled / shutdown`，由 Manager 管理；
2. **activities**：worker 本轮实际做过的动作；
3. **outcome**：被派任务本身完成到什么程度；
4. **verification**：本轮实际达到的验证深度、结果、证据与剩余未验证项。

新的统一报告合同为：

```ts
interface WorkerReport {
  outcome: "completed" | "partial";
  summary: string;
  activities: Array<
    | "inspected"
    | "modified"
    | "tested"
    | "executed"
    | "captured_visual"
  >;
  facts: Array<{ claim: string; evidence: string }>;
  verification: {
    depth: "none" | "inspection" | "automated" | "runtime" | "visual";
    status: "passed" | "failed" | "partial" | "not_run";
    evidence: string[];
    remaining?: string[];
  };
  uncertainties?: string[];
}
```

## 字段定义

- `outcome=completed`：worker 完成了被派任务；`partial`：任务本身仍有未完成部分。它不表示验证通过。
- `activities`：
  - `inspected`：读取代码、文档、diff、配置或其他材料；
  - `modified`：修改或创建文件；
  - `tested`：运行 build、静态检查或自动化测试；
  - `executed`：实际运行目标程序、服务、CLI 或用户路径；
  - `captured_visual`：渲染、截图并检查视觉产物。
- `facts`：可复验、可交给下一轮 worker 的事实；Manager 继续在 completed event 中附加真实 `workerId` provenance。
- `uncertainties`：尚未查明且可能改变结论的事实。
- `verification.depth`：worker 对当前任务实际达到的最深直接验证方式，不是全局质量分数：
  - `none`：没有验证；
  - `inspection`：只通过阅读或静态核对；
  - `automated`：运行了 build、静态检查或自动化测试；
  - `runtime`：实际执行目标运行路径；
  - `visual`：对有视觉表面的任务运行、捕获并检查真实视觉结果。
- `verification.status`：在该深度上得到的 `passed / failed / partial / not_run` 结论。
- `verification.evidence`：支撑验证深度与结果的命令、输出、运行路径或产物位置。
- `verification.remaining`：明确知道但本轮没有完成的验证，例如“无模拟器，未做视觉复测”。它不同于未知事实。

`human` 不属于 worker 证据。用户人工复测发生在 worker 报告之后，保留在主对话、dgoal 验收或项目工件中；终态 worker 不为后续人工结果改写历史报告。

## 校验不变量

- `activities` 必须非空且不重复；`facts` 至少一项，每项 `claim / evidence` 非空；
- `verification` 始终必填；没有验证时必须显式提交 `depth=none`、`status=not_run`、空 evidence；
- `depth!=none` 时 status 不得是 `not_run`，且 evidence 至少一项；
- `inspection` 要求包含 `inspected`；`automated` 要求包含 `tested`；`runtime` 要求包含 `executed`；`visual` 要求包含 `executed` 与 `captured_visual`；
- `remaining` 与 `uncertainties` 若存在，只接受非空字符串；
- 未知字段、`human`、`expectedVerificationDepth` 或旧报告形状 fail-closed；reload 后所有 worker 都是 fresh session，不保留内部兼容层。

## 状态解释

Manager 的 `state=completed` 只表示 worker 正常结束并提交合法报告。以下组合都有效：

- `state=completed + outcome=completed + verification.status=failed`：worker 成功完成审查，并确认目标未通过；
- `state=completed + outcome=completed + depth=automated + remaining=["未做视觉复测"]`：工作完成且自动检查通过，但视觉结果尚未确认；
- `state=completed + outcome=partial`：worker 正常结束，但被派任务没有完整完成，主代理不得直接收口。

WorkerRequest 不新增最低验证深度。环境可能缺少模拟器、浏览器、账号或服务；worker 只诚实报告实际深度和 remaining，主代理再决定是否补验、重派或交给用户人工复测。

## 代价与收益

代价是内部 schema、prompt、测试和 UI 投影都要更新，并且旧形状在 reload 后不兼容。收益是消除“worker 完成 = 工作通过”“写了代码 = 已验证”“跑了测试 = 用户体验正确”等混淆，同时保持 facts handoff 与单报告入口不变。
