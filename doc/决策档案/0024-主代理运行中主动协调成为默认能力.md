# 主代理运行中主动协调成为默认能力

> **状态：✅ 决定已确认并实施。**
>
> **更新范围**：取代 ADR 0009 中“所有非阻塞 signal 只更新 UI”、ADR 0013 中“不提供模型侧通用 steering”、ADR 0023 中“主代理不能取消 running worker”的相关限制；扩展 ADR 0018 的可消费事件边界，但继续保留其禁止轮询、单次消费和仅在真实依赖时等待的原则。ADR 0008 的模型分级定位、ADR 0010 的无 batch / 依赖调度、ADR 0004 的不做 resume 均保持有效。

## 决定

主代理运行中主动协调成为 dteam 的默认核心能力，而不是显式开启的第二模式：

1. worker 的普通 `progress`、实时文本和工具活动继续只更新 UI / Snapshot；只有可能改变其他任务、当前路径、风险判断或下一步路由的有界、带证据可行动发现才进入主代理事件队列。
2. 可行动发现（Actionable Finding）在主代理 idle / settled 后合并交付；若有匹配的显式依赖等待，则沿同一单消费者事件链返回。Worker Manager 不解释 finding、不选择接收者，也不自动派发或 steer。
3. 主 LLM 无需等待 worker 先发 request，即可主动向 running worker 发送上下文、跨 worker 事实、纠偏、收敛或停止指令。主动指令不得隐式授予工具、扩大预授权或绕过 `writeScope`。
4. 停止 running worker 时先要求其优雅收敛并提交 `partial` 报告；未及时收敛或任务已明确失去价值时，主 LLM 可以强制取消。可写 worker 继续执行 ADR 0017 的中断完整性守卫，已知取消终态继续原子清理待回放旧事件。
5. 主 LLM 在既定用户目标内自主协调；重要改派、强制取消和未解决风险在下一次自然回复或最终总结中说明。产品取舍、越界和不可逆风险仍回到用户。
6. 最终产品不保留“安静 fork–join / 主动协调”双轨配置。实施期若使用内部实验开关，必须带有退出条件。

完整需求与验收合同已归档于 [`doc/90-归档/版本实施方案/40-主代理运行中主动协调需求规格.md`](../90-归档/版本实施方案/40-主代理运行中主动协调需求规格.md)。

## 为什么

当前实现已经采集 `progress` / `finding`、维护 Signal Log 与 Worker Snapshot，也已经实现 `WorkerManager.steer()`，但两端没有对主 LLM 闭合：非阻塞 finding 不产生 parent event，模型侧 `dteam_respond` 又必须绑定已有 `requestId`；底层 steer 只由 `/dteam` 用户界面调用。结果是主代理虽然名义上负责路由与冲突裁决，实际只能在 worker 请求、超时或终态之间行动，dteam 仍主要表现为异步分发—汇合。

此前限制是为避免 ADR 0005 的 Orchestrator Loop、信号驱动自动召唤和 P2P 复杂度复活；它正确阻止了 Manager 成为导演，却同时阻断了“signal → 主 LLM 判断 → 主 LLM 主动协调”的安全路径。新决定只补全主代理拥有的双向控制，不把语义决策下沉给 Manager。

## 取代关系

- **ADR 0009**：保留会话级 Worker Manager、星型拓扑、Request State 和非持久运行时；将“非阻塞过程信号只更新 UI”收窄为普通进度，可行动发现可以进入主代理事件队列。
- **ADR 0013**：保留 dispatch / respond / recover / wait 的职责分离与禁止通用 status；取代“模型侧不提供通用 steering”的限制，新增清晰的主动控制接缝，具体工具拆分由实现阶段收口。
- **ADR 0018**：保留显式依赖等待、禁止忙等与 parent event 单次消费；可行动发现成为可驱动主代理裁决的事件，不把 wait 变成状态查询。
- **ADR 0023**：保留 waiting request 上的 `dteam_respond(cancel)` 与同步守卫；取代“running worker 只能由用户取消”的限制，改为主 LLM 优雅停止优先、必要时强制取消。
- **路线图候选 33**：只读 `dteam_inspect` 只能让主代理看见状态，不能完成主动协调闭环；首版不采用，候选由本决定吸收并取代。

旧 ADR 保留原始历史，不改写为从未作出过旧决定；其索引与状态说明应指向本 ADR。

## 权衡与守卫

可行动发现和模型侧控制会增加主模型轮次、上下文占用与事件竞态，也可能被模型误用成高频协调。为此固定以下边界：

- 只推送会改变路由的可行动发现，普通进度保持 UI-only；
- 事件有界、合并、去重并沿单消费者队列交付；
- 主动指令不改变权限边界；
- Manager 不作语义判断，不自动 steer、派发或建立依赖；
- 禁止 inspect/status 轮询，`dteam_wait` 仍只用于真实依赖；
- 先优雅收敛，强制取消继续受写入中断守卫约束；
- 重要协调动作对用户摘要透明。

## 为什么不直接引入 Pi 的 EventStream

### 已核实的上游能力

本决定在 `@earendil-works/pi-ai@0.83.0` 上核对了 Pi 自带的 `EventStream<T, R>`：它由包根公开导出，以一个无键的 FIFO `queue` 保存先到事件，以 `waiting` 保存先到消费者的 Promise resolver；`push()` 优先唤醒最早 waiter，否则入队；`AsyncIterable` 逐项消费，`isComplete` / `end()` 负责终止和最终结果。`pi-agent-core` 的 `agentLoop()` 正是用它把单条 agent loop 的事件流以 `agent_end` 收口。证据见上游包内 `dist/utils/event-stream.{js,d.ts}`、`dist/index.d.ts` 与 `pi-agent-core/dist/agent-loop.js`。

这证明 queue / waiter 配对、push 驱动和异步消费模式是成立的，dteam 也沿用同一思路；但上游类型解决的是**一条无选择器事件序列**，不是 dteam 的 parent event 合同。

### dteam 不能由一个裸 EventStream 承担的语义

1. `dteam_wait(workerIds)` 必须按一组 worker ID 选择事件，并在迟到 wait 时一次消费全部匹配的已排队事件；一个全局 FIFO stream 无法跳过不匹配事件而不引入重排、回塞或第二层 buffer。
2. 同一 parent event 必须在显式 wait 与 idle / settled follow-up 之间单次消费；`follow_up` 与 `wait_only` 还具有不同投递资格。EventStream 只决定“给最早 waiter还是入队”，不知道这两种 delivery policy。
3. finding 需要按 worker、delivery 有界合并去重；主代理 cancel / stop 需要按 worker 原子删除旧事件；可写中断守卫、脱敏和人类可读 WaitResult 也都属于领域合同，而非通用流能力。
4. 为每个 worker 建一个 stream 虽能绕开选择器，却会增加 stream 生命周期、跨 worker 聚合和 shutdown 清理，并且仍不能解决 wait 与 follow-up 的单消费者仲裁；在 EventStream 外再包一层 selector / delivery queue，则只是重建当前 `pendingParentEvents + waiters`。
5. `EventStream` 虽由 `@earendil-works/pi-ai` 包根公开导出，但它不是 Pi `ExtensionAPI` 的宿主原语。dteam 当前只把 `pi-ai` 放在 devDependencies，发布运行时只 peer 依赖 coding-agent / tui；为一个仍需领域包装的容器增加直接运行时依赖，会扩大版本耦合而不减少总体复杂度。

### 决定与重评条件

因此当前选择是：**借鉴 EventStream 的 push + queue / waiter 模式，不直接导入它，也不为替换而抽象 WorkerManager 的专用事件队列。** 这不是因为上游类不可用，而是因为直接复用不能承载现有选择性单消费合同，最终仍需第二套状态。

只有同时出现以下证据才重新评估：Pi 提供稳定的 Extension API 级、支持 selector / 单次消费 / cancel 清理的事件原语；或当前专用队列出现重复的真实竞态与维护成本，并能以无第二 buffer、无协议变化的替换原型证明代码和状态总量下降。文章或 API 形状相似本身不构成迁移理由。

## 验证

必须以公开工具接缝和真实 Pi 会话共同验证：worker A 在终态前提交可行动发现，主 LLM 在 A 完成前把该事实主动交给 running worker B 并改变 B 的后续动作；普通 progress 不唤醒主模型，事件不重复投递，Manager 没有自动选择接收者或下一任务。另需覆盖优雅停止、running 强制取消、可写中断守卫和重要动作摘要。**该合同已通过自动化端到端测试与真实 Pi 多 worker 冒烟验证。**

## 实施验证

- `dteam_control` 已作为第五个模型侧公开工具实现，严格限制为 `running` worker，`steer` / `graceful_stop` / `cancel` 不需要 `requestId`，不改变工具权限或 `writeScope`。
- `finding` 已进入有界、合并去重的 parent event 单消费者链；`dteam_wait` 与 idle/settled follow-up 不重复交付。
- 自动化端到端测试与真实 Pi 冒烟均证明 A finding → 主代理 control → B partial report 的闭环；详细命令、绝对 checkout、HEAD 与工作区边界见归档规格的实施验证记录。
