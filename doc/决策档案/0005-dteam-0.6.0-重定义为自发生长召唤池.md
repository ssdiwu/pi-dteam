# dteam 0.6.0 重定义为自发生长召唤池

> **状态：❌ 定位已被 [ADR 0006](./0006-dteam重定位为对抗式合议.md) 推翻，并由 [ADR 0008](./0008-dteam重定位为模型分级路由执行层.md) 最终取代。** 本文仅保留 0.6.0 历史追溯；进程内 `AgentSession` + Logical Isolation、Multi-Provider Routing、Adaptive Concurrency 三项执行基底仍被 0008 沿用。
> **曾推翻**：[ADR 0003（后台运行依附 Extension Runtime）](./0003-后台运行依附Extension-Runtime而非单次tool-call.md)、旧 0.6.0「Task Plan + Live Plan + `mode: solo/chain/team`」。
> **仍有效**：[0002](./0002-角色写死不做用户自定义角色.md) 的“不做用户自定义角色”精神、[0004 不做 resume](./0004-不做resume和默认持久化.md)。

## 1. 一句话决定

dteam 从「后台运行的二维编排引擎（`solo / chain / team` × `direct / build_check / adaptive`）」重定义为：**基于 goal（目标）自发生长的多 worker 群策群力扩展**。

## 2. 背景：为什么要重定义

dteam 此前的实现由两条不相容的血脉合并而成：

1. **原始召唤池构想**（来自 `ant-colony` 启发）：5 个角色是可被按需召唤的专业角色池，任务从执行中长出来。
2. **后来叠加的 `pi-subagents` 风格 chain**（预先穷举 step、按表执行）：把召唤池做成了固定流水线 / 预制步骤执行。

这产生了今天别扭的 `solo / chain / team` 模型、planner 穷举、后台 `runId` 一整套。根因诊断：**dteam 漂离了它本来的召唤池本质，变成了一个预先穷举 plan 的执行引擎。**

同时存在一个对照项目 [`pi-dgoal`](../../../pi-dgoal)：它把「主代理单兵持续推进 + 独立审核」做得很顺。这暴露了 dteam 的定位问题——如果主 Agent 能直接干，dteam 凭什么存在？

## 3. 18 条根本决策（dteam 新定义骨架）

| # | 决策点 | 选定 | 说明 |
|---|---|---|---|
| 1 | dteam 本质 | **召唤池**，非流水线 | 5 个角色是召唤池，不是流水线阶段 |
| 2 | `solo / chain / team` | **删除** | 推翻二维编排的组织维度 |
| 3 | 谁触发召唤 | **Orchestrator（主 LLM 启动 loop）** | 主 LLM 触发的是启动 Orchestrator Loop |
| 4 | 后台运行 | **放弃，同步前台 Orchestrator Loop** | 推翻 ADR 0003 |
| 5 | worker 执行基底 | **进程内 `AgentSession`** | 非 OS 子进程 |
| 6 | 环境信息存放 | **Signal Store**（临时、TTL 衰减、不落项目目录） | ant-colony `pheromone` 的去虫化 |
| 7 | vs dgoal | **群策群力 ≠ 建检循环，独立并列** | 两个项目不合并 |
| 8 | 预先 Task Plan | **不要，召唤轨迹即计划** | 任务从执行中涌现，非预先穷举 |
| 9 | `queen` 改名 | **Orchestrator / Orchestrator Loop** | 去 ant 隐喻 |
| 10 | 启动方式 | **C 混合**（`/dteam` 显式 + 主 LLM 自动） | 两种入口都保留 |
| 11 | worker 隔离 | **Logical Isolation**（逻辑 fresh） | `SessionManager.inMemory()` + 最小 ResourceLoader + 工具白名单 |
| 12 | Signal Store 失效 | **TTL 衰减** | 新信号优先，旧信号过期 |
| 13 | 角色池 | **固定五角色** `explore/design/build/check/close` | 不做角色市场 |
| 14 | 完成判定 | **强制 `check` 收口（Completion Gate）** | Orchestrator 不能自停 |
| 15 | 并发 | **Adaptive Concurrency**（自适应并发） | 可同时召唤多 worker |
| 16 | 多供应商 | **Multi-Provider Routing** | 避免单供应商约 3 并发撞墙 |
| 17 | 召唤决策 | **LLM-Driven Orchestration** | 每轮一次 LLM 调用决定召唤谁 |
| 18 | 信号写入 | **进程内事件订阅** | `session.subscribe` 实时写入 Signal Store |

## 4. 与 dgoal 的边界（贯穿所有文档）

| | dgoal | dteam |
|---|---|---|
| 本质模式 | 建检循环（build-check loop） | 群策群力 |
| 主导者 | 主代理单兵 | Orchestrator 协调多专业角色 |
| 执行 | 主代理自己干 | 进程内 `AgentSession` worker（Logical Isolation） |
| 完成 | 独立审核员（零上下文子进程终审） | 强制 `check` 角色收口（进程内 worker） |

**主 LLM 自己判断**：单代理能干用 dgoal，需要召唤专业角色用 dteam。两个项目独立并列，不合并，不自动切换。

## 5. 推翻了什么

- **ADR 0003（后台运行依附 Extension Runtime）**：dteam 不再后台运行，`runId`、`RunsStore`、立即返回式 run、`dteam(action="run")` 返回 `{status:"running", runId}` 均失效。
- **旧 0.6.0（Task Plan + Live Plan + `mode: solo/chain/team`）**：`DPlan Contract` 的 `mode` 字段、预先穷举 plan、二维编排的 `Mode × Strategy` 均失效。
- **planner 穷举 / quick rule-based plan / LLM JSON fallback**：改为 LLM-Driven Orchestration（每轮一次 LLM 调用）。
- **`SchedulingPlan` / `FileGraph` / preflight batches**：不再是核心模型；文件依赖可作为未来辅助，但不再是编排主轴。

## 6. 保留有效

- **[ADR 0002 角色写死](./0002-角色写死不做用户自定义角色.md)**：5 个角色写死，不做角色市场——与第 13 条一致，强化。
- **[ADR 0004 不做 resume](./0004-不做resume和默认持久化.md)**：仍有效。
- **`build` 唯一可 `edit`（编辑）现有文件**：安全边界不变。
- **`availableTools` 契约**：主 LLM 传入可见工具，dteam 校验透传——保留。

## 7. 代价与权衡

| 取舍 | 代价 | 换来 |
|---|---|---|
| 放弃后台运行 | dteam 期间主对话阻塞 | Orchestrator 能实时读 Signal Store、动态决策；定位干净（= dgoal 区分清晰） |
| 放弃 OS 子进程隔离 | 靠 Logical Isolation 保证 fresh | 实时信号（`session.subscribe`）、低启动开销、直接访问父进程状态 |
| 放弃预先 Task Plan | 没有可预览的完整计划 | 自发生长，避免穷举 plan 漂离真实需求 |
| 自适应并发 | Signal Store 有并发写、需限流消解 | 吞吐、贴近 ant-colony 本质 |
| 固定五角色 | 不可扩展 | 决策稳定、术语清晰、安全边界可验证 |
| 强制 check 收口 | 每次 run 多一次 check 调用 | 完成标准稳定，check 不被忽略 |

## 8. 实施指向（本轮不动代码）
