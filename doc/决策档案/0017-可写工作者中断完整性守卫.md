# 可写工作者中断完整性守卫

> **状态：✅ 已实施**
>
> **补充**：补充 ADR 0015 的结构化工作报告和 ADR 0016 的递增成本验证；不引入 resume、workspace 持久标记、文件锁、worktree 或自动回滚。
>
> **修订**：主代理通过 `dteam_respond(cancel)` 或 `dteam_recover(stop)` 明确放弃 worker 时，守卫改为随该工具结果同步返回；Manager 同时清除该 worker 尚未消费的 parent event，避免已知终态后迟到回放。用户经 `/dteam` 取消和未显式停止的 timeout 首次守卫仍按原渠道通知主代理。

本 ADR 决定并已实施：凡在 `dteam_dispatch` 中获得 `edit` 或 `write` 的 worker，必须声明项目相对 `writeScope`（文件或目录）。Worker Manager 在该 worker 因 failed、cancelled、shutdown、timed_out 或缺少必需 `dteam_report` 而未被确认完成时，向主模型回传带 worker、reason 与 `writeScope` 的 `write_interrupted` 事实。主模型不得将该 worker 的结果当作可信证据或收口父任务；必须派发 fresh T3，对 scope 内 diff、编译或定向测试作完整性检查，并将结果经结构化报告和 handoff 交给修复或后续验证。

同步返回不等于静默丢弃守卫：主代理仍必须按 `writeScope` 执行 fresh 完整性检查。区别只在交付时序——既然主代理已通过 cancel/stop 同步知道终态，就在同一工具结果中拿到守卫，不再让终止前排队的旧事件在后续轮次重复提醒。

不自动回滚中断写入：部分改动可能有效，自动恢复会误删有效工作并需要事务/冲突机制。也不持久化专用中断标记：这会扩大“不做 resume / 默认持久化”边界。为覆盖 reload 或新会话后的残留，每次准备派发可写 worker 前，主模型若发现工作区存在未解释的 dirty diff，必须先派 fresh T3 做工作区完整性检查，再继续可写派发。

该守卫仍由主模型决策式路由：Manager 只记录和回传中断事实，不自动创建检查 worker，不阻塞为编排器，也不根据自然语言推断写入范围。
