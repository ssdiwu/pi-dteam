# 设计 v2 与实施现状

> 本文记录旧「二维编排设计」与当前实现的关系，并明确它在 0.6.0 被推翻。
>
> ⚠️ **两层都已推翻**：旧二维设计被 ADR 0005 推翻；0005 召唤池形态（Orchestrator Loop + SignalStore）又被 [ADR 0008](../../决策档案/0008-dteam重定位为模型分级路由执行层.md) 推翻。本文仅作历史追溯。
>
> **当前权威架构见 [`10-系统架构.md`](../../10-架构与运行/10-系统架构.md)（0008 模型分级路由）；决策骨架见 [`ADR 0008`](../../决策档案/0008-dteam重定位为模型分级路由执行层.md)。**

## 1. ⚠️ 旧「二维编排设计」已被 ADR 0005 推翻

dteam 此前的 v2 设计是「`solo / chain / team` × `direct / build_check / adaptive`」的二维编排引擎。它在 0.6.0 被整体推翻：

| 旧设计（v2，失效） | 推翻后（0.6.0） |
|---|---|
| `solo / chain / team` 组织模式 | 删除；召唤池，无预设组织 |
| `direct / build_check / adaptive` 执行策略 | 删除；Orchestrator LLM 驱动每轮决策 |
| planner 穷举 / quick rule-based plan / LLM JSON fallback | LLM-Driven Orchestration（每轮一次 LLM 调用） |
| `SchedulingPlan` / `FileGraph` / preflight batches | 不再是编排核心；文件依赖降级为辅助信号 |
| 后台运行 / `runId` / `RunsStore` | 同步前台 Orchestrator Loop |
| 进程级 OS 子进程隔离 | 进程内 `AgentSession` + Logical Isolation |
| Task Plan / DPlan Contract | 无预先计划，召唤轨迹即计划 |

根因诊断：**旧 v2 把召唤池做成了预先穷举 step、按表执行的流水线**，漂离了 dteam 本来的召唤池本质。

## 2. 旧 v2 实现已退场（0.6.0 代码已重写）

0.6.0 Phase 5 已删除旧 v2 的全部编排代码（`orchestrator.ts` / `planner.ts` / `pool.ts` / `orchestrator/strategies/*` / `orchestrator/history-context.ts` / `scheduler/*`）。

| 旧设计点 | 0.6.0 处置 |
|---|---|
| Plan / Execute / Report 三段生命周期 | 已删，改为 Orchestrator Loop |
| `solo / chain / team` 组织形式 | 已删 |
| `direct / build_check / adaptive` 执行策略 | 已删 |
| 5 个角色 | 保留（ADR 0002） |
| `build` 唯一可 edit | 保留 |
| chain 上一步输出注入下一步 | 已删（chain 模式已废） |
| team 分批并行 ≤ 3 | 已改为 Adaptive Concurrency |
| help / found / progress / blocked 信号 | 保留，接入 SignalStore（TTL 衰减） |
| 后台 run 立即返回 `runId` | 已删，改同步前台 |
| `availableTools` 方案 D | 保留 |
| 进程内 `createAgentSession` | 保留并强化 Logical Isolation（跳过 discoverAndLoadExtensions） |

## 3. 旧 v2 有意收敛的设计（仍有效，0.6.0 继承）

### 3.1 不接入递归分解

旧 v2 决定：orchestrator 直接执行 planner 给出的 step，不在 build 中再递归拆任务。

0.6.0 继承：任务从 Orchestrator Loop 涌现，由主 LLM 拆成多次 dteam 调用，而非一次 dteam 无限递归。

### 3.2 不做固定工业流水线

旧 v2 决定：不做 `plan → execute → review → TDD → verify → merge` 固定流程。

0.6.0 继承：`check` 是收口闸门，但不是固定流水线阶段；Orchestrator 按需召唤。

### 3.3 角色写死

旧 v2 决定：保留写死 5 角色。

0.6.0 继承并强化（ADR 0002）：固定五角色是召唤池本质，不做角色市场。

## 4. 0.6.0 的新增设计（旧 v2 没有）

| 新设计 | 来源 |
|---|---|
| Orchestrator Loop（编排循环） | ant-colony `runColony` 去虫化 |
| Signal Store（信号存储，TTL 衰减） | ant-colony `pheromone` 去虫化 + 现有信号机制 |
| Logical Isolation（逻辑隔离） | ant-colony `makeMinimalResourceLoader` + `SessionManager.inMemory()` |
| LLM-Driven Orchestration | Orchestrator 每轮一次 LLM 调用决定召唤谁 |
| Adaptive Concurrency | ant-colony `ConcurrencyConfig`（min/max/optimal/lastRateLimitAt） |
| Multi-Provider Routing | ant-colony `ModelOverrides` + `FallbackModels` |
| Completion Gate（强制 check 收口） | 防止 check 被忽略 |
| 同步前台执行 | 放弃后台运行，换取实时信号决策 |

## 5. 当前设计边界（~~0.6.0~~ 已被 ADR 0008 推翻，仅追溯）

dteam 的主线不是"更像某个多 agent 框架"，而是：

> 在 Pi 里提供一个**基于 goal 自发生长的召唤池**；主 LLM 协调，按需召唤固定五角色协作，同步前台 Orchestrator Loop，强制 check 收口。dteam 是群策群力，与 dgoal 的建检循环独立并列。

对应路线图见 [`30-项目路线图.md`](../../30-路线图/30-项目路线图.md)；实施方案见 [`42-v0.6.0-召唤池重定义实施方案.md`](../版本实施方案/42-v0.6.0-召唤池重定义实施方案.md)。
