## 经验教训

### 1. `worker_sendSignal` 是 customTool，不是基础工具
- 定义在 `src/session.ts:196-200`（`makeWorkerSendSignalTool`）
- 注入点在 `src/session.ts:286-288`：`...(dteamContext ? [makeWorkerSendSignalTool(dteamContext)] : [])`
- `dteamContext` 由 `src/leaf.ts:37-40` 的 `execute()` 构建（取自 `ctx.dteam`），并通过 `createWorkerSession({ dteamContext: workerDteamCtx })` 传入
- **结论**：只有通过 `leaf.execute()` 派发的 worker 才会拿到这个工具；脱离主编排器上下文直接调起的 worker 拿不到

### 2. "用信号通路测信号通路"是鸡生蛋
任务本意是验证"双向信号通路"，但**验证手段本身**就是这条通路。结构性矛盾导致：
- 在 build 里调 → 工具不在 build 的工具集
- 在 close 里调 → 工具不在 close 的工具集
- 唯一能调的是 leaf 派发的真实 worker（build/explore/...），但这些 worker 的 systemPrompt 里没要求"自检信号通路"

### 3. "fresh" 上下文策略与工具注入的张力
close 的设计是 `defaultContext: fresh`（不继承父对话历史），目的是基于事实收口。
但 fresh worker 同样会丢掉"自己是被哪个 dteam run 派发的"这个上下文信息——而这正是 `dteamContext` 注入的**前置条件**。
**实际后果**：close 几乎不可能通过 `worker_sendSignal` 上报任何信号；它的"上报 progress"职责在当前实现下名存实亡。

### 4. 单元测试才是当前唯一可验证手段
`tests/signal-bus.test.ts` + `tests/signal-integration.test.ts` 覆盖了：
- `emit` 写入 + `getHistory` 读出
- `on` 监听器实时触发
- 多 worker 信号聚合
- progress / help / blocked 三种信号类型的通路

如果用户的真实需求是"验证双向信号通路工作正常"，**跑 `npx vitest run tests/signal-*` 即可**——已验证 20/20 通过。

## 踩坑记录

### 坑 1：build 和 close 都缺 `worker_sendSignal`
- 现象：上一步 build 报告工具不存在，本步 close 同样不存在
- 根因：两个角色的 systemPrompt 都提到"使用 worker_sendSignal 上报 progress"，但工具注入条件（`dteamContext`）在 fresh worker 上下文中不满足
- 影响：所有"按角色规范"要求上报信号的步骤，都会在工具调用阶段失败

### 坑 2：任务目标与可达手段不匹配
- 目标"用 worker_sendSignal 测试信号通路"在 build/close 角色下**结构性不可达**
- 设计上应当：用单元测试（已存在且通过）验证通路；或在 leaf worker 的 systemPrompt 里增加"自检信号"指令（不推荐，污染职责）

### 坑 3：close 的"上报 progress"职责形同虚设
- `agents/close.md` 写得很清楚："使用 worker_sendSignal 工具上报 progress 信号表示任务完成"
- 但实际跑下来 close 拿不到这个工具 → 主编排器收不到 close 的 progress → 编排器视角下 close 步骤"静默完成"
- **建议**：要么 a) 给 close 注入 dteamContext，要么 b) 把"上报 progress"从 close 职责里删掉，改用 step 状态机（`status: "done"`）隐式通知
