# 主代理运行中主动协调需求规格

> **状态：已实施并归档。** 本文记录该能力的产品与验收合同；实现与决策见 [ADR 0024](../../决策档案/0024-主代理运行中主动协调成为默认能力.md)。

## Problem Statement（问题陈述）

当前 dteam 能并发派发后台 worker，也会采集运行中的 `progress`、`finding`、实时文本、工具活动和阻塞请求，但非阻塞信息只进入 `/dteam` 与 Worker Snapshot。主 LLM 只能在 worker 主动请求、超时或结束后参与，且不能主动向 running worker 发送上下文、跨 worker 发现或纠偏指令。

因此，主代理虽然名义上负责路由、冲突裁决和收口，实际协作却主要发生在 worker 终态之间，整体更接近异步分发—汇合：中间事实无法及时改变其他正在进行的工作，跑偏或已经失去价值的 worker 也只能等待请求、超时或用户手动接管。

## Solution（解决方案）

将**主代理运行中主动协调**设为 dteam 的默认核心能力，补全现有星型协议的双向闭环：

1. worker 发现可能改变其他任务、当前路径、风险判断或下一步路由的事实时，以有界、带证据的**可行动发现（Actionable Finding）**通知主 LLM；普通进度仍只用于人类可观察性。
2. 主 LLM 在既定用户目标内判断该事实，可主动向一个或多个 running worker 发送上下文、跨 worker 发现、纠偏、收敛或停止指令，也可立即派发新的独立 worker。
3. 停止 worker 时优先要求其停止扩展并提交 `partial` 报告；若未及时收敛，主 LLM 可以强制取消。可写 worker 被强制取消后继续执行现有写入中断完整性守卫。
4. Worker Manager 只负责传递、生命周期和安全约束，不解释 finding、不选择接收者、不自动 steer、不自动派发下一轮。
5. 协调默认自主进行，不为常规技术路由阻塞用户；重要改派、强制取消和剩余风险在下一次自然回复或最终总结中说明。产品取舍、越界和不可逆风险仍由用户决定。

最终产品只保留这一套默认语义。实施期可以使用有退出条件的内部实验开关验证真实模型行为，但不得形成永久的“安静模式 / 协调模式”配置面。

## User Stories（用户故事）

1. 作为主代理，我希望在 worker 尚未结束时收到会改变路由的事实，从而能及时纠偏其他正在运行的工作，而不是等待整轮结束。
2. 作为主代理，我希望主动向 running worker 补充上下文、转发跨 worker 事实或要求收敛，从而真正承担协调责任。
3. 作为主代理，我希望先优雅停止不再需要的 worker，并在其不收敛时强制取消，从而减少无效成本且不牺牲写入安全。
4. 作为用户，我希望 dteam 自主处理既定目标内的技术协调，同时能在自然交互中看见重要改派、取消和未解决风险。
5. 作为用户，我希望普通进度不会持续唤醒主模型或制造轮询，从而保留 dteam 的成本与上下文优势。

## Confirmed Constraints（已确认约束）

- 可行动发现只表达可能改变其他任务、当前路径、风险判断或下一步路由的中间事实；普通 `progress`、实时文本、思考和工具活动继续只进入 UI / Snapshot。
- 可行动发现必须有界并携带可核验依据；不得转发完整 worker transcript、完整主会话或无证据的自由发散。
- 事件在主代理当前推理结束、进入 idle / settled 后合并交付，不中断正在进行的主模型调用；同一事件在显式等待与异步回放之间保持单次消费。
- 主 LLM 的主动指令只改变任务上下文与执行方向，不隐式增加工具、扩大预授权或绕过 `writeScope`。工具授权继续由 worker 请求并经现有策略校验。
- 主 LLM 可以对 running worker 发起优雅停止；强制取消只在优雅停止未及时收敛或任务已明确失去价值时使用，并保留终态、事件一致性和可写中断守卫。
- `dteam_wait` 仍只用于真实后续依赖，不作为默认进度查看或轮询手段。
- Worker Manager 不保存 batch、依赖图、任务计划或后续派发决定；worker 不 P2P。
- 主 LLM 在既定目标内自主协调；只有产品意图、风险承受、越界或不可逆取舍需要用户确认。
- 最终能力默认启用，不建立永久模式分叉；内部实验开关若存在，必须在验证完成后退出。

## Acceptance Criteria（验收标准）

- [x] running worker 能在终态前提交一条带证据的可行动发现；主 LLM 在下一安全轮次收到有界事件，普通 `progress` 不触发主模型轮次。
- [x] 多条短窗可行动发现会被有界合并或去重，不重复污染主上下文；同一 finding 不会同时由 `dteam_wait` 和异步 follow-up 重复交付。
- [x] 主 LLM 无需已有 `requestId` 即可向指定 running worker 发送主动指令；worker session 能在当前任务尚未终态时接收该指令。
- [x] 主动指令不能授予未预授权工具、扩大 `writeScope` 或携带完整 transcript；非法请求 fail-closed。
- [x] 主 LLM 能先要求 worker 停止扩展并提交 `partial` 报告；worker 合规收敛时，其已完成动作、事实、验证与剩余项仍可被主代理消费。
- [x] worker 未在有界窗口内优雅收敛时，主 LLM 能强制取消 running worker 并释放会话与并发槽；可写 worker 同步返回 `writeInterrupted` 守卫，且旧事件不会在收口后迟到回放。
- [x] 端到端场景可复验：worker A 在结束前报告影响 worker B 的事实，主 LLM 据此在 A 终态前主动纠偏 B；Worker Manager 全程不自动选择接收者或后续任务。
- [x] 主 LLM 不在派发后默认忙等；只有当前后续动作真实依赖 worker 事件时才使用 `dteam_wait`。
- [x] 重要改派、强制取消和仍未解决的风险会出现在下一次自然回复或最终总结中；常规协调不要求用户逐次批准。
- [x] 自动化测试与真实 Pi 冒烟均证明：事件降噪、单次消费、主动指令、优雅停止、强制取消和写入守卫共同成立。

## Out of Scope（非目标）

- 不恢复 Orchestrator Loop、TTL Signal Store、自发生长或 Manager 自动派发。
- 不增加 worker P2P、共享邮箱、竞争认领或 worker 自主改派。
- 不引入 batch、依赖图、持久任务计划、跨进程 resume 或 dgoal task 映射。
- 不引入 worktree、文件锁、自动 merge 或完整 Kimi Tower 工作流。
- 首版不新增通用 `inspect` / `status` 轮询能力；若主动事件闭环仍不能覆盖真实场景，再以独立证据重新论证。
- 不把工具数量、字段命名、事件合并算法或具体时间上限固化为产品需求；这些由实现阶段在本合同内收口。

## Further Notes（补充说明）

本需求会增加主模型轮次与上下文压力，也可能因 worker 漏报或误报而错过协调窗口。实现必须以真实多 worker 场景验证“及时性收益是否高于新增成本”，并保留可观测的事件与主动控制轨迹。若数据证明可行动发现仍频繁制造噪声，应收窄触发条件，而不是回退为轮询或恢复自动编排。

## 实施验证记录

- **实现范围**：新增带 `summary` / `evidence` / `impact` 的 `finding` 事件与有界合并去重；新增严格 schema 的 `dteam_control`，支持 `steer`、`graceful_stop`、`cancel`；主动取消区分 `cancelInitiator="main"`，并沿用 `writeScope` 中断守卫与旧事件清理。
- **自动化证据**：`npm test` 覆盖前置回归与端到端协调场景；定向测试通过，包含 finding 单次消费、control 生命周期、graceful_stop、主代理取消来源与结果投影。
- **真实 Pi 冒烟结果**：主代理执行一次 `dteam_dispatch` 派 B(T1) 与 A(T3)，第一次 `dteam_wait` 只等待 A 并消费 A 的 finding；随后 `dteam_control(steer)` 对当时 `running` 的 B 成功返回。B 停止剩余核对并提交 `outcome="partial"` 报告，报告包含“安全路径”和“纠偏”。第二次 `dteam_wait` 同时等待 A/B，但实际先消费 B 的 `completed` 事件；第三次 `dteam_wait` 单独等待 A，消费 A 的 `completed` 事件。临时原始 JSONL 仅用于本轮调试，不是本归档的唯一证据。
- **边界核对**：冒烟未修改项目文件；B 使用默认只读 `read` 保持运行，未因主动控制获得额外工具或写入权限。`addTools` 仍是候选权限，须经 worker request 与主代理 `dteam_respond(grant_tools)` 激活。

## 可复现的真实 Pi 冒烟步骤（脱敏、有界）

在上述 checkout 中执行以下命令；它只使用默认只读 worker 工具，不修改项目文件：

```bash
pi --no-extensions -e ./index.ts --no-skills --no-session \
  --model openai-codex/gpt-5.6-terra:high --mode json \
  -p '派发两个 worker，顺序为 B(T1)、A(T3)，不要 addTools。B 读取 src/runtime/signal-tool.ts 和 index.ts 后，对 src/runtime/signal-tool.ts 做 30 次独立 read；在主代理 dteam_control 前不得 report/request signal，收到 steer 后停止并提交包含“安全路径”和“纠偏”的 partial WorkerReport。A 读取 src/runtime/types.ts、src/runtime/worker-manager.ts、src/runtime/signal-tool.ts 后立即提交 finding，summary/evidence/impact 分别说明 control 只允许 running worker、引用 worker-manager.ts:247-254、说明过晚控制会 fail-closed；finding 后再读取 report-tool.ts、request-state.ts、signal-log.ts，完成后提交报告。主代理只 wait A；收到 finding 后立即以 {workerId:B 的真实 ID, action:steer, instruction:依据 A 的发现改走安全路径并在报告中说明已执行该纠偏} 调 dteam_control；control 成功后第一次 wait A、B，若只消费 B 的 completed 事件，则继续第二次只 wait A，直到 A completed。最终只报告四项：finding 早于 A 终态、control 返回 state=running、B 报告包含安全路径和纠偏、A/B 终态事件的实际消费顺序。'
```

复现时按标题 `A` / `B` 绑定 dispatch 返回的随机 worker ID，不把随机 ID 写入耐久文档。只保留以下四条有界断言作为证据：

1. 第一次 `dteam_wait` 的 `events[0].type` 为 `finding`，且该事件返回时 A 的 Snapshot 仍为 `running`；A 的最终 `completed` 事件尚未消费。
2. 紧随其后的 `dteam_control` 返回 `{ action: "steer", state: "running" }`，没有 `requestId`，且没有工具授权或 writeScope 变化。
3. 第二次 `dteam_wait` 以 A/B 为目标但实际只消费 B 的 `completed` 事件；B 的 `report.outcome` 为 `partial`，其 summary/facts/verification 至少一处同时出现“安全路径”和“纠偏”，并记录停止剩余核对的 `verification.remaining`。
4. 第三次 `dteam_wait` 单独以 A 为目标并消费 A 的 `completed` 事件；因此实际终态消费顺序为 B 后 A，而不是一次 wait 同时消费 A/B。

本次实际冒烟的脱敏结果摘要与上述四条断言一致；不归档完整会话 transcript、prompt 回显、usage、随机 ID 或原始 JSONL。
