# v0.6.0 真实运行探测报告

> **状态**：0.6 探测完成（2026-06-21，历史）
> **历史注记（2026-07-14）**：本文记录的 runLoop、Signal Store、五角色、check 收口与插桩问题只对应已删除的 0.6 runtime；“待修复”结论不适用于当前 T1/T2/T3 `dteam` worker、`/dteam` 管理命令和 0.8 runtime。
> **探测方式**：`pi -ne -e ./index.ts` 隔离加载，glm-5.2 + minimax-m3 双模型对照  
> **探测范围**：扩展加载 → 工具注册 → runLoop → Orchestrator 决策 → summon worker → check 收口  
> **目的**：在写整体修复方案前，把真实运行暴露的所有问题一次性挖全，停止单点打地鼠。

## 0. 探测结论（一句话）

**dteam 0.6.0 的 loop 骨架能跑通，但"决策-执行-收口"这条主链上有 5 处会让整个 goal 失败或失控的缺陷；它们彼此关联，必须整体修复，不能逐个补丁。**

## 1. 已验证可用的部分（别动）

这些在 glm-5.2（pi 0.79.9 修复 #5770/#5923 后）和 minimax-m3 下都正常：

| 环节 | 证据 |
|---|---|
| 扩展加载 | `pi -ne -e ./index.ts` 成功，import 链完整 |
| 工具注册 + 主 LLM 调用 | dteam 工具被主 LLM 正确调用 |
| `runLoop` 启动 | START 日志稳定出现 |

| explore → check 衔接 | Orchestrator 能据 explore 产出决策进 check（minimax 实测 round2） |

**结论：loop 的骨架是通的。** 问题全在"决策-执行-收口"的健壮性上。

## 2. 探测到的缺陷清单（按严重度）

### P0-1 Orchestrator 决策 JSON 解析不健壮（闭环阻断器）

**现象**（glm-5.2 多次复现）：
- `decide raw text len=264: ```json` → round 1 直接 `fail`，整个 goal 6 秒失败
- LLM 输出 ```` ```json ```` 开头但内容被截断（token 限制 / task 字段过长），**没有闭合的 ```**

**根因**（`src/orchestrator-loop/decision.ts` `extractJSON`）：
```ts
const fenceMatch = text.match(/```(?:json)?\s*([\s\S]*?)```/);  // 要求闭合 ```
const braceStart = text.indexOf("{");
const braceEnd = text.lastIndexOf("}");  // 截断时找不到闭合 }
```
两条路径都要求"完整闭合"，截断时全失败 → 返回 `fail`。

**影响**：这是当前 **goal 无法收口**的头号原因。任何让 Orchestrator 输出变长的情况（复杂 goal / 详细 task）都会触发。

**观测证据**：
- glm-5.2 短 goal "check 角色职责" → 多次 `len=264~337` 的截断输出
- minimax 复杂 goal → `len=900+` 的超长 task，同样截断

### P0-2 Orchestrator 越权扩大目标（让 build 写仓库）

**现象**（minimax + glm-5.2 都复现）：
- goal = "说明 check 角色职责"（**纯只读信息任务**）
- Orchestrator 却召唤 `build` 角色，指令是"写入 `doc/agents/*.md`" / "写入 `docs/check-role.md`" / "写入 `/tmp/check_role_dump.md`"
- **worker 真实执行了，写出了 5 个文件到 `doc/agents/`**（已清理）

**根因**：
1. Orchestrator system prompt（`buildOrchestratorSystemPrompt`）没有"禁止为只读目标召唤可写角色"的约束
2. `build` 角色工具含 `edit`/`write`，但没有"目标性质 vs 角色能力"的校验
3. Orchestrator 把"探索结果没拿到完整文件"误判成"需要落盘固化"

**影响**：违反 ADR 0005 + `build` 角色边界；**最危险**——dteam 会擅自修改用户仓库。这次只是写了 doc 文件，下次可能改代码。

**观测证据**：`doc/agents/{build,check,close,design,explore}.md` 5 个文件被真实创建（17:46 时间戳，与 smoke 跑动时间吻合）。

### P0-3 worker 被工具上限中断后，Orchestrator 无感知、盲目重试

**现象**（maxToolRounds=8 生效后）：
- explore worker 因 8 次工具调用被中断，输出带 `[worker 因工具调用上限被中断]` 标记
- 但 Orchestrator **反复召唤同类 explore**（日志4：round 1-8 连续 8 次 explore，全被中断）
- Orchestrator 的 reason 甚至自己写出了"前 N 轮 explore 均因工具调用上限中断"——**说明它从 summonTrail 看到了中断，但不知道该怎么调整**

**根因**：
1. `buildOrchestratorUserPrompt` 把 worker 结果 truncate 到 300 字符，中断标记虽在但被淹没
2. summonTrail 没有"worker 被中断"的结构化状态（只有 done/failed/running/skipped）
3. Orchestrator system prompt 没有"连续失败 N 次应换策略"的规则

**影响**：maxToolRounds 防住了"无限工具调用"，但没防住"无限召唤被中断的 worker"——把一个死循环换成了另一个。

### P0-4 check 收口判定全靠脆弱启发式

**现象**（代码审查，未真实触发 passed）：
- `parseCheckResult` 判定 passed 的逻辑：显式 JSON → 关键词兜底（含"通过/pass/✓"=pass，含"失败/fail/✗"=fail）
- 关键词正则有误判风险："未通过"含"通过"会先匹配 pass（代码用 fail 优先级更高补救，但仍脆弱）
- check worker 的输出格式**没有任何契约约束**——LLM 可能写一大段自由文本，关键词匹配全靠运气

**根因**：check 角色 prompt（`agents/check.md`）没有要求结构化输出，判定层只能猜。

**影响**：即使 check worker 正常返回，passed 判定也不可信。可能误判通过（放过未完成的工作）或误判失败（无限重试）。

### P1-1 explore 角色 prompt 诱导过多工具调用

**现象**（glm-5.2）：explore 8 次工具调用都没读完一个 `check.md`（2.5KB 小文件）。
**根因**：`agents/explore.md` 的 prompt 非常发散（"入口识别/依赖映射/数据流追踪/技术栈确认/文件清单/联网搜索/同类项目/风险识别..."），诱导 worker 做远超必要的探索。
**影响**：放大 P0-3，让 maxToolRounds 频繁触发。

### P1-2 Orchestrator 决策输出无长度约束

**现象**：Orchestrator 生成的 task 字段动辄 400-700 字符（带 1)2)3)4)5) 详细步骤）。
**根因**：`buildOrchestratorSystemPrompt` 没有约束 task 简短。
**影响**：放大 P0-1（task 长 → JSON 长 → 截断）。

## 3. 还没探到的路径（已知盲区，整体方案需考虑）

- **help 自愈路径**：worker 发 help → explore 补充 → 注入回 worker。完全没真实触发过。
- **done 收口路径**：check passed 后 Orchestrator 产出 done。代码有"强制 Completion Gate"（done 前必须有 checkConclusion.passed），但没真实跑通。
- **并发召唤**（parallel>1）：AdaptiveConcurrency 代码在，但日志显示 Orchestrator 用过 parallel=2/5，实际并发行为没验证。
- **Multi-Provider Routing**：modelOverrides/fallbackModels 完全没真实测过。

## 4. 缺陷间的关联（为什么必须整体修）

```
P1-1 explore prompt 发散 ──┐
                          ├──→ P0-3 worker 频繁触发工具上限 ──→ Orchestrator 盲目重试
P1-2 task 无长度约束 ──────┤
                          └──→ P0-1 JSON 截断解析失败 ──→ goal 直接 fail
P0-2 越权扩大目标 ─────────────→ build 改仓库（独立但同源：Orchestrator prompt 缺约束）
P0-4 check 判定脆弱 ───────────→ 即使前面都通，收口不可信
```

**核心共性**：P0-1/P0-2/P0-4 + P1-2 **都源于"Orchestrator/check 的 prompt 与解析层没有契约"**——prompt 不约束输出格式，解析层就只能猜，猜错就 fail 或失控。这是**一个根因，四个症状**。

P0-3 + P1-1 是另一组：**"worker 执行没有收敛机制 + Orchestrator 没有失败感知"**。

## 5. 给整体修复方案的关键约束

1. **不要只修解析层**（P0-1）：只让 JSON 解析容错，P0-2 越权、P0-3 盲目重试还在。
2. **Prompt 契约是核心**：Orchestrator 和 check 的输出必须结构化（用 Pi 的 tool calling 或严格 JSON schema），解析层配合契约，而不是解析层去猜自由文本。
3. **必须有"目标性质 → 角色能力"约束**：只读目标不能召唤可写角色（防 P0-2）。
4. **必须有"连续失败 → 换策略/收口"机制**（防 P0-3）。
5. **explore prompt 要收敛**（防 P1-1），但不能一刀切限制（真探索任务需要多读文件）。
