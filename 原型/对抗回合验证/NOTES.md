# 原型问题

**这个原型要回答什么**：ADR 0007 的积分制对抗回合，在**真实模型**下能不能收敛、分数可不可信、token 代价多大。

## 为什么需要原型（纸面看不出的）

纸面设计里，以下几件事无法靠推理验证，必须真模型跑：

1. **收敛性**：5 分上限 / 3 轮下限，真实对抗下会不会出现"永远各有千秋、凑不齐 5 分"？还是过早收敛到某一个？
2. **打分一致性**：close 用 fresh 子进程打分，同一组方案打分稳不稳？还是每次乱跳、分不可信？
3. **方差来源**：N design 用不同模型 + 不同 prompt 偏好，真制造出"有得选"的方差了吗？还是趋同？
4. **token / 时间代价**：一个合议单元走完大概多少 token、多少秒？这决定 dteam 实际可用性。

## 不验证的（纸面已够）

- 积分 reducer 的算术对不对（纯逻辑，推理即证）
- 状态机合法性（纯逻辑）

## 形状

逻辑原型：一个 TS 程序，跑一个真实的合议单元。每个角色（explore / N design / build / check / close）都是一次 `pi -p` 真模型调用。每轮打印完整状态：各 design 方案摘要、反方质疑、本轮分数、累计分、收敛判断。

## 运行

```bash
cd 原型/对抗回合验证
bun run run.ts "<goal>"            # 用默认模型群
bun run run.ts "<goal>" --mock     # 不调真模型，走确定性 mock，验证状态机流转
```

需要 `pi` 在 PATH 且配过 provider（507 环境已满足）。

## 模型配置（制造 design 方差）

N design 用不同模型 + 不同 prompt 偏好：
- design A：模型 X + "稳健、重风险、最小改动" 偏好
- design B：模型 Y + "激进、重突破、敢于重写" 偏好
- design C（可选）：模型 Z + "务实、重落地成本" 偏好

具体模型 ID 从 `pi --list-models` 选三个不同族。见 `run.ts` 顶部常量。

## verdict（2026-06-27 原型验证后的感受）

### 原型回答了什么

跑了多轮真实模型（先是多模型：M3/kimi-k2.7/deepseek-v4-flash；后改为全 glm-5.2 验证单模型根基）。

**成立的部分**：
- **单模型靠 prompt 偏好也能制造可分辨方差**：即使全用同一个 glm-5.2、只靠 stance（稳健/激进/务实）区分，三个 design 出的方案确实有可分辨差异——稳健派守边界、激进派推翻重做、务实派重落地成本。close 的 selection 确实能分出胜负、给出像样的裁决理由。积分制的物理基础（方差来源）成立，不是空中楼阁。
- **打分分档有效**：tie_or_minor / none 区分出来了；裁决理由能解析出来且言之有物。
- **close 没有明显的同模型偏好污染**（第 1 轮 close=M3 给 D1=M3 只打 tie_or_minor，没独抬高分）——但样本太少，不能下结论。

### 原型暴露的核心问题（比成本更深的）

**积分制是个天生贵的机制。** 每轮 6 次调用 × 至少 3 轮，就算 provider 不限流、就算 thinking 关掉、就算 spawn 改成真异步并行，一个合议单元也是几分钟起步。这不是实现没调好，是机制本身的成本量级。

**而我（agent）之前在 ADR 0007 里把它写成 dteam 的默认收口**——这里要诚实承认：它不该是所有 dteam 任务的默认走法。把一个改 README 的活塞进 3 轮 5 分制，是大炮打蚊子，还会制造新的不确定性（用户不知道"我这个任务值不值得等几分钟跑积分"）。

### 最深的感受（需要警惕的）

507 一开始说"越努力越没用"。现在要警惕：积分制会不会是这句话的新版。0.6.0 的错是"把确定性当敌人"，我改成积分制把确定性找回来了——但会不会把成本当成了可接受的代价？一个机制如果默认让用户等几分钟、烧几十次调用，它会再次走向"我自己都不愿意用"。这正是 507 最初说的症状。

**507 的回应（2026-06-27）：的确像你说的一样。会有些迷茫我们是不是该往这个方向继续走，一次这么重的负载最终只是产出一个方案，似乎成本和最终收益不成正比。**

### 判断（待与 507 对齐，未拍板）

倾向：**积分制不要做成 dteam 的唯一/默认收口，而是"可选的重决策档"**。轻任务走更简单的路径（甚至退回"一次 design + 一次 close"的轻量合议），只有当决策真的值得对抗时才拉起完整积分制。这是对 ADR 0007 的一个待确认修正——它现在写成了"每个合议单元都走多轮积分"，但更准的可能是"积分制是重决策档，轻决策有轻档"。

### 原型暴露的工程问题（次要）

- spawnSync 阻塞导致"并行"变串行——已改 spawn 异步。
- zai-coding-cn/glm-5.2 provider 在密集调用后会限流（单次从 13s 涨到 68s）——验证要换通道或冷却。
- 裁决理由解析正则在某些 close 输出格式下匹配失败——可修。
- kimi-k2.7 在 --thinking off 下输出不稳/为空——多模型路径的脆弱性，反过来印证"单模型也能做"是对的。

### 是否吸收进正式代码

**暂不吸收。** 核心机制方向待与 507 重新对齐（见上"判断"）。原型的 scoring.ts（纯积分 reducer）是可移植的，待方向定了再决定是否吸收。原型壳保留备查。
