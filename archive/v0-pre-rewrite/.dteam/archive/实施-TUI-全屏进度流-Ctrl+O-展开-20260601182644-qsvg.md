## 阶段记录### 探索发现（2026-06-02 增量）

> 触发场景：用户报告 TUI widget 显示 `Tools: 0` `Elapsed: 0.0s` 永远不动。本节为新发现的补充，不覆盖原有「探索发现」内容。

#### 1. 内部代码事实（断点定位）

**`AgentProgress` 数据源已就绪（`P1/spawn.ts:23-30`）**

```ts
export interface AgentProgress {
  startTime: number;
  currentTool?: string;
  recentOutput: string;       // 后 500 字
  tokenCount: number;
  status: "running" | "tool" | "done" | "error" | "aborted";
}
```

**`spawnAgent` 回调钩子已存在（`P1/spawn.ts:43-46, 230-242`）**

- `onUpdate?: (partial: { output, progress?: AgentProgress }) => void` — text_delta 触发
- `onToolEvent?: (event: { type: "start"|"end"; toolName?; progress? }) => void` — tool 事件触发
- handleTextEvent / handleToolEvent / handleTurnEnd / handleMessageEnd 四类处理器均已挂上

**🔴 关键断点（`P2/worker.ts:193-211`）**

调 `spawnAgent({...})` 时**完全没传 `onUpdate` / `onToolEvent`**。闭包执行器 `executorFn(context)` 直接调 `spawnAgent`，没有任何流式回调穿出 → widget 永远收不到工具调用/文本增量。

**🔴 widget 是「瞬时快照」模型（`P4/worker-widget.ts:99-117`）**

- `showWorkerStatus` 只在 `worker_start` 调一次（`P4/index.ts:125-130`）
- 节流是 throttle 不是 interval — 没有外部触发源就不重绘
- 传进去的 `elapsedMs: 0`、`toolCount: 0` 永远是初始值
- 没保存 `tui` 引用，没法在外部调 `requestRender()`
- 工厂返回的 Component 没实现 `dispose()`，interval 即使加上也清不掉

**🔴 三套并行的进度通道不互通**

| 通道 | 数据源 | 触发点 | 消费者 |
|---|---|---|---|
| Widget (`P4/worker-widget.ts`) | `WorkerWidgetState` | `wrapWorker` start 分支 | `ctx.ui.setWidget` |
| Status bar (`P4/renderers.ts:73-79`) | `workerProgress: Map<id, ...>` | `dteam:render-status` 事件 | `ctx.ui.setStatus("dteam", ...)` |
| Renderer (`P4/renderers.ts:48-71`) | 解析消息流 `[DTEAM_PROGRESS]` | 主 LLM 主动 emit | 聊天行 `● [running] task` |

`emitWorkerProgress`（`renderers.ts:131-145`）只改 Map + emit 事件，**完全没碰 widget**。

#### 2. TUI 接口与官方模式

**`setWidget` 签名（`@earendil-works/pi-coding-agent/dist/core/extensions/types.d.ts`）**

```ts
setWidget(key: string, content: ((tui: TUI, theme: Theme) => Component & {
    dispose?(): void;
}) | undefined, options?: ExtensionWidgetOptions): void;
```

- 工厂里**能抓住 `tui` 引用** → 外部状态变化时调 `tui.requestRender()` 即可触发 widget 重绘
- Component 有可选 `dispose()` → 是清理 interval / 清空 tui 引用的官方钩子
- 必须在 `invalidate()` 时清缓存（theme 切换会触发）
- 渲染 `[]` 自动隐藏 widget（joelclaw 验证）

**官方实时刷新模式**（参考 `examples/extensions/border-status-editor.ts`、`dist/modes/interactive/components/countdown-timer.ts`）：

```ts
pi.on("session_start", (_event, ctx) => {
  ctx.ui.setWidget("my-widget", (tui, theme) => {
    activeTui = tui;  // 抓住引用
    const timer = setInterval(() => activeTui?.requestRender(), 1000);
    return {
      render(width) { /* ... */ },
      invalidate() {},
      dispose() { clearInterval(timer); activeTui = undefined; },
    };
  });
});
```

#### 3. 外部最佳实践

**JoelClaw `inngest-monitor` 案例（joelclaw.com/extending-pi-with-custom-tools）** — 完整工程级参照：

- 工厂抓住 `widgetTui`，调 `widgetTui.requestRender()` 触发更新
- 状态变化（含 5s 轮询）只改 Map + 调 requestRender
- `dispose` 清空 `widgetTui = null`
- 多 run 场景用 `Map<runId, Timer>` 跟踪，render 时按状态着色
- 后台完成时 `pi.sendMessage({ customType, display: false, ... }, { triggerTurn: true, deliverAs: "followUp" })` 把结果推给主 LLM 而不刷屏

**`@firstpick/pi-extension-todo-progress`（pi.dev 收录、903 downloads/月）** — Todo widget 模式，验证了「reactive widget + 状态正则解析」的可行性。

#### 4. 约束与风险

| 风险 | 说明 | 应对 |
|---|---|---|
| **多 worker 并发** | 现有 `showWorkerStatus` 是个全局 widget key `dteam-worker`，多 worker 同时跑会互相覆盖 | 改 key 为 `dteam-worker-${workerId}`；用 `Map<workerId, tuiRef>` 跟踪；render 时只画自己 |
| **tui 引用失效** | session 重启时旧 ctx 失效，旧 `widgetTui` 已无意义 | dispose 必须清；`session_start` 重新注册 |
| **节流 vs interval 叠加** | 现有 throttle 1s + 新增 1s interval，理论双触发 | throttle 改为 interval 内部消化；外部事件优先（实时） |
| **dispose 链** | setWidget(undefined) 会触发 dispose，setWidget(new) 也会触发旧 dispose | 把 interval 清理 / Map 删除都放进 dispose |
| **worktree 隔离下的 cwd** | 后台 worker 在 worktree 里跑，进度回调闭包需要捕获原 ctx | `executeInBackground` 已用 `worker.abortController.signal`，加回调时复用同一闭包 |
| **renderer ↔ widget 数据源分裂** | 三套进度通道不一致会让用户看到"widget 是 A，status bar 是 B" | 设计上合并：让 `emitWorkerProgress` 同时驱动 widget 和 status |
| **公共/私有 API 边界** | `P4` 是用户接口层，`P2/worker.ts` 调 `showWorkerStatus` 会破坏分层 | 通过 P3/事件总线 / P2 注入 callback，**不要**让 P2 直接 import P4 |

#### 5. 建议方向

**短（最小可行修复，让 Elapsed 跳起来）**

- `P4/worker-widget.ts`：
  - 工厂抓住 `tui`，存为模块级 `let activeTui: TUI | undefined`
  - Component 内部 `setInterval(..., 1000)` 调 `activeTui?.requestRender()`
  - 实现 `dispose()` 清 interval + 清 activeTui
  - `render()` 内 `elapsedMs` 改成 `Date.now() - this.startTime`（不再吃入参）
- `P2/worker.ts` 默认 executor：`spawnAgent({...})` 补 `onUpdate` / `onToolEvent` 回调
- 回调里 `showWorkerStatus(ctx, { ...state, toolCount: ++toolCount, currentTool, elapsedMs: now - startTime })`

**中（数据通路贯通）**

- 引入 P3 进度事件总线 `worker.progress` 事件，dteam 总线统一分发
- `emitWorkerProgress` 改为既发事件又驱动 widget
- worker key 改 `dteam-worker-${workerId}` 支持多 worker
- 拆 `workerWidgetState` 模块为可被 P2 注入的纯函数

**长（架构统一）**

- 合并 widget / status / renderer 三套数据源为单一 store
- 折叠态（bordered box）/ 展开态（Ctrl+O 全屏）共用 store，按模式取视图
- 与现有 task `qsvg` 目标一致（Ctrl+O 展开）— 探索发现可被 design 阶段直接消费
