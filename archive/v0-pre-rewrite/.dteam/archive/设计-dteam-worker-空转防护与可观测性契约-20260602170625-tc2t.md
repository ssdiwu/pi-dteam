## 目标
- 为什么: 当前现象表明 dteam worker 可在无有效产出的情况下快速失败并丢失诊断上下文，需要从设计层面建立参数校验、失败写入、链路可观测性与默认编排兜底，避免再次进入无效循环。
- 做什么: 设计并收敛一套 worker 空转防护方案：1) 明确 worker_create/worker_start 的必填参数与校验规则；2) 定义失败路径的诊断数据落点（共享内存/错误输出/状态字段）；3) 固化 LLM 调度入口与自动编排(task→chain plan)间的输入输出契约；4) 给出回归测试与验收标准，确保后续实现可按此方案一次性修复并验证。

## 范围- 包含:
  - worker_create / worker_start 的必填参数、校验与默认值策略设计
  - 失败路径的诊断落点设计（共享内存、错误文本、状态字段、日志）
  - LLM 调度入口(dteam 工具)与自动编排(task→chain plan)的输入输出契约
  - 回归测试与验收标准（可直接转实施任务）
- 排除:
  - 直接代码实现
  - 重构整个 dteam 架构
  - 新增角色或新编排模式
  - 环境级别的 LLM 账号/密钥排查

## 阶段记录### 探索发现
- 设计目标不是"更聪明的 LLM"，而是"更快失败且失败可解释"：当前空转问题本质是链路在缺信息时仍启动执行，并在终态只保留 status=failed，不留结构化根因。
- 现有代码已经具备关键主链路：worker_create → worker_start → executor/spawnAgent → runWorker → 契约回调/共享内存（见 `src/P2/worker.ts`、`src/P3/worker.ts`、`src/P4/index.ts`、`src/P4/dteamTool.ts`），说明问题更多在"契约薄弱"而非"链路全缺"。
- 与历史修复经验一致：之前就出现过因 role/model/sessionModel 注入缺失导致大量 `spawn/error.md` 的情况（归档：`修复-worker_create-的-model-注入逻辑-20260602135829-gqpz.md`），提示当前需优先固化参数解析与兜底策略。
- 运行时与测试状态出现分离信号：代码测试仍全绿（19 文件 / 258 测试通过），但实际 worker 运行快速 failed 且共享内存无键，指向"运行时入口参数或执行契约未被现有单测充分覆盖"。
- 架构评估结论（基于当前约束）：优先采用"最小侵入可逆方案"——先加强参数校验与失败可观测，再补调度入口与自动编排契约，而不是重写 worker 架构。

### 讨论决策
- **D1 Fail-fast + 结构化错误输出**：worker_start 在参数不完整（无 workerId/找不到 worker/关键上下文缺失）时，直接返回可机器解析的错误对象，并同步写入共享内存（如 namespace `worker:<id>` 下的 `lastError`/`lastStatus`）。
- **D2 参数默认策略显式化**：role/model/sessionModel 解析固定为三级链：`config显式值 → dconfig角色配置 → 会话模型(ctx/sessionModel)`，并把每级命中结果记录到诊断上下文，避免"静默为空"。
- **D3 调度入口契约**：dteam(plan/run) 的输出至少包含 `workerId`、`mode`、`agents[]`、`taskId/chainPlan`，任何字段缺失都不允许进入 worker_start。
- **D4 自动编排契约**：task→chain plan 必须保证每个 step 都有可执行描述与角色，空描述/空角色直接拒绝执行并提示修正方式。
- **D5 观测层最小集**：无论成功失败，都沉淀一组最小键：`status`、`startedAt`、`endedAt`、`lastError`、`lastPhase`、`lastModel`，保证事后可复盘。
- **D6 回归测试策略**：新增三类最小 case：(a) 缺必填参数失败；(b) 模型解析失败；(c) 自动编排产出空 step；以避免"逻辑测试通过但运行时仍空转"。

#### 决策取舍（ADR 简版）
- **采用**：可逆、低侵入的"加强契约+可观测"方案。
- **否决**：先大改 worker 架构/重写调度器（当前信息不足以支撑，且成本收益差）。
- **风险**：过度校验可能影响灵活性；通过"校验规则集中在 P2/P4 且附清晰错误提示"缓解。
