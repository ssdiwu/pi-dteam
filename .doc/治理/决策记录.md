# 决策记录

> **定位**：dteam 的已确认决策记录。

## 决策清单

### D01：项目命名

**决策**：项目命名为 dteam

**理由**：
- 更简洁
- 更直观
- 避免与 dflow 混淆

### D02：概念重命名

**决策**：
- dworker → worker
- dsolo → solo
- dchain → chain
- dteam → team

**理由**：
- 更简洁
- 更直观
- 去掉 d 前缀

### D03：存储格式

**决策**：使用 Markdown 格式存储 task

**理由**：
- 对人类更可读
- 对 AI 也更友好（通过工具只读需要的部分）
- 不需要 TOML 的结构化约束

### D04：存储结构

**决策**：
```
.dteam/
├── task/                          # 活跃任务
├── archive/                       # 归档任务
└── pitfalls/                      # 经验库（可选）
```

**理由**：
- 清晰的目录结构
- 支持归档机制
- 支持经验库（可选）

### D05：文件命名

**决策**：`{name}-{timestamp}-{random4}.md`

**理由**：
- 包含任务名称，便于人类阅读
- 包含时间戳，便于排序
- 包含随机字符，防碰撞

### D06：TaskStage

**决策**：todo / InSpec / InProgress / Done / Cancelled

**理由**：
- 简化状态机
- 保留关键状态
- 支持探索阶段

### D07：TaskType

**决策**：functional / ui / bugfix / refactor / infra

**理由**：
- 5种类型覆盖常见场景
- 与 dflow 保持一致

### D08：去掉 parent_dfeat

**决策**：去掉 parent_dfeat 字段

**理由**：
- dteam 是独立的项目
- 不依赖 dflow 的概念
- task 是独立的工作单元

### D09：去掉 assignee

**决策**：去掉 assignee 字段

**理由**：
- 运行时决定
- 任务过程中可能会随时切换 worker
- 不需要提前写好分配

### D10：worker 定义位置

**决策**：worker 基本概念在 P0，角色定义在 P2

**理由**：
- P0 定义数据模型（worker 的三种模式）
- P2 定义角色执行（6个角色）
- 职责分离清晰

### D11：保留dflow历史引用

**决策**：决策记录中保留dflow的历史引用

**理由**：
- 这些是历史决策记录，解释决策背景
- 保留可以追溯设计演变过程
- 帮助理解为什么做出某些选择
