# 信号类型

> **定位**：dteam 的原子层。定义所有信号类型，不依赖其他概念。

## 一句话

信号是 dteam 的**通信协议**——每种信号类型代表一种语义，worker 通过它报告状态、请求帮助、分享发现。

## 信号类型全景

### 总览（9种）

| 类别 | 信号 | 说明 |
|------|------|------|
| **信号** | progress, blocked, found, help | worker 之间的通信 |
| **策略** | retry, adjust, switch, replan, learn | worker 内部的恢复机制 |

### 信号（4种）

| # | 信号 | 谁发 | 含义 | 使用场景 |
|---|------|------|------|---------|
| 1 | `progress` | worker | 报告进度 | worker 报告执行进度、阶段性成果 |
| 2 | `blocked` | worker | 遇到阻塞 | worker 无法继续执行，需要外部介入 |
| 3 | `found` | worker | 发现信息 | worker 发现对其他 worker 可能有价值的信息 |
| 4 | `help` | worker | 请求帮助 | worker 需要其他角色或用户的帮助 |

### 策略（5种）

| # | 策略 | 触发条件 | 动作 |
|---|------|----------|------|
| 1 | `retry` | 瞬时错误 | 重试 |
| 2 | `adjust` | 参数错误 | 调整参数后重试 |
| 3 | `switch` | 工具不适合 | 切换工具 |
| 4 | `replan` | 计划根本错误 | 重新规划 |
| 5 | `learn` | 任何失败 | 记录经验到 pitfalls |

## 信号详细说明

### 1. progress — 报告进度

**语义**：worker 正在执行，报告阶段性进展。

**使用场景**：
- maker-checker 模式中，maker/checker 完成各自任务后发出
- adaptive 模式中，planner/executor/evaluator 完成后发出
- chain 模式中，每步完成后发出

**payload 结构**：
```typescript
{ output: string }       // 执行结果
{ plan: string }         // 规划结果
{ evaluation: string }   // 评估结果
```

**响应**：记录进度，不阻塞。

---

### 2. blocked — 遇到阻塞

**语义**：worker 无法继续执行，原因是环境/依赖/权限等外部问题。

**使用场景**：
- spawnAgent 返回错误且策略链无法恢复时
- maker/checker/planner/executor/evaluator 任一执行失败时
- team 的 worker 执行抛出异常时

**payload 结构**：
```typescript
{ error: string }       // 错误描述
{ reason: string }      // 阻塞原因
```

**响应**：尝试自动解决（策略链）。

**与 `help` 的区别**：`blocked` 表示"我搞不定了"；`help` 表示"我需要别人帮一下"。

---

### 3. found — 发现信息

**语义**：worker 在执行过程中发现了对其他 worker 有价值的信息。

**使用场景**：
- explorer 发现了相关代码位置
- worker 发现了潜在的 bug 或改进点
- 搜索过程中找到关键文档

**payload 结构**：
```typescript
{
  finding: string;       // 发现内容
  relevance?: string;    // 与谁相关
  location?: string;     // 文件/代码位置
}
```

**响应**：记录发现，判断是否需要新开 worker 处理。

---

### 4. help — 请求帮助

**语义**：worker 需要其他角色或用户的帮助才能继续。

**使用场景**：
- chain 某步执行失败，需要链级别的干预
- worker 需要其他 worker 的中间结果
- 遇到歧义，需要用户做决策

**payload 结构**：
```typescript
{
  step: number;          // 出错步骤
  agent: string;         // 出错角色
  error: string;         // 错误描述
}
```

**响应**：上层处理（决定是否派更多 worker、调整任务描述或人工介入）。

**与 `blocked` 的区别**：`help` 仍有解决意愿，只是缺资源/信息；`blocked` 是完全卡住。

---

## 策略详细说明

### 策略链流程

```
worker 发出 blocked
    │
    ▼
worker 接收 blocked
    │
    ├── 尝试 retry → 成功 → 继续
    │
    ├── 尝试 adjust → 成功 → 继续
    │
    ├── 尝试 switch → 成功 → 继续
    │
    ├── 尝试 replan → 成功 → 继续
    │
    └── 全部失败
          │
          ├── 有上层 → worker 发出 help → 上层处理
          │
          └── 无上层 → 任务失败
```

### 1. retry — 重试

**触发条件**：瞬时错误（网络抖动、模型暂时不可用）

**动作**：用相同参数重试当前任务

**payload 结构**：
```typescript
{ iteration: number }   // 当前迭代次数
```

**响应**：通常自动处理，无需人工干预。

---

### 2. adjust — 调整参数

**触发条件**：参数错误

**动作**：在 task 末尾附加错误信息，调整后重试

**payload 结构**：
```typescript
{ iteration: number }   // 当前迭代次数
```

**响应**：评估调整合理性，决定是否采纳。

---

### 3. switch — 切换工具

**触发条件**：工具不适合

**动作**：切换到 fallback 模型列表中的下一个模型

**payload 结构**：
```typescript
{ iteration: number }   // 当前迭代次数
```

**响应**：通常自动处理，无需人工干预。

---

### 4. replan — 重新规划

**触发条件**：计划根本错误

**动作**：重新规划任务

**payload 结构**：
```typescript
{
  evaluation: string;    // 评估结果
  iteration: number;     // 当前迭代次数
}
```

**响应**：审查新规划，决定是否批准。

---

### 5. learn — 记录经验

**触发条件**：任何失败

**动作**：记录失败经验到 pitfalls 经验库

**payload 结构**：
```typescript
{
  task: string;          // 原始任务
  error: string;         // 错误描述
  iteration: number;     // 迭代次数
}
```

**响应**：记录学习成果，更新知识库。

---

## 信号流转示意

```
dsolo 策略链（agent 执行失败时）：
  retry → adjust → switch → replan → learn
   ↓       ↓        ↓        ↓        ↓
  重试   调整参数  换工具   重新规划   记录经验

dchain 双向沟通：
  dsolo --help/blocked--> dchain
  dchain --adjust-------> dsolo

dteam 内部协调：
  子代理 --progress/blocked/found/help--> owner
  owner 决定是否重建 worker / 调整策略 / 升级人工
```

## 使用注意事项

1. **信号不可变**——一旦发出，不可修改或撤回
2. **TTL 过期**——默认 5 分钟后信号从 query 结果中消失（历史记录仍在）
3. **类型安全**——emit/on/query 均使用 TypeScript 类型约束
4. **进程内通信**——信号总线不走网络，生命周期与 team 实例绑定
