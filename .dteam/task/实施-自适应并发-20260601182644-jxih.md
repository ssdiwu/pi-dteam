## 目标
- 为什么: dteam P2 团队模式（src/P2/team.ts:33）使用 mapWithConcurrencyLimit 配合静态 concurrency 参数。复杂任务中最佳并发度会随 CPU 负载、内存压力、任务队列长度动态变化。any 用"冷启动→探索→稳态→过载保护"机制，dteam 没有，会出现"开多了过载/开少了吞吐低"的两难。
- 做什么: 在 dteam 引入自适应并发控制器：基于系统 CPU/内存采样 + 任务吞吐反馈，动态调节 team 模式实际并发度。冷启动保守、探索期递增、稳态期围绕最优值微调、过载保护自动降级。

- P0 新增 `adaptiveConcurrency.ts`：采样器（CPU/内存/吞吐）+ 状态机（coldStart/exploring/steady/overload）

- 单元测试：状态机转移、采样器、边界保护

- 全局并发预算（多个 team 共享一个并发池，独立 task）
- LLM 模型自适应（指 worker 内调用的模型选择，不在本 task）

## 阶段记录

### 探索发现

#### 当前并发控制

- `src/P2/team.ts`：使用 `mapWithConcurrencyLimit` 配合静态 `concurrency` 参数
- `src/P0/concurrency.ts`：提供 `mapWithConcurrencyLimit` 工具函数
- 并发度由用户显式传入，不随系统负载动态调整

#### 系统资源采样

- Node.js 提供 `os.cpus()` 和 `os.freemem()` 获取 CPU 和内存信息
- 需要定期采样（如每 5 秒）计算 CPU 使用率和可用内存

#### 自适应并发状态机

参考业界实践，状态机包含 4 个状态：
- `coldStart`：初始保守，从 minConcurrency 开始
- `exploring`：逐步递增，探索最优并发度
- `steady`：稳态微调，围绕最优值 ±1
- `overload`：过载保护，CPU > 85% 或内存 < 500MB 时降级

### 讨论决策

#### 实现方案

1. 新增 `src/P0/adaptiveConcurrency.ts`：状态机 + 采样器
2. 修改 `src/P2/team.ts`：集成自适应并发控制器
3. 新增配置字段：`concurrencyMode: "static" | "adaptive"`，默认 adaptive

#### 状态机转移规则

```
coldStart → exploring: 首次采样完成
exploring → steady: 吞吐稳定（连续 N 次采样无显著变化）
steady → overload: CPU > 85% 或内存 < 500MB
overload → steady: CPU < 70% 且内存 > 1GB
```

#### 边界保护

- `minConcurrency`：最小并发数（默认 1）
- `maxConcurrency`：最大并发数（默认 8）
- 任何状态下并发数不得突破边界

#### 兼容性

- 显式传 `concurrency` 时走原 `mapWithConcurrencyLimit`，行为不变
- 不传时默认走自适应模式
