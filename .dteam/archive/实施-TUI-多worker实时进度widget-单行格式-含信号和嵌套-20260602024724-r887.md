## 目标
- 为什么: dteam 当前 worker widget 有 4 个问题：(1) Tools/Elapsed 永远不动，不实时刷新；(2) 同一时间只能显示一个 worker；(3) background worker 完成后不清理；(4) 不显示信号类型和 chain/team 嵌套关系。用户需要看到多个后台 worker 并行运行的实时状态、信号事件、父子关系。
- 做什么: 实现折叠态多 worker 单行实时进度 widget + 嵌套关系可视化 + 信号角标；支持 A 变体方案（widget 详细 + status bar 极简计数）；修掉 background 不清理的 bug；onProgress 链路全程贯通。

## 范围- 包含:
  - 折叠态 widget: 多 worker 单行 + 1s 跳秒 + 实时 currentTool + 信号角标 + 嵌套缩进
  - status bar: 极简计数 (N workers · M running)
  - background worker 终态自动清理 widget 行
  - onProgress 链路全贯通: P4 wrapWorker → P2 context → P2 spawnAgent onUpdate/onToolEvent → P4 updateAgentProgress → widget store
  - chain/team 子 worker 透传 onProgress + parentWorkerId
  - 4 种信号类型 (progress/blocked/found/help) 在 widget 行末以角标显示
  - chain 步骤以 `→` 横排可视化，team 子 worker 缩进挂在 team 父节点下
  - dispose 正确清理: clearInterval + 清 tui 引用 + setWidget(undefined)
  - 单元测试覆盖核心路径 (progress 注入、信号桥接、嵌套、清理)

- 排除:
  - 展开态 (Ctrl+O 全屏): 独立 task，本期不实现
  - 嵌套层级超过 3 层时的 UI 截断算法: 暂用简单折叠 (多层缩进)
  - 信号历史滚动回放: 只保留最近一次信号
  - 多终端 (RPC mode) 同步: 单 TUI 实例假设
  - widget 主题自定义: 用现有 token (success/error/warning/muted/accent)
  - dteam tool 之外的 worker 工具 (worker_create/worker_status 等) UI 改动
  - 重构 P3 事件总线 (本期用直接闭包回调，避免架构大改)

#### 6. 修正 #2：onProgress 链路"通了但丢了 workerId 维度"

更深挖发现，链路是通的但**关键的 workerId 关联没建立**：

| 节点 | 现状 | 关键问题 |
|---|---|---|
| `P4/index.ts:86` `wrapWorker` 注入 `onProgress: updateAgentProgress` | ✅ | **但 updateAgentProgress 签名只接 `AgentProgress`，不接 workerId**（`worker-widget.ts:281`）|
| `P2/worker.ts:328` `workerStart({ onProgress })` 参数 | ✅ | 接收 onProgress 但不绑定 workerId |
| `P2/worker.ts:375-376` 注入 `context.onProgress = onProgress` | ✅ | **context 也没有 workerId 字段**（`contextBuilder.ts:33-47`）|
| `P2/worker.ts:197-211` 默认 executor 调 `spawnAgent` 转发 onUpdate/onToolEvent | ✅ | 但 onUpdate 也不带 workerId |

**根因 1（更深层）**：
- wrapWorker 给主 LLM 的 workerId 是 `worker-${Date.now()}-${random}`（`P2/worker.ts:workerCreate`）
- `P2/solo.ts:19` 内部用 `solo-${Date.now()}` 当 workerId
- `P2/chain.ts:25` 内部用 `chain-${Date.now()}` 当 workerId
- `P2/team.ts:31` 内部用 `team-${Date.now}` 当 workerId
- **这些 ID 互不相通**！主 LLM 视角的 `worker-xxx` 不会出现在 `bus.emit` 的 signal 中

**修复方案**：
1. wrapWorker 注入的 onProgress 改为 `(p) => updateAgentProgress(workerId, p)` —— **闭包绑定 workerId**
2. updateAgentProgress 签名改为 `updateAgentProgress(workerId: string, progress: AgentProgress)`
3. WorkerProgressStore 用 `Map<workerId, WorkerProgress>` 索引
4. P2/worker.ts 的 onComplete 也用同样方式传 workerId

#### 7. 修正 #3：现有 dispose 有内存泄漏风险

| 位置 | 现状 | 风险 |
|---|---|---|
| `P4/worker-widget.ts:413` `fullscreenRefreshTimer = setInterval(...)` | 有 timer | ✅ `closeFullscreen` 有 clearInterval |
| `P4/worker-widget.ts:228-230` `setWidget` 工厂返回的 component | **没实现 `dispose()`** | ❌ setWidget 被新 factory 替换时，旧 timer 不会清 |
| `P4/worker-widget.ts:283-289` updateAgentProgress 不通知 tui 重绘 | tui 引用没存 | ❌ 外部事件不能触发折叠 widget 重绘 |
| `WorkerStatusBox.invalidate()` 空实现 | 没清缓存 | ⚠️ theme 切换时 widget 不会更新 |

**修复方案**：
- Widget 工厂改回 `(tui, theme) => { activeTui = tui; return { render, invalidate, dispose } }`
- `dispose()` 负责 clearInterval + 清 tui 引用
- `invalidate()` 调 `this.cachedLines = undefined`（参考官方推荐模式）

#### 经验教训（学到的东西）

1. **设计阶段必须先深入读现有代码** —— 这次 design 阶段误以为 widget 啥都没实现，实际已有 438 行 + 14 测试。修正后才发现原 task `qsvg` 目标（Ctrl+O 展开）已实现。**教训**：design agent 必读全文件、跑测试、读 git log，不要凭印象设计。

2. **链路断了要追到根因** —— onProgress 链路"通了但丢了 workerId 维度"是最深 bug。链路每一节看起来 OK（inject onProgress / set context.onProgress / call spawnAgent onUpdate），但 workerId 没在闭包里绑定，所有 store 写入都丢 workerId 维度。**教训**：链路审查要看"数据流经每节点时是否保留业务 key"，不是只看"调用是否成立"。

3. **mock 类型断言隐藏 bug** —— `(state as any).workerId ?? "unknown"` 这种写法第一眼像"防御性 fallback"，实际掩盖了"上游没传 workerId"的根因。**教训**：`as any` 是 bug 温床；类型断言应该报错而不是 fallback 默认值。

4. **动态 import 丢异步事件** —— `import("./worker-widget.js").then(...)` 是异步的，progress 事件高频触发时堆在 microtask 里会丢。**教训**：node_modules 解析过的路径用静态 import；动态 import 只用于真的"按需加载"（首次访问才加载）。

5. **dispose 必须真清** —— `dispose() { disposedCount += 1 }` 测计数 OK 但不清 interval 实际泄漏。**教训**：dispose 测试要验证"真清"，不能只数调用次数。

6. **检查 agent 必跑** —— 5 个 bug 都是 build agent 自验时没发现。**教训**：build + check 分离，check agent 用 fresh 上下文，不被"已经过了"的认知污染。
